# Контракт поручений ЭДО ↔ Workspace, версия 1

Дата: 2026-10-14. Результат задачи 1: контракт для реализации задач 2–8.
**Приёмник v1 реализован в задаче 3; отправитель и неизменяемый outbox — в задаче 4.** Раздел 7 сохраняет исходный аудит задачи 1. Текущее поведение, миграции и порядок включения описаны в [документе приёмника](odo-assignments-receiver.md) и [документе отправителя](odo-assignments-sender.md). Это не подтверждение развёртывания на production.
Сервисную авторизацию этапа 2 и правила настройки описывает [отдельный документ](odo-assignments-service-auth.md).

## 1. Источник данных и существующие маршруты

ЭДО — источник истины для поручения, его исполнителя и статуса. Workspace хранит проекцию для раздела «Работа / Поручения», а не независимое поручение.

| Направление | Существующий маршрут | Назначение |
|---|---|---|
| ЭДО → Workspace | `POST /api/v1/internal/documentolog/assignments/upsert` | Получить снимок поручения |
| Фронт → Workspace | `GET /api/v1/kanban/documentolog/assignments` | Получить поручения текущего исполнителя |
| Workspace → ЭДО | `POST /api/v1/workspace/assignments/{id}/complete` | Команда задачи 6 с пользовательской идентичностью, expected revision и durable receipt; старый маршрут `/workflow/assignments/{id}/complete` сохраняется отдельно |

`source_system="documentolog"` и существующие пути сохраняются для совместимости. В интерфейсе источник называется «ЭДО». Переименование маршрутов или массовое изменение старых задач не входит в контракт.

## 2. Идентификаторы и границы компании

| Поле | Значение и правила |
|---|---|
| `organization_id` | UUID компании Workspace; ЭДО уже получает его через каталог Workspace. Не ID подразделения и не ID клиента Keycloak. Если отдельная установка ЭДО имеет другую систему ID, нужна явная серверная таблица соответствия. |
| `assignment_id` | Непрозрачный строковый ID поручения ЭДО, до 255 символов. Не преобразовывать в UUID задачи Workspace. |
| `document_id` | Непрозрачный ID исходного документа ЭДО, до 255 символов. Не UUID файла Drive. |
| `identity_issuer` | Точный `iss` доверенного Keycloak realm. URL без нормализации, удаления slash или автоматической подстановки другого realm. |
| `author_sub`, `assignee_sub` | Непрозрачные строки Keycloak `sub`, до 255 символов, в пространстве `identity_issuer`. Не email, логин, ИИН, числовой ID Workspace или локальный ID пользователя ЭДО. |
| `department_id` | ID подразделения из структуры текущей компании Workspace либо null. |
| `task.id`, `board_id` в ответе | UUID локальной задачи и системной доски Workspace; ЭДО хранит их как результат синхронизации. |

Ключ поручения в Workspace: **(`organization_id`, `source_system`, `assignment_id`)**. Компания поручения неизменяема; смена компании требует отдельного бизнес-сценария, а не upsert существующей записи.

Сопоставление пользователя: доверенный `identity_issuer` + `sub` → пользователь Workspace. Пока Workspace хранит только `keycloak_id`, допустим только его настроенный issuer; второй realm нельзя подключать без изменения модели идентичности.

ЭДО иногда использует резервный ID `workspace:<число>`. В протоколе v1 такой ID в `author_sub`/`assignee_sub` запрещён: адаптер должен найти реальный Keycloak ID в каталоге указанной компании. Если его нет, запись остаётся недоставленной с диагностикой. Поиск по email и автоматическое создание пользователя запрещены.

Компания из тела — проверяемое утверждение отправителя, а не право доступа. Приёмник проверяет доверенную интеграцию и её разрешённые компании, принадлежность документа по доверенным данным ЭДО, участников и подразделения. Из одного тела нельзя независимо доказать компанию документа; для этого нужна доверенная привязка источника или проверка на стороне ЭДО.
Автор сохраняется как исторический участник. Его увольнение не должно делать старое поручение нечитаемым; историческая принадлежность проверяется по сохранённой доверенной связи. Назначение нового исполнителя требует активного пользователя текущей компании. Переход пользователя в другую компанию не переносит вместе с ним старые поручения.
Права на доску не заменяют проверку компании. GET возвращает только поручения текущего исполнителя с доступом к компании и модулю ЭДО; владение системной доской не раскрывает чужие поручения.

## 3. Запрос: полный снимок, а не PATCH

JSON Schema: [odo-assignment-event.schema.json](contracts/odo-assignment-event.schema.json).
Проверенные примеры: [odo-assignment-events.json](contracts/examples/odo-assignment-events.json).

| Поле | Тип | Смысл |
|---|---|---|
| `schema_version` | integer, всегда 1 | Версия протокола |
| `event_id` | UUID | Один ID события для всех попыток доставки |
| `event_type` | `created`, `updated`, `status_updated` | Причина формирования снимка; `updated` также используется для первоначальной сверки существующих поручений |
| `occurred_at` | RFC 3339 UTC | Время фиксации события, не время очередной отправки |
| `revision` | integer, 1…9007199254740991 | Монотонная версия конкретного поручения |
| `organization_id`, `source_system` | UUID, `documentolog` | Компания и источник |
| `identity_issuer` | URI | Доверенный issuer идентификаторов участников |
| `assignment_id`, `document_id` | string | Исходные идентификаторы |
| `author_sub`, `assignee_sub` | string | Автор и один исполнитель |
| `title` | string, 1…255 | Название; отправитель задаёт осмысленное название, без fallback при приёме |
| `description` | string, до 20000 | Описание; пустая строка очищает описание |
| `department_id` | string или null | null очищает привязку подразделения |
| `priority` | `low`, `medium`, `high`, `critical` | Нормализованный приоритет |
| `due_date` | `YYYY-MM-DD` или null | Дата срока без времени; null очищает срок |
| `timezone` | string | IANA timezone компании на момент формирования снимка |
| `status` | `assigned`, `in_progress`, `completed`, `closed`, `cancelled` | Исходный нормализованный статус ЭДО |
| `source_url` | абсолютный HTTPS URL или null | Ссылка на поручение в разрешённом публичном origin ЭДО; без токенов и credentials |
| `completed_at`, `closed_at` | RFC 3339 UTC или null | Даты выполнения/закрытия; не подменять текущим временем при повторной доставке |

Все перечисленные поля обязательны. Для очищаемых полей требуется явный null или пустая строка по таблице. Пропуск поля — ошибка v1, а не команда оставить старое значение. JSON Schema проверяет структуру; существование компании, документов, пользователей и IANA timezone проверяется бизнес-логикой.
Даты выполнения/закрытия исторических записей могут быть неизвестны: тогда передаётся null, без выдуманной даты. Новые события выполнения/закрытия используют время, сохранённое ЭДО в транзакции. closed_at допустимо только в статусе closed; completed_at — только в completed/closed. Если обе даты известны, closed_at не раньше completed_at. Срок должен быть реальной календарной датой, не только строкой подходящего формата.

Если в ЭДО поручение назначено нескольким людям, существующая реализация создаёт отдельные записи поручений: каждому `assignment_id` соответствует один `assignee_sub`. Массив исполнителей и общий статус на всех в v1 не вводятся.
`board_id` не входит в запрос v1: приёмник выбирает системную доску по компании. Legacy-настройка общей доски не должна позволять направлять поручение в чужую компанию.

Отправитель сохраняет снимок, revision и событие вместе с изменением поручения в одной транзакции. При повторе нельзя дополнять старый снимок новыми данными из текущей строки БД: иначе поля и revision перестанут соответствовать друг другу.

## 4. Статусы и приоритеты

| Статус ЭДО на входе | Статус протокола / `source_status` | Статус задачи Workspace | Отображение |
|---|---|---|---|
| `open` или `assigned` | `assigned` | `К ВЫПОЛНЕНИЮ` | Назначено |
| `in_progress` | `in_progress` | `В РАБОТЕ` | В работе |
| `done` или `completed` | `completed` | `ГОТОВО` | Выполнено |
| `closed` | `closed` | `ГОТОВО` | Закрыто |
| `cancelled` | `cancelled` | `cancelled` | Отменено |

`open` и `done` — legacy-алиасы: отправитель преобразует их до отправки. Приёмник v1 принимает только пять канонических статусов. `completed` и `closed` нельзя объединять в исходном статусе: выполненное поручение ещё может требовать закрытия автором.

Переходы, проверяемые в ЭДО по текущей реализации:
- `assigned` → `in_progress`, `completed`, `cancelled`;
- `in_progress` → `assigned`, `completed`, `cancelled`;
- `completed` → `closed`;
- `closed` и `cancelled` — окончательные;
- повтор того же статуса допустим при соблюдении прав.

Получение первого снимка сразу в `completed`/`closed` допустимо при первоначальном переносе. Репликация не проигрывает промежуточные бизнес-переходы; она применяет доверенный снимок с более высокой revision.
Просрочка — вычисляемый признак, не отдельный статус. Поручение просрочено после окончания `due_date` в его `timezone`, если статус `assigned` или `in_progress`. `completed`, `closed`, `cancelled` не считаются просроченными.

| Приоритет в ЭДО | Приоритет протокола и Workspace |
|---|---|
| `low` | `low` |
| `normal` или `medium` | `medium` |
| `high` | `high` |
| `critical` | `critical` |

Неизвестный приоритет — ошибка адаптера. Пустой legacy-приоритет отправитель преобразует в `medium`. Русские подписи — только UI, не значения API.

`due_date` остаётся датой без времени. Фронт не должен считать её UTC timestamp или определять просрочку по часовому поясу браузера. Существующее `due_at` может оставаться для совместимости, но новый ответ должен дополнительно сохранять исходные `source_due_date` и `source_timezone`.

## 5. Порядок, идемпотентность и подтверждение

Заголовки: `Authorization: Bearer <integration token>`, `Content-Type: application/json`, `Idempotency-Key: odo-assignment:<event_id>`; `X-Request-ID` — для трассировки. Секреты и пользовательские токены не входят в событие.

Revision начинается с 1, увеличивается на каждое изменение синхронизируемых полей и хранится в ЭДО. Она не является timestamp или порядковым номером попытки отправки. При контролируемом backfill исправленный снимок один раз получает `max(source revision, observed Workspace revision)+1`; повтор того же плана использует сохранённую revision, event ID и тело, а не создаёт новую версию на каждый запуск. Порядок запуска описан в [задаче 5](odo-assignments-backfill.md).

Приёмник применяет сравнение revision и запись всех полей атомарно:
1. Нет проекции — создать её из полного снимка, даже если это `updated` или `status_updated`.
2. Входящая revision больше сохранённой — полностью обновить проекцию и текущего исполнителя.
3. Та же revision и тот же семантический снимок — подтвердить без повторного изменения/уведомления.
4. Более старая revision — подтвердить как устаревшую без изменения данных.
5. Та же revision, но другой снимок — 409 `ODO_REVISION_CONFLICT`; перезапись запрещена.
6. Повторный `event_id` с другим телом либо несовпадающий `Idempotency-Key` — конфликт/ошибка валидации. Идентификатор нельзя использовать для чужого поручения или другой компании.

Для сравнения семантического снимка исключаются `event_id`, `event_type`, `occurred_at`; остальные поля снимка входят в сравнение. Для выявления изменения тела одного event_id сравнивается весь JSON после канонизации порядка ключей. `created` с revision 1 не получает право обнулить более новую запись.

При смене исполнителя старый перестаёт видеть поручение в своих поручениях; новый начинает видеть после успешного применения снимка. Недостаточно добавить нового исполнителя в доску, оставив старую связь с задачей.

Успех: HTTP 200, существующие `task`, `board_id`, `source_system` сохраняются; добавляются:

```json
{
  "task": {"id": "77777777-7777-4777-8777-777777777777"},
  "board_id": "88888888-8888-4888-8888-888888888888",
  "source_system": "documentolog",
  "organization_id": "11111111-1111-4111-8111-111111111111",
  "assignment_id": "asg-example-1",
  "event_id": "bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb",
  "received_revision": 2,
  "current_revision": 2,
  "applied": true,
  "outcome": "updated"
}
```

`task` здесь сокращён для примера; в реальном ответе сохраняется существующий объект задачи. `outcome`: `created`, `updated`, `duplicate`, `stale`. Последние два имеют `applied=false`; для `stale` current_revision больше received_revision. Подтверждение отправляется только после commit, а повтор не создаёт новую задачу.

Отправитель отмечает событие доставленным только после проверки 200 и совпадения компании, assignment_id, event_id, received_revision и непустых task.id/board_id. Timeout после commit повторяется с тем же event_id, ключом и телом.

| Ответ | Действие отправителя |
|---|---|
| 200, валидное подтверждение | Пометить событие доставленным, включая duplicate/stale |
| Timeout, сетевой сбой, 429, 5xx | Повторить с задержкой; учитывать Retry-After; тело и идентификаторы не менять |
| 401 | Один раз обновить сервисный токен, затем повторить; устойчивый отказ требует диагностики конфигурации |
| 403 | Не обходить права, отправить в диагностируемое состояние ошибки |
| 404 неизвестного исполнителя/привязки | Диагностика каталога, контролируемая повторная отправка после исправления |
| 400/422 либо 409 | Не бесконечно повторять; исправить данные/конфликт и сформировать корректное событие |
| 200 с неполным/несовпадающим подтверждением | Не считать доставленным; ограниченные повторы и диагностика несовместимого приёмника |

Коды `ODO_REVISION_CONFLICT`, `ODO_EVENT_CONFLICT`, `ODO_LEGACY_CONFLICT` и новые поля подтверждения реализованы приёмником задачи 3. Формат ошибок остаётся общим для API Workspace; ошибки не содержат токенов или содержимого документов.

## 6. Чтение и выполнение из Workspace

GET списка сохраняет массив существующих Task DTO и поля `source_system`, `source_assignment_id`, `source_document_id`, `source_url`, `source_author_sub`, `source_department_id`. Целевые добавления: `source_organization_id`, `source_status`, `source_revision`, `source_due_date`, `source_timezone`. `task.id` остаётся локальным UUID; для команды в ЭДО используется `source_assignment_id` и проверенная компания.
Отменённые и закрытые поручения сохраняются для истории; фильтрация списка — задача интерфейса, а не удаление исходной записи. Ссылка на ЭДО не выдаёт доступ к документу: ЭДО повторно проверяет пользователя и права. Отсутствие source_url означает отсутствие кнопки перехода, а не генерацию произвольной ссылки фронтом.

«Выполнено» — пользовательская команда, отдельно от события репликации. В задаче 6 реализован `POST /api/v1/kanban/documentolog/assignments/{task UUID}/complete`: команда несёт проверенного пользователя, компанию, ID поручения, ожидаемую source_revision, ID команды и результат выполнения; ЭДО проверяет актуальные права и переход. Вызов служебным токеном без проверенной идентичности пользователя не разрешает выполнение от его имени.
Успех показывается после durable receipt ЭДО; новая revision возвращается через синхронизацию. При недоступности ЭДО статус не подменяется успешным. Повтор использует прежние command ID, revision и результат; проекция Workspace не изменяется напрямую. Контракт, настройки и порядок подключения интерфейса описаны в [задаче 6](odo-assignments-completion.md). Фронтенд подключается в задаче 7.

## 7. Текущее состояние и необходимые изменения

| Проверено в коде | Следствие / задача |
|---|---|
| DTO Workspace содержит assignment_id, document_id, author_sub, assignee_sub и бизнес-поля, но не organization_id, issuer, revision, event_id или schema_version | Задача 3: добавить строгий приём v1 и атомарную проекцию |
| Поиск и уникальность текущей задачи используют только assignment_id для documentolog | Задача 3: компания должна входить в ключ и в проверки доступа; миграция нужна в реализации, не в задаче 1 |
| Обновление существующей задачи меняет только completed/closed/cancelled | Задача 3: применять полный снимок и сохранять исходный статус |
| Создание по умолчанию привязывает системную доску к вызывающему пользователю | Задачи 2–3: определить доверенного отправителя и доску компании; не считать ID сервисного пользователя компанией документа |
| Воркер ЭДО получает client_credentials, а приёмник Workspace использует пользовательскую авторизацию и проверку списка ролей | Задача 2: согласовать проверку сервисной идентичности и разрешённых компаний; наличие слова internal в пути не является защитой |
| ЭДО имеет durable outbox и второй путь с передачей токена пользователя | Задачи 2 и 4: основной надёжный путь — outbox; токен пользователя не сохранять для фоновых повторов; два пути не должны порождать разные снимки одной revision |
| Воркер дополняет payload текущими деталями из БД в момент доставки | Задача 4: фиксировать все детали и revision транзакционно; не смешивать старый статус с новым текстом |
| Очередь формируется при создании/смене статуса; гарантированная публикация всех изменений деталей не подтверждена | Задача 4: покрыть изменение текста, срока, приоритета, подразделения и исполнителя |
| Legacy idempotency_key использует только assignment_id; DTO Workspace его не обрабатывает | Задачи 3–4: различать ключ поручения и ключ события, защитить параллельные и повторные доставки |
| Фронт меняет статус локальной Kanban-задачи | Задачи 6–7: отдельная команда выполнения ЭДО и отображение source_status |

Ввод v1: сначала реализовать приёмник и его проверки, затем переключать отправитель. Отправитель не должен считать поддержку неизвестных полей старым JSON-декодером поддержкой v1: существующий endpoint может их проигнорировать.
Legacy-запросы без schema_version должны оставаться на явно отделённом проверенном пути до миграции отправителей; их нельзя считать событиями v1 или придумывать им issuer/компанию/revision из непроверенного тела. Правила безопасного доступа legacy-пути реализуются в задаче 2.
После переключения воркера, заполнения компаний и первоначальной сверки legacy-доставка отключается контролируемо. Пользовательский GET и техническое source_system остаются совместимыми.

## 8. Проверка готовности реализации контракта

1. Исполнитель получает своё поручение; другой пользователь или компания его не видит.
2. Сопоставление идёт по доверенному issuer/sub; email и workspace:<id> не принимаются вместо sub.
3. normal → medium, open → assigned, done → completed; неизвестные значения отвергаются.
4. Смена срока, текста и исполнителя отражается в Workspace; null действительно очищает поле.
5. Повтор после timeout не создаёт дубль и не повторяет уведомление.
6. revision 3 после revision 4 не откатывает состояние; разные данные одной revision дают конфликт.
7. Первый снимок завершённого поручения сохраняет completed/closed, включая исходные даты.
8. Закрытое/отменённое поручение не подсвечивается как просроченное; граница срока вычисляется в timezone компании.
9. Поручение можно повторно доставить после восстановления связи; долговременные ошибки видны оператору.
10. Команда выполнения из Workspace не показывает успех без подтверждения ЭДО.
