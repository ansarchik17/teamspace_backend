# План: добавить пользователя в активный 1-на-1 видеозвонок

## Цель

Нужно, чтобы во время обычного 1-на-1 звонка участник мог добавить еще одного пользователя, и звонок продолжился в той же LiveKit комнате как групповой. Важно: это не должно создавать новый отдельный звонок между приглашающим и третьим пользователем.

## Общая модель для 1-на-1 и группового звонка

Да, после добавления третьего пользователя 1-на-1 звонок по факту становится групповым звонком. Поэтому дальше логика должна быть общей:

- есть один `call_id`;
- есть один `room_name`;
- есть один список участников звонка;
- каждый участник имеет свой статус: `invited`, `ringing`, `joined`, `left`, `declined`, `missed`;
- LiveKit комната не меняется при добавлении новых людей;
- новые участники добавляются через invite, а не через start нового звонка.

Разница только в том, как звонок начинается:

- 1-на-1 начинается через `/calls/start`;
- групповой чат начинается через `/calls/group/start`;
- после старта оба типа звонка должны работать через одну participant-based логику.

То есть backend может внутри хранить `call_type`:

- `private` - обычный 1-на-1 до добавления третьего пользователя;
- `group` - обычный групповой звонок из группового чата;
- `upgraded_group` или `group` - бывший 1-на-1, куда добавили еще участника.

Для мобильной части важно не название типа, а поведение: если в текущем звонке нужно добавить пользователя, всегда использовать `/calls/invite` с текущими `call_id` и `room_name`.

## Что сейчас уже есть в мобильной части

- В `LiveKitCallPage` уже есть кнопка/диалог приглашения участников.
- Диалог умеет:
  - показывать участников звонка;
  - искать пользователей;
  - отправлять ссылку в чат;
  - вызывать `CallRemoteDataSource.inviteToCall(...)`.
- Видеолэйаут уже рассчитан не только на 2 участников, поэтому базово 3 участника в комнате отрисоваться должны.

## Главная проблема текущей логики

Часть мобильной логики уже пытается приглашать пользователя через `/calls/invite`, но есть риск, что:

- бэк не переводит приватный звонок в групповой режим;
- приглашение не привязывается к текущему `call_id`;
- третий пользователь получает/принимает приглашение как новый звонок;
- повторный звонок участнику из списка сейчас может вызывать `startCall`, а это создает новый 1-на-1 звонок вместо приглашения в текущий.

## Что нужно изменить на бэке

### 0. Сделать единый lifecycle для private-upgraded и group calls

Бэку лучше привести 1-на-1 после invite и обычный групповой звонок к одной модели.

Единая модель:

```text
call
  id
  room_name
  call_type: private | group
  source: private_chat | group_chat | meeting_link
  chat_id/conversation_id/group_id
  status: ringing | accepted | ongoing | ended

call_participants
  call_id
  user_id
  role: host | participant
  status: invited | ringing | joined | left | declined | missed
  joined_at
  left_at
```

Для 1-на-1:

- `/calls/start` создает call и 2 participant-записи;
- caller сразу `joined`;
- callee `ringing`;
- когда callee принимает, он становится `joined`.

Для группового звонка:

- `/calls/group/start` создает call и participant-записи для участников группы;
- caller сразу `joined`;
- остальные участники `ringing` или `invited`;
- accept работает так же, как в upgraded 1-на-1.

Для добавления пользователя:

- `/calls/invite` добавляет нового participant в существующий call;
- если call был `private`, он становится `group`;
- если call уже был `group`, просто добавляется еще один participant.

### 1. Доделать `POST /api/v1/calls/invite`

Эндпоинт должен добавлять пользователя в уже существующий активный звонок.

Рекомендуемый запрос:

```json
{
  "call_id": "current-call-id",
  "room_name": "current-livekit-room",
  "callee_id": 123,
  "chat_id": 456,
  "is_video": true
}
```

Правила:

- пользователь, который приглашает, должен быть участником текущего звонка;
- звонок должен быть активным: `ringing`, `accepted` или `ongoing`;
- если звонок был приватным, его нужно пометить как групповой;
- если звонок уже был групповым, просто добавить участника в этот же звонок;
- новый пользователь добавляется в таблицу участников звонка со статусом `invited` или `ringing`;
- `call_id` и `room_name` должны остаться теми же, что у текущего звонка.

Рекомендуемый ответ:

```json
{
  "call_id": "current-call-id",
  "room_name": "current-livekit-room",
  "livekit_url": "wss://livekit.example.com",
  "invited_user_id": 123,
  "status": "invited"
}
```

### 2. Отправить invite-событие третьему пользователю

После `/calls/invite` бэк должен отправить третьему пользователю обычное входящее событие звонка через WebSocket/FCM.

Payload должен содержать:

```json
{
  "event": "incoming_call",
  "call_id": "current-call-id",
  "room_id": "current-livekit-room",
  "room_name": "current-livekit-room",
  "livekit_url": "wss://livekit.example.com",
  "livekit_token": "token-for-invited-user",
  "caller_id": 9,
  "caller_name": "User Name",
  "invited_by_user_id": 9,
  "is_video": true,
  "call_type": "group",
  "is_group_call": true
}
```

Можно оставить `incoming_call`, чтобы старая мобильная логика входящего звонка продолжила работать. Главное, чтобы `call_id` и `room_name` были от текущего звонка.

### 3. Исправить `POST /api/v1/calls/accept`

Сейчас приватная логика может быть завязана на одного callee. Для добавления третьего пользователя и для нормального группового звонка accept должен работать по участникам.

Правила:

- если пользователь есть в participants со статусом `invited` или `ringing`, он может принять звонок;
- accept не должен падать только потому, что звонок уже был принят вторым участником;
- бэк должен выдать LiveKit token для той же комнаты;
- статус конкретного участника меняется на `joined`;
- существующие участники получают событие `participant_joined`.

### 4. Исправить `POST /api/v1/calls/end`

Для группового или upgraded-звонка один участник не всегда должен завершать звонок для всех. Эта логика одинаковая и для звонка, который начался как group call, и для 1-на-1, который стал group после invite.

Нужна семантика:

- обычный выход участника: пометить только его как `left`;
- отправить остальным `participant_left`;
- весь звонок завершать только если:
  - инициатор явно нажал "завершить для всех";
  - все участники вышли;
  - остался один активный участник после grace timeout.

Для старого приватного 1-на-1 поведения можно оставить текущую логику, пока звонок не был upgraded.

### 4.1. Разделить leave и end-for-all

Чтобы не ломать групповой звонок, желательно иметь два действия:

```json
{
  "call_id": "current-call-id",
  "action": "leave"
}
```

и:

```json
{
  "call_id": "current-call-id",
  "action": "end_for_all"
}
```

Если пока не хочется менять API, можно временно оставить один `/calls/end`, но бэк должен сам понимать:

- private 1-на-1: завершить весь звонок;
- group/upgraded group: обычный участник только выходит;
- host может завершить для всех, если в запросе есть явный флаг.

### 5. Исправить `GET /api/v1/calls/{id}/status`

Статус должен точно возвращать активных участников.

Минимальный ответ:

```json
{
  "call_id": "current-call-id",
  "status": "ongoing",
  "call_type": "group",
  "room_name": "current-livekit-room",
  "participants_count": 3
}
```

Важно: `participants_count` должен считаться по реальным joined-участникам, а не оставаться `0`, когда люди уже в LiveKit комнате.

### 6. Исправить `GET /api/v1/calls/{id}/participants`

Мобильный диалог приглашения уже пытается читать участников. Бэк должен вернуть стабильный список.

Рекомендуемый формат:

```json
{
  "participants": [
    {
      "user_id": 9,
      "full_name": "User One",
      "username": "user_one",
      "avatar_url": null,
      "status": "joined",
      "joined_at": "2026-07-09T10:00:00Z",
      "left_at": null
    },
    {
      "user_id": 123,
      "full_name": "User Three",
      "username": "user_three",
      "avatar_url": null,
      "status": "invited",
      "joined_at": null,
      "left_at": null
    }
  ]
}
```

### 7. LiveKit token

Для всех участников должен использоваться один `room_name`.

Требования к token:

- `roomJoin: true`;
- `canPublish: true`;
- `canSubscribe: true`;
- `canPublishData: true`;
- identity должен быть уникальным для пользователя/устройства.

## Что нужно изменить в мобильной части

### 0. Использовать одну mobile-логику invite для private и group call

В мобильной части не нужно делать отдельную механику добавления для 1-на-1 и группового звонка.

Правило:

- если call screen уже открыт, добавление пользователя всегда идет через `inviteToCall`;
- `startCall` используется только для создания нового 1-на-1 звонка из чата;
- `startGroupCall` используется только для создания нового группового звонка из группового чата;
- внутри активного звонка `startCall` и `startGroupCall` больше не должны вызываться.

### 1. Расширить `inviteToCall`

Файл:

`lib/features/chat/data/datasources/call_remote_datasource.dart`

Нужно добавить в `inviteToCall(...)` параметры:

- `callId`;
- `isVideo`;
- `chatId`;
- текущий `roomName`.

Тело запроса должно отправлять текущий `call_id`, чтобы бэк понял, что это приглашение в существующий звонок.

Пример:

```json
{
  "call_id": "current-call-id",
  "callee_id": 123,
  "room_name": "current-livekit-room",
  "chat_id": 456,
  "is_video": true
}
```

### 2. Передавать `callId` из call page в invite dialog

Файлы:

- `lib/features/chat/presentation/pages/livekit_call_page_invite.part.dart`
- `lib/features/chat/presentation/widgets/livekit_call_page_invite_dialog.dart`

Диалог уже получает `callId`, но все invite-запросы должны реально использовать его при вызове datasource.

### 3. Не использовать `startCall` для повторного приглашения участника

Файл:

`lib/features/chat/presentation/pages/livekit_call_page_invite_methods.part.dart`

Метод, который сейчас звонит пользователю из списка участников, не должен создавать новый звонок через `startCall`.

Нужно заменить на:

- `inviteToCall(...)`;
- тот же `callId`;
- тот же `roomName`;
- тот же `conversationId/chatId`, если он есть.

Это исправление нужно и для 1-на-1 upgraded-звонка, и для обычного группового звонка.

### 4. Обновлять UI после invite

После успешного приглашения:

- показать короткий статус "Приглашение отправлено";
- обновить список participants;
- оставить текущий звонок открытым;
- не делать переход на другой call screen.

### 5. Обработать события участников

Мобильная часть должна обновлять экран по событиям:

- `participant_joined`;
- `participant_left`;
- `call_ended`;
- `incoming_call`.

Если третий пользователь принял invite, у первых двух участников он должен просто появиться в LiveKit комнате.

## Что не нужно делать

- Не создавать новый чат-группу автоматически, если пользователь просто добавил третьего человека в звонок.
- Не создавать новый `/calls/start` при добавлении пользователя.
- Не создавать новый `/calls/group/start` при добавлении пользователя в уже открытый group call.
- Не менять `room_name` после приглашения.
- Не завершать весь звонок, если один из трех участников просто вышел.

## Проверочные сценарии

### Сценарий 1: базовый happy path

1. User A звонит User B.
2. User B принимает.
3. User A нажимает добавить пользователя.
4. User A выбирает User C.
5. User C получает входящий звонок.
6. User C принимает.
7. Все трое находятся в одной LiveKit комнате.
8. У всех один `call_id` и один `room_name`.

### Сценарий 2: третий пользователь отклонил

1. User A и User B уже в звонке.
2. User A приглашает User C.
3. User C отклоняет.
4. User A и User B остаются в звонке.
5. Участник C отображается как `declined` или исчезает из pending.

### Сценарий 3: третий пользователь не ответил

1. User A приглашает User C.
2. User C не отвечает.
3. После timeout User C становится `missed` или `no_answer`.
4. User A и User B остаются в звонке.

### Сценарий 4: третий пользователь вышел

1. В звонке A, B, C.
2. User C нажимает завершить/выйти.
3. User A и User B остаются в звонке.
4. Бэк отправляет `participant_left`, но не `call_ended`.

### Сценарий 5: завершить звонок для всех

1. В звонке A, B, C.
2. User A завершает звонок для всех.
3. User B и User C получают `call_ended`.
4. Все call screens закрываются.

### Сценарий 6: плохая сеть во время invite

1. User A нажимает добавить User C.
2. Сеть плохая или VPN тормозит.
3. Invite-запрос не должен висеть бесконечно.
4. UI показывает ошибку/timeout.
5. User A и User B остаются в текущем звонке.

### Сценарий 7: реконнект в групповом звонке

1. В звонке A, B, C.
2. У User C временно пропадает интернет.
3. User A и User B остаются в звонке.
4. User C переподключается в ту же комнату.
5. Бэк не должен преждевременно отправлять `call_ended`.

### Сценарий 8: обычный групповой звонок из группового чата

1. User A открывает групповой чат.
2. User A начинает групповой видеозвонок.
3. Бэк создает один `call_id` и один `room_name`.
4. User B принимает.
5. User C принимает.
6. Все участники находятся в одной LiveKit комнате.
7. Если User D добавляется во время звонка, используется `/calls/invite`, а не новый `/calls/group/start`.

### Сценарий 9: 1-на-1 превращается в групповой звонок

1. User A звонит User B через личный чат.
2. User B принимает.
3. User A добавляет User C.
4. Бэк оставляет тот же `call_id` и тот же `room_name`.
5. `call_type` становится `group`.
6. User C принимает и входит в ту же LiveKit комнату.
7. Дальше end/reconnect/participants работают так же, как в обычном group call.

## Открытые решения

1. Кто может добавлять пользователя:
   - рекомендация: любой joined-участник;
   - альтернатива: только host/caller.

2. Максимум участников:
   - рекомендация для мобилки: 6 или 8;
   - больше участников лучше делать отдельным групповым call UX.

3. Что означает кнопка завершения:
   - для группового звонка лучше разделить "Выйти" и "Завершить для всех";
   - если оставить одну кнопку, нужно явно решить, завершает ли она только участника или весь звонок.

## Рекомендуемый порядок работ

1. Бэк: привести private, upgraded и group calls к единой participant-based модели.
2. Бэк: реализовать `/calls/invite` как приглашение в текущий `call_id`.
3. Бэк: перевести accept/end/status/participants на общую participant-based логику.
4. Мобилка: отправлять `call_id` в `inviteToCall`.
5. Мобилка: заменить `startCall` внутри invite dialog на `inviteToCall`.
6. Мобилка: убедиться, что внутри открытого call screen не вызывается новый `startGroupCall`.
7. Мобилка: обновлять participants UI после invite/join/leave.
8. Прогнать сценарии из этого документа на двух-трех устройствах.
