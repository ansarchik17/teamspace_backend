# Учёт Unified AI чата: задача 23

Подключён маршрут `POST /api/v1/unified-ai/chats/:id/messages` через `UnifiedAIService`. Общий `AIPaidCallerService` инициализирован в `cmd/api/main.go`; отсутствие зависимостей учёта закрывает платный путь с ошибкой `AI_CHAT_ACCESS`. Владение чатом проверяется до начала генерации. Идентичность пользователя берётся из проверенного обработчика, компания — через серверный `UserRepository.GetByID`. Активность и членство в компании повторно валидируются в транзакции резервирования. Плательщиком всегда выступает проверенный пользователь.

## Архитектура и переиспользование общего адаптера

Для исключения дублирования жизненного цикла резервирования `UnifiedAIService` переиспользует единый механизм учёта:
- `aiPaidUserContext`: общая серверная валидация пользователя, его активности, отсутствия soft delete и принадлежности к компании.
- `alemPaidChat`: универсальный адаптер над `aiCompletionClient`, параметризованный префиксом ключа идемпотентности (`unified_ai:`) и источником операции (`unified_ai_chat`).
- `alemChatEvidence`: общее извлечение и валидация реальных токенов (`prompt_tokens`, `completion_tokens`, cached, reasoning) из `resp.AccountingUsage`, расчёт стоимости по закреплённой тарифной политике задачи 08 и отклонение нулевого расхода без доказательств бесплатности.
- `alemSingleAttempt`: транспортные повторы отключены (`CreateChatCompletionOnce`). Ошибка сети/таймаут без подтверждения расхода оставляет удержание (hold) для фоновой сверки задачи 20.

## Жизненный цикл сообщения и fallback

1. **Проверка прав и контекста**: проверяется владение чатом и извлекается проверенный контекст плательщика через `s.paidUserContext(ctx, userID)`.
2. **Фиксация пользовательского сообщения**: сообщение пользователя записывается в таблицу `unified_ai_messages` через `CreateMessageWithID` с получением серверного UUID (`turnID`).
3. **Резервирование**: на основе текста, истории и переданного `max_tokens` (1000) оценивается верхняя граница входа и выхода в микрокредитах. Атомарно проверяются бюджет компании, недельная квота и пятичасовое личное окно.
4. **Отправка и фиксация расхода**: после отметки `MarkSent` выполняется один HTTP-запрос провайдеру. При успехе фактические токены из `usage` списываются через `SettleSuccess`, резерв закрывается.
5. **Смена модели и fallback**: если выбранная пользователем модель отклонена провайдером (`isModelAccessDenied`), первая попытка фиксируется с исходом `unknown` и сохраняет удержание. Затем автоматически инициируется **вторая независимая попытка** под `defaultModel` с отдельным резервом по её тарифам и раздельным списанием. Модель чата в БД обновляется на дефолтную.
6. **Независимость фиксации расхода от истории**: ответ ассистента сохраняется в `unified_ai_messages` после успешного завершения платёжной транзакции. Если при сохранении сообщения в базу данных происходит сбой (например, переполнение диска), метод возвращает ошибку, однако **уже проведённый платёж остаётся оплаченным**, а повторная генерация ради восстановления текста в истории не производится.

## Обработка ошибок в API

В HTTP-обработчике `UnifiedAIHandler.SendMessage`:
- Отказ в резерве (`AIReservationDenied`) транслируется в HTTP 429 с кодом `AI_CREDIT_LIMIT` (или 403 `AI_CHAT_ACCESS` при блокировке компании/аккаунта).
- Отсутствие контекста плательщика или несовпадение компании транслируется в HTTP 403 с кодом `AI_CHAT_ACCESS`.
- Ошибки локализуются на русском и казахском языках через `internal/i18n/ai_chat.json`.
- Внутренние диагностические сообщения, секреты и детали провайдера клиенту не возвращаются.

## Проверки

Реализованы тесты:
1. **Unit-тесты (`internal/service/unified_ai_accounting_test.go`)**:
   - отсутствие проверенного плательщика (не настроен сервис, неактивный пользователь, отсутствие компании, несовпадение контекста);
   - отказ по квоте до обращения к провайдеру (провайдер не вызывается);
   - ошибка провайдера с неизвестным расходом (исход `unknown`, удержание сохранено);
   - успешная генерация и сохранение сообщения;
   - успешная генерация с последующей ошибкой сохранения ассистента (вызов остаётся оплаченным, повторной генерации нет);
   - смена модели и fallback с раздельными попытками в журнале.
2. **Тесты обработчика (`internal/handler/unified_ai_chat_error_test.go`)**:
   - сокрытие внутренних секретов и исключений провайдера;
   - локализация ошибок учёта на русском и казахском языках (429 и 403).
3. **Интеграционные тесты (`internal/service/unified_ai_accounting_integration_test.go`)**:
   - выполнение на отдельной тестовой схеме PostgreSQL;
   - проверка реальных счётчиков в таблицах `ai_usage_attempts` (статусы `settled`, `unknown`, суммы `charged_microcredits`), `organization_ai_budget_periods` (`used_microcredits`, `reserved_microcredits`) и записей в `unified_ai_messages`.
