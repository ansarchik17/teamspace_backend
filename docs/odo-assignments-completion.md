# Задача 6: выполнение поручения из Workspace

Реализован серверный путь выполнения текущим исполнителем. Источник истины — ЭДО. В задаче 9 к этому API подключена форма результата в разделе «Работа»; см. [проверки прав и поведения интерфейса](position-access.md#поручения-эдо-в-разделе-работа-задача-9).

## API для интерфейса Workspace

`POST /api/v1/kanban/documentolog/assignments/{task UUID}/complete`

Требуются обычная авторизованная пользовательская сессия и `Idempotency-Key: odo-command:<command_id>`. В URL используется локальный `task.id` из списка поручений, а не `source_assignment_id`.

```json
{
  "command_id": "22222222-2222-4222-8222-222222222222",
  "expected_revision": 4,
  "result_comment": "Ответ подготовлен и передан заказчику."
}
```

Все три поля обязательны. `command_id` — новый UUID для одного осознанного действия. `expected_revision` — `source_revision` карточки, целое от 1 до 9007199254740990. Результат обязателен, не должен состоять из пробелов, максимум 20000 символов Unicode. Поля идентичности, компании, исходного поручения или документа в публичном теле запрещены. Дубликаты JSON-ключей и лишние поля отвергаются.

Workspace проверяет активного сотрудника, активную компанию, модуль ЭДО, при управляемых правах `assignment.read`, одно из `document.read` / `document.read_department` / `document.read_all` и `assignment.complete`. Директор и суперадминистратор получают рабочий доступ через назначенную должность, без исключения по административной роли. Выполнить можно только своё поручение: права директора/admin не позволяют выполнить чужое. Необходима v1-проекция с подтверждённой компанией/issuer и настоящим Keycloak sub. Legacy-записи сначала проходят задачу 5.

Сервер сам извлекает `organization_id`, `source_assignment_id`, `source_document_id`, закреплённый `identity_issuer` и sub текущего пользователя. Пользовательский access token передаётся только настроенному серверу ЭДО по текущему запросу. URL не берётся из `source_url` карточки. Перенаправления запрещены; токен не сохраняется в БД, outbox или для фоновых повторов. Сервисный client_credentials из sender не используется вместо пользователя.

Успех HTTP 200:

```json
{
  "confirmed": true,
  "projection_pending": true,
  "task_id": "33333333-3333-4333-8333-333333333333",
  "receipt": {
    "command_id": "22222222-2222-4222-8222-222222222222",
    "organization_id": "11111111-1111-4111-8111-111111111111",
    "identity_issuer": "https://identity.example.test/realms/Workspace",
    "actor_sub": "executor-keycloak-sub",
    "assignment_id": "asg-example",
    "document_id": "doc-example",
    "expected_revision": 4,
    "revision": 5,
    "status": "completed",
    "event_id": "44444444-4444-4444-8444-444444444444",
    "completed_at": "2026-10-15T07:00:00Z",
    "outcome": "completed"
  }
}
```

`confirmed=true` означает commit команды в ЭДО. `projection_pending=true` требует перечитать список: Workspace не переписывает локальные status/revision по ответу команды. Новая revision приходит через существующий outbox → `/upsert` задачи 4. Успех не возвращается при timeout, ошибке авторизации, HTTP 409 или неполном/несовпадающем подтверждении ЭДО. Результат хранится в ЭДО; v1-снимок сохраняет прежние 22 поля и не получает неподдерживаемое поле `result_comment`.

## Повторы и ошибки

При timeout/обрыве/502/503 результат неизвестен: ЭДО могло успеть сделать commit. Повторять **тот же command_id, Idempotency-Key, expected_revision и result_comment**. Подтверждённая команда вернёт тот же event ID, revision и completed_at с `outcome=duplicate`. Это работает и после того, как проекция Workspace уже получила новую revision. Не генерировать новый UUID автоматически при сетевой ошибке и не менять результат внутри старой команды.

При `ODO_COMMAND_CONFLICT` (409) обновить список/проверить ЭДО: изменилась revision, исполнитель или статус, либо command ID использован для другого тела. Новый осознанный запрос формировать после проверки состояния. Другая команда к уже выполненному/закрытому/отменённому поручению не создаёт новый результат.

`ODO_REAUTH_REQUIRED` (401) — ЭДО отвергло пользовательскую сессию: восстановить вход/настройки доверия; повторять с прежними данными команды. 403 — права/доступ к документу, 404 — поручение недоступно пользователю. `ODO_UNAVAILABLE` (503) и `ODO_INVALID_RECEIPT` (502) не означают, что выполнение отменено. Ошибки Workspace локализованы на русский и казахский; сырые ошибки ЭДО/SQL и секреты не возвращаются.

## Проверки в ЭДО

Workspace вызывает отдельный `POST /api/v1/workspace/assignments/{source_assignment_id}/complete`. Старые маршруты `/api/v1/workflow/assignments/{id}/complete` и обычные workflow-переходы сохраняют совместимость и не заменяют этот протокол.

Тело содержит ровно 7 полей: command_id, organization_id, identity_issuer, actor_sub, document_id, expected_revision, result_comment. ID поручения берётся из пути. Заголовки — пользовательский Bearer token и `Idempotency-Key: odo-command:<UUID>`.

BFF сначала выполняет существующую проверку токена через auth-service и актуальный каталог Workspace. Для обоих путей выполнения требуются `assignment.read` и `assignment.complete`; `user.manage` не обходит эту проверку. Затем workflow повторно проверяет доступ текущего пользователя к документу через document-service. Делегирование и выполнение за другого человека для этой команды не включены.

Транзакция workflow блокирует поручение и command ID, сверяет сохранённую компанию/issuer/документ, текущую revision и исполнителя. Канонический sub пользователя и исполнителя разрешается через проверенные связи задачи 5; локальные ID пользователей ЭДО/ACL не переименовываются. Отсутствующая связь, другой исполнитель и неизвестная компания закрывают доступ. Авторство документа или административная роль не заменяют текущего исполнителя.

Допустимы только `assigned`/`open`/`in_progress` → `completed`. Незавершённое создание и staged backfill блокируют выполнение. Статус, result_comment, completed_at, новая revision, полный неизменяемый outbox-снимок, запись аудита и durable receipt сохраняются **в одной транзакции**. Ошибка любой записи откатывает всё. Для одного command ID изменять тело/поручение нельзя. Параллельные разные команды одной ожидаемой revision дают один commit; остальные получают 409.

Подтверждение повторной команды выдаётся только после повторной проверки текущих прав/доступа. Последующая смена исполнителя или потеря доступа не обходится старым receipt. Глобальный command ID защищён от повторного использования в другой компании/поручении.

После commit сохраняется существующая логика уведомлений и продолжения маршрута документа. Уведомление/публикация делается для нового выполнения, не для duplicate. Проверка завершённости всех поручений и переход документа повторяется при успешном retry: document-service — отдельный сервис, его переход не является частью транзакции workflow. Ошибка этого последующего шага не отменяет запись поручения, но возвращает ошибку подтверждения продолжения; клиент сохраняет ту же команду для безопасного повтора. Общий механизм восстановления применяется и внутри ЭДО. Основной event для Workspace доставляет durable outbox.

## Развёртывание

1. В workflow-БД ЭДО применить `000020_workspace_assignment_commands.sql`. В Workspace новой DB-миграции нет.
2. Обновить workflow-service и bff-gateway ЭДО совместно: добавлены protobuf-поля в существующем RPC `UpdateAssignmentStatus` и типизированное подтверждение в `Assignment`. Старые клиенты продолжают работать с прежними полями. Смешанная версия без receipt не выдаёт успешное подтверждение новой команды.
3. В workflow-service ЭДО включить `ODO_WORKSPACE_COMMANDS_ENABLED=true`. Закреплённый `ALEM_WORKSPACE_SYNC_IDENTITY_ISSUER` должен совпадать с namespace Keycloak sub в Workspace. Штатный sender задачи 4 должен быть настроен и включён для обновления проекции.
4. В Workspace задать `ODO_COMMANDS_ENABLED=true`, `ODO_COMMANDS_BASE_URL=<доверенный адрес bff-gateway ЭДО без /api/v1>`, `ODO_COMMANDS_TIMEOUT=10s`. Можно использовать внутренний адрес между серверами; для публичного транспорта нужен HTTPS. Поддерживается закреплённый префикс пути в base URL; URL карточки не используется. Неправильный включённый конфиг останавливает запуск API.
5. Сохранить существующее доверие пользовательским сессиям в auth-service ЭДО: для токенов обычного входа Workspace — `WORKSPACE_JWT_SECRET`, `WORKSPACE_JWT_ISSUER`, `WORKSPACE_JWT_AUDIENCE` и `WORKSPACE_API_BASE_URL`; для Keycloak — правильные issuer/JWKS/audiences/AZP. Значения секретов этой задачей не создаются и не меняются. Не заменять пользовательскую проверку общим сервисным токеном.

Оба новых флага по умолчанию выключены. В production compose ЭДО переменные workflow берутся из общего env_file; в локальном compose флаг передаётся явно. Форма результата Workspace подключена в задаче 9. После развёртывания отдельно проверить реальные токены, права и доставку новой revision (задача 8).

## Проверки реализации

PostgreSQL: параллельные одинаковые/разные команды, устойчивый receipt, CAS, смена исполнителя, межкорпоративные границы, alias, held/backfill, неизменяемый снимок и rollback при сбое аудита/outbox/receipt. HTTP → авторизация BFF → protobuf → workflow → PostgreSQL проверены вместе с повтором команды и запретами прав/идентичности. Workspace проверяет отказ от лишних полей, права, только свои поручения, неизменность проекции до события, повтор после обновления проекции, timeout/redirect и неверный receipt. Полный набор тестов ЭДО и затронутые пакеты Workspace запускаются на отдельном локальном PostgreSQL. Реальные production-токены и сеть между серверами этой задачей не проверялись.
