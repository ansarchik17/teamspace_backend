# Задача 2: сервисная авторизация поручений ЭДО

Реализовано в ветках `odo-integration` обоих бэкендов. Приёмник v1 из [контракта](odo-assignments-contract.md) реализован в задаче 3; актуальный порядок включения и миграция — в [документе приёмника](odo-assignments-receiver.md). Отправитель переключён на полный v1 с неизменяемым outbox в [задаче 4](odo-assignments-sender.md); ниже legacy payload сохранён как промежуточный формат этапа 2.

## Проверки входящего запроса Workspace

`POST /api/v1/internal/documentolog/assignments/upsert` больше не использует пользовательский middleware или перечень пользовательских ролей. Он принимает только подписанный Keycloak RS256 bearer token:

- issuer и подпись проверяются существующим доверенным JWKS/issuer Workspace;
- audience — отдельная, заданная `ODO_ASSIGNMENTS_AUDIENCE`;
- azp — ровно `ODO_ASSIGNMENTS_CLIENT_ID`;
- sub — ровно `ODO_ASSIGNMENTS_SERVICE_SUB`, то есть закреплённый service-account subject;
- обязательный exp, отсутствие истечения срока и запрет refresh-токенов;
- cookie, локальный HS256 JWT, чужой service account или пользователь с ролью admin не заменяют эту идентичность.

Отдельный verifier использует тот же доверенный JWKS cache, но не расширяет audiences/clients обычной пользовательской авторизации. Сервисный токен не создаёт пользователя в базе и не получает обычный user_id/roles context.

Настройки отсутствуют/некорректны или интеграция выключена → 403. Некорректный токен → 401. Компания не разрешена, issuer тела не совпадает с доверенным issuer, чужие участники/подразделение/доска или отключённый модуль → 403. Сырые токены и тела ответов стороннего сервиса в ошибки не включаются.

## Настройки Workspace backend

```dotenv
ODO_ASSIGNMENTS_ENABLED=true
ODO_ASSIGNMENTS_CLIENT_ID=odo-assignment-sync
ODO_ASSIGNMENTS_SERVICE_SUB=<реальный Keycloak sub сервисного аккаунта>
ODO_ASSIGNMENTS_AUDIENCE=workspace-odo-assignments
ODO_ASSIGNMENTS_COMPANIES=11111111-1111-4111-8111-111111111111:10,22222222-2222-4222-8222-222222222222:20
ODO_ASSIGNMENTS_SOURCE_ORIGIN=https://odo.example.test
```

UUID/10/20 здесь — примеры, не готовая production-конфигурация. Каждая пара разрешает сервису только указанную компанию и задаёт локального технического пользователя Workspace для существующей модели владельца доски/истории задач. Технические пользователи должны существовать, быть активными и принадлежать соответствующей компании. Не использовать реального сотрудника как технического автора без необходимости; роль платформенного admin техническому пользователю не требуется.

Wildcard, одинаковая компания дважды, пустая привязка, nil UUID, нулевой/отрицательный user ID отвергаются. JSON тела не может выбирать технического пользователя или расширять этот список.
Модуль `odo` у компании должен быть available и enabled, сама компания — active. Автор и исполнитель сопоставляются только по keycloak_id внутри этой компании; исполнитель должен быть активным. Новая доставка требует существующего автора без deleted_at; историческая поддержка удалённых авторов остаётся задачей миграции данных, а не поиска по email.

## Настройки Keycloak и ЭДО

Выделить confidential service client в том же доверенном realm: Service Accounts включены; пользовательские login/password flows для него не используются. В токен добавить audience `workspace-odo-assignments`, записать реальный service-account sub в настройки Workspace. Не добавлять сервисный client в список разрешённых браузерных azp и не передавать ему пользовательскую роль admin.

В `.env` workflow-service ЭДО:

```dotenv
ALEM_WORKSPACE_USER_SYNC_ENABLED=false
ALEM_WORKSPACE_SYNC_ENABLED=true
ALEM_WORKSPACE_API_URL=https://workspace.example.test
ALEM_WORKSPACE_KEYCLOAK_TOKEN_URL=https://identity.example.test/realms/Workspace/protocol/openid-connect/token
ALEM_WORKSPACE_CLIENT_ID=odo-assignment-sync
ALEM_WORKSPACE_CLIENT_SECRET=<секрет из защищённого хранилища>
ALEM_WORKSPACE_SYNC_IDENTITY_ISSUER=https://identity.example.test/realms/Workspace
ALEM_WORKSPACE_SYNC_ALLOWED_ORGANIZATIONS=11111111-1111-4111-8111-111111111111,22222222-2222-4222-8222-222222222222
ALEM_WORKSPACE_ASSIGNMENTS_BOARD_ID=
```

Примеры origin также не являются адресами production. Public issuer должен точно соответствовать iss токена и текущему issuer Workspace. API/token endpoints должны быть явно доверенными; production использует HTTPS либо контролируемую внутреннюю сеть.
При включённом воркере неполная конфигурация останавливает workflow-service с безопасным сообщением; при выключенном синке настройки не обязательны. HTTP redirect не получает client secret или bearer token: отправитель не следует redirect ни при получении токена, ни при доставке.

## Компания и источник данных

При создании/смене статуса ЭДО сохраняет `organization_id` из проверенного внутреннего access.Scope вместе с outbox-событием. Не использовать идентификатор компании из публичного JSON, компанию сервисного аккаунта, email автора или последний выбранный офис.
Проверки доступа к исходному документу остаются в workflow-service ЭДО перед записью события. Workspace доверяет только закреплённому сервису с явным набором компаний; Workspace не имеет базы документов ЭДО и не может доказать компанию произвольного document_id только по его строке. Поэтому внутренние gRPC-сервисы ЭДО и metadata scope должны оставаться недоступными внешним клиентам, как в существующей схеме развёртывания.
Отправитель проверяет company allowlist до обращения за токеном, добавляет настроенный identity_issuer и ожидает совпадающие organization_id/assignment_id в подтверждении Workspace.

Пример допустимого промежуточного payload (пока **без schema_version=1**):

```json
{
  "organization_id":"11111111-1111-4111-8111-111111111111",
  "identity_issuer":"https://identity.example.test/realms/Workspace",
  "source_system":"documentolog",
  "assignment_id":"asg-example-1",
  "document_id":"doc-example-1",
  "author_sub":"author-keycloak-sub",
  "assignee_sub":"executor-keycloak-sub",
  "title":"Подготовить ответ",
  "priority":"medium",
  "due_date":"2026-10-16",
  "status":"assigned"
}
```

Сервисные доски имеют immutable system_key `documentolog-assignments:<organization UUID>` и отделены от обычных пользовательских досок. Board ID legacy-запроса должен иметь этот ключ и владельца данной компании. С задачи 3 одинаковый assignment_id разных компаний создаёт независимые записи по составному ключу.

GET моих поручений требует активной компании, активного пользователя и включённого модуля ЭДО. Если права ЭДО управляются через должности, дополнительно требуется assignment.read; директор и admin допускаются в рамках своей компании. Запрос возвращает только записи текущего исполнителя из доски своей компании, даже если по ошибке ему добавили связь с чужой задачей.

## Совместимость и границы этого этапа

- Старый прямой вызов upsert пользовательским токеном выключен; переменная ALEM_WORKSPACE_USER_SYNC_ENABLED=true теперь сообщает о необходимости перейти на outbox, но не отправляет пользовательский токен.
- Старые outbox-записи без проверенной компании не отправляются. После ограниченных попыток они доступны для диагностики; backfill с доверенным сопоставлением — задача 5. Нельзя добавлять им компанию из произвольного текущего пользователя.
- Старые общие доски без компании не раскрываются через GET поручений и не принимают новые сервисные изменения. Их контролируемый перенос — задачи 3/5.
- Автоматическое сопоставление workspace:<id>, удалённых исторических авторов и отсутствующих Keycloak ID не выполняется; нужен каталог и контролируемая миграция.
- В задаче 3 реализованы revision-aware upsert и полный снимок всех полей. Обратная команда выполнения остаётся задачей 6; отправитель с immutable outbox-событиями v1 — задачей 4.
- Новая DB-миграция в этом этапе не нужна: компания хранится в существующем JSON outbox и company-specific system_key. Изменения модели проекции поручений остаются задачей 3.

## Проверки

Покрыты реальные RS256 JWT: правильный сервис, неверные issuer/aud/azp/sub, пользователь admin, истечение срока, отсутствие exp, refresh и HS256. Тест PostgreSQL проверяет создание двух разных досок, отсутствие чужих поручений, запрет чужих автора/исполнителя/подразделения/доски, inactive пользователя, disabled модуля и assignment.read. На стороне ЭДО проверены company allowlist, canonical sub, подтверждение другой компании/поручения и запрет redirect для токенов.
Production Keycloak client и секреты этим изменением не создавались. Для запуска нужен согласованный набор настроек на обоих серверах.
