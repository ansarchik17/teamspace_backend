# Диагностика загрузки списка чатов

`GET /api/v1/chats/unified` сохраняет прежнюю JSON-схему и параметры `limit` / `offset`.
Без `limit` по-прежнему возвращаются все чаты: вводить скрытый лимит нельзя без
подключения пагинации на фронтенде.

## Замер без доступа к серверным логам

После деплоя откройте DevTools → Network → `chats/unified` → Headers.
В ответе есть `Server-Timing`, например:

```text
personal;dur=12.50, groups;dur=8.00, channels;dur=3.00, pinned;dur=1.00, fetch;dur=13.00, app;dur=15.00
```

Все значения — миллисекунды:

- `personal`, `groups`, `channels`, `pinned`: получение и преобразование данных
  соответствующего репозитория, включая ожидание соединения из пула.
- `fetch`: время ожидания всех параллельных источников.
- `app`: всё выполнение сервиса, включая дополнительные закрепы, support-чат,
  подготовку ссылок и сортировку.

Это не чистое время SQL. Метрики источников выполняются параллельно и **не суммируются**.
В `app` не входят аутентификация, JSON-сериализация, сеть и обработка прокси.
Сопоставляйте `app` с Waiting for server response (TTFB), но не считайте разницу
исключительно сетевой задержкой. Stalled до отправки запроса также не входит в `app`.
Заголовок содержит только фиксированные имена этапов и длительности, без ID пользователей,
текста запросов и сообщений. Доступ остаётся за существующей авторизацией эндпоинта;
широкий `Timing-Allow-Origin` не добавляется.

## Изменения в запросах

Списки личных чатов и групп считают unread и mentions одной LATERAL-агрегацией
по видимым непрочитанным сообщениям вместо двух отдельных подсчётов. Упоминания
учитываются через уникальную пару `(message_id, user_id)`.
Сохранены границы вступления и очистки истории, удаления для всех / конкретного
пользователя и индивидуальные статусы прочтения. Отсутствие статуса означает unread.
Сохранённые `unread_count` не используются как источник истины, кэш не вводится.

Превью также ограничено датой вступления, включая single-view пути для support
и догрузки закреплений. Ошибки чтения строк списков возвращаются как ошибки,
а не успешный неполный результат.

Это сокращает повторную работу, но не гарантирует определённого ускорения на
продовой БД. Следующая оптимизация определяется замером: при большом времени
репозитория нужны EXPLAIN (ANALYZE, BUFFERS), реальные индексы, статистика и ожидания пула.

## Проверки

`TestUnifiedListBadgesAndHistoryIntegration` запускает реальные list / single-view
запросы для личных чатов и групп в отдельной PostgreSQL-схеме. Проверяет read,
delivered-only, отсутствующие статусы, mentions другого пользователя, удаления,
границы вступления и очистки, скрытые и покинутые чаты.

```powershell
$env:TEST_MESSENGER_DATABASE_URL = 'postgres://USER:PASSWORD@localhost:PORT/DISPOSABLE_DB?sslmode=disable'
go test ./internal/repository ./internal/handler -run TestUnified -count=1 -v
```

Используйте только одноразовую тестовую БД. Тест создаёт собственную уникальную
схему и удаляет её после выполнения. Без переменной DB-тест явно пропускается.
`TestUnifiedHandlerServerTiming` проверяет формат заголовка, неизменный ответ и ошибки.
