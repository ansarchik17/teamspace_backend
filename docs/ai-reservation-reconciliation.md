# Фоновая сверка зависших резервов

Задача 20. Репозиторий: ScheduleReconciliation, ClaimReconciliation, ApplyReconciliation. Фоновый исполнитель: AIReconciliationWorker.Run / RunOnce. Запуск подключён к cmd/api/main.go, включая отдельный AI-document worker-процесс, при включённой настройке.

## Что обрабатывается

Обнаруживаются активные резервы, для которых наступил reconcile_after либо истёк технический интервал StaleAfter от создания. Отсутствие reconcile_after не делает резерв невидимым. На каждую попытку создаётся одно долговечное задание. Уже существующие задания исключаются до ограничения размера пакета, чтобы не блокировать обнаружение следующих резервов.

Возраст резерва — повод проверить состояние, а не доказательство отсутствия расхода. Воркер никогда не повторяет генерацию, не оценивает реальные токены по тексту и не освобождает sent/unknown по TTL.

`manual` относится к сверке расхода, а не к активной генерации. Неопределённая попытка, уже переведённая в ручную сверку, исключается из счётчика выполняемых генераций. Её финансовый резерв остаётся активным и полностью учитывается во всех лимитах. Новый явный запрос допускается только через обычные проверки частоты, живых Redis-аренд, атомарной параллельности и доступных кредитов; старая операция повторно не запускается. Это изменение не подтверждает завершение работы на стороне провайдера и не списывает неизвестный расход как нулевой.

| Состояние / доказательство | Действие |
| --- | --- |
| reserved, известен отпечаток запроса, отправка ещё не отмечена | Атомарная проверка local_dispatch_guard задачи 18; освобождение только если вызов действительно не начался |
| Полный подтверждённый usage | Списание задачи 17 по исходным периодам и закреплённым коэффициентам, закрытие резерва |
| Явное подтверждение провайдера о неисполнении со ссылкой на доказательство | Освобождение через confirmed_not_executed задачи 18 |
| Провайдер ещё не закончил / временная ошибка чтения | Резерв удерживается, попытка unknown, операция needs_reconciliation; повтор после RetryDelay |
| Контракт чтения расхода недоступен / доказательство невалидно / исчерпаны попытки сверки | Задание manual, резерв остаётся active, charge не становится вымышленным нулём |
| Вызов уже завершён обычным обработчиком | Задание completed / already_final; существующий расход не меняется |

Если MarkSent успел выполниться между захватом задания и применением local_dispatch_guard, автоматическое освобождение отклоняется, задание откладывается. Исторические строки без отпечатка не считаются доказанно неотправленными. Перевод, блокировка и приостановка не препятствуют проведению уже возникшего обязательства.

## Несколько экземпляров и сбои

В `ai_usage_reconciliation_jobs` хранятся статус pending/processing/manual/completed, срок следующей проверки, lease_token, lease_until, число захватов и безопасный код последнего результата.

Захват выполняется короткой транзакцией с FOR UPDATE SKIP LOCKED. Каждый захват, включая восстановление после просрочки, получает новый случайный UUID аренды. Время аренды и повторов определяется PostgreSQL clock_timestamp(), поэтому часы разных экземпляров не влияют на владение заданием. Задания захватываются по одному непосредственно перед обработкой; пакет заранее не арендуется на время последовательных обращений к провайдеру.

Сетевое чтение usage происходит без открытой транзакции. При применении результата сохраняется порядок «исходная компания → исторический пользователь → бюджет → операция → попытка/резерв → задание». После ожидания этих блокировок повторно проверяются актуальные статус, маркер и непросроченность аренды. Старый процесс после повторного захвата получает ErrAIReconciliationLeaseLost и не меняет расход или резерв.

Проводка и подтверждение задания фиксируются **одной транзакцией**. Ошибка записи completed откатывает также списание или освобождение. Если процесс остановился до commit, аренда позже позволяет повторную сверку. Если commit состоялся, но ответ потерян, закрытое задание и финальный журнал не позволяют провести деньги повторно.

Изолированный savepoint позволяет отправить невалидное доказательство на ручную проверку без частичного изменения журнала и счётчиков. Внешнее успешное завершение одновременно со сверкой сериализуется теми же блокировками; поздний воркер не переписывает финальные данные. Sweep закрывает также отложенные/manual задания, если обычный обработчик уже завершил их резерв.

## Контракты провайдеров

`AIUsageLookup.LookupUsage` — исключительно чтение существующего результата. Реестр использует точные provider_id, endpoint_kind и закреплённую usage_adapter_version. Адаптер должен проверять принадлежность подтверждения исходному запросу, полноту usage, модель и правила нормализации задачи 03. HTTP 404/ошибка/пустой ответ не являются подтверждением неисполнения. Сам адаптер не вправе заявлять local_dispatch_guard.

В существующем `internal/alem/methods.go` реализованы генерация, embeddings, rerank и список моделей; подтверждённого контракта чтения usage по request ID нет. Поэтому основной процесс пока запускает пустой реестр удалённых lookup-адаптеров: неизвестные отправленные вызовы паркуются в manual, а доказанно неотправленные могут завершаться автоматически. Выдуманного endpoint, обращения к генерации для проверки и предположительного тарифа нет.

Добавление реального lookup-адаптера требует подтверждённого read-only контракта провайдера. Если provider_request_id отсутствует, поиск по AttemptID допускается только при отдельной гарантии адаптера. Иначе нужна ручная сверка.

Ручной оператор должен получить доказательства и использовать операторскую CLI `go run ./cmd/ai-accounting resolve` (без `--apply` — preview), которая вызывает существующий транзакционный Fail для подтверждённого расхода или неисполнения. Формат доказательства, привязка к исходной попытке и права на подключение описаны в [ai-production-readiness.md](ai-production-readiness.md). Публичного административного интерфейса и оформления неизвестного расхода за счёт платформы нет. Ни MaxClaims, ни возраст не разрешают автоматический waiver. После ручного завершения очередной Sweep закроет задание.

## Настройки и запуск

Применить `20261020100800_ai_reservation_reconciliation.sql` после миграций задач 05–07, 15 и 17–19. Откат непустой очереди останавливается, чтобы не уничтожить историю сверок. Настройки приведены в .env.example; реальный .env этой задачей не менялся.

| Переменная | По умолчанию |
| --- | --- |
| AI_RECONCILIATION_ENABLED | false |
| AI_RECONCILIATION_INTERVAL | 1m |
| AI_RECONCILIATION_STALE_AFTER | 15m |
| AI_RECONCILIATION_LEASE | 2m |
| AI_RECONCILIATION_LOOKUP_TIMEOUT | 30s |
| AI_RECONCILIATION_RETRY_DELAY | 5m |
| AI_RECONCILIATION_BATCH_SIZE | 25 |
| AI_RECONCILIATION_MAX_CLAIMS | 10 |

Это эксплуатационные параметры, не границы бюджетных периодов. Lease должен превышать LookupTimeout как минимум на время ограниченной 10-секундной операции БД. Размеры, длительности и число попыток проверяются при включении. Избыточные/аварийные повторные захваты тоже учитываются в MaxClaims и приводят к manual, сохраняя резерв.

Run делает первый проход сразу, затем работает по таймеру и штатно останавливается по контексту сервера. При остановке не снимает резервы и не обнуляет аренды: незавершённые задания подберёт другой экземпляр после lease_until. Сводные логи содержат количества и безопасные коды, без ответов провайдера, промптов и секретов.

## Проверки

На отдельной PostgreSQL выполнены:

- имитация падения процесса через брошенную аренду, повторный захват с новым маркером и отказ старому обработчику;
- 12 конкурентных захватов восьми заданий без повторного владения;
- два воркера одновременно: одно чтение usage и одна проводка;
- откат списания и освобождения при ошибке подтверждения задания, затем безопасный повтор;
- повтор после потерянного подтверждения без повторного списания/возврата;
- остановка воркера в ходе lookup с последующим восстановлением другим экземпляром;
- неизвестный результат, ошибка lookup, неполный usage и отсутствие доказательства неисполнения без освобождения;
- лимит повторов, задержка проверки, ручная очередь и закрытие обычным обработчиком;
- гонка локальной сверки с MarkSent, отсутствие starvation при обнаружении, применение и защищённый откат миграции;
- конфигурация, сборка cmd/api и регрессионный набор задач ИИ-учёта.

Использовались тестовые lookup-адаптеры. Реальный usage API провайдера, production-БД и развёртывание не проверялись. Фронтенд и публичные маршруты не менялись.
