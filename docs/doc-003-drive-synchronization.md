# DOC-003 — синхронизация редактора и Drive

Открытие выполняется через существующий `GET /api/v1/drive/onlyoffice/editor-link`
из DOC-001. Созданные через DOC-002 и загруженные в Drive документы используют
одинаковый путь сохранения. Фронтенд и API создания файлов не меняются.

## Открытие и сохранение

- Новая download-ссылка фиксирует версию, выбранную при открытии. DocumentServer
  не получит случайно более новую версию, если файл изменился до скачивания.
  Права и наличие файла проверяются повторно, история скачиваний сохраняется.
- `status=6` callback сохраняет снимок в новую версию того же файла Drive и
  сохраняет текущий ключ общей сессии. Следующие сохранения и новые участники
  могут продолжать работать с той же сессией. Кнопка force-save включена.
- `status=2` сохраняет финальный снимок и меняет ключ для следующего открытия.
- Запись объекта и истории не создаёт новый `file_id`, не переносит файл и не
  меняет владельца. Если документ перенесли или переименовали в Drive, сохранение
  обновляет его по ID на новом месте. Для аудита читаются актуальные имя и папка.
- Успешное сохранение создаёт событие `edited`, обновляет Recent и индекс Drive.
  Содержимое шаблона DOC-002 также становится доступным для будущих копий.

Для каждого callback вычисляется SHA-256 от status и URL снимка. В одной
транзакции записываются версия, текущий объект и квитанция
`(file_id, document_key, event_hash)`. Повтор точно того же callback возвращает
успех без повторной версии или аудита, в том числе после финального сохранения.
Разные URL считаются разными снимками. Сами подписанные URL в квитанциях не хранятся.
При конкурирующей доставке одинаковых callback лишний объект MinIO удаляется.

Если за время сохранения в Drive загрузили/восстановили другую версию, сессия
редактора устарела: возвращается `409` и `{"error":1,...}`. Внешняя версия остаётся
целой; редактор нужно открыть заново. Конкурирующие разные снимки используют
проверку ожидаемой версии: один может получить `409`; порядок событий сервер
не угадывает. При отзыве доступа, удалении файла или исчерпании квоты сохранение
не подтверждается успешным ответом.

Новые callback-токены привязаны к document key. Старые токены без ключа принимаются
в течение прежнего срока действия, но сервис всё равно проверяет активный ключ
файла. Callback session действует 24 часа; после этого нужно открыть документ заново.
При наличии `filetype` в callback несовпадение с расширением Drive возвращает
конфликт, чтобы не записать, например, DOCX под расширением DOC. Автоматическая
конвертация форматов не добавлена.

## Автоматические снимки открытой сессии

Автосохранение внутри редактора и сохранение в Drive — разные этапы. Для
периодической отправки снимков в Drive нужно включить `autoAssembly` на
DocumentServer. Подготовлен фрагмент `deploy/onlyoffice/auto-save.json`:

```json
{"services":{"CoAuthoring":{"autoAssembly":{"enable":true,"interval":"5m","step":"1m"}}}}
```

Добавить/объединить эти поля с существующим
`/etc/onlyoffice/documentserver/local.json`, сохранив JWT, базу данных и остальные
настройки, затем перезапустить DocumentServer. **Не заменять весь local.json этим
фрагментом.** Период — 5 минут, проверка планировщика — 1 минута. Фактическая
доставка также зависит от обработки и сети. Без настройки таймера работают
сохранение по кнопке и финальное сохранение после закрытия редакторов.

DOC-006 добавляет скрипт объединения autoAssembly/backoff и постоянные тома в overlay; см. `docs/doc-006-reliability.md`. Настройки
работающего DocumentServer этой задачей не менялись. Интервал на production
должен быть включён при развёртывании.

## Развёртывание и проверка

Сначала применить `20260929140000_office_save_receipts.sql`, затем обновить API.
Миграция не изменяет содержимое файлов. Down удаляет только квитанции; перед
откатом отключить force-save/таймер и завершить активные сессии, поскольку прежний
API не поддерживает повторные сохранения с постоянным ключом.

Тесты используют одноразовую PostgreSQL и локальные HTTP-серверы DocumentServer/S3:

```sh
go test ./...
TEST_MESSENGER_DATABASE_URL='<одноразовая БД>' go test ./internal/service -run 'TestOffice|TestDrive|TestDocument|TestOnlyOffice' -count=1 -timeout 120s
```

Проверяются force-save → force-save → финальное сохранение, повторная и
конкурентная доставка, версии и аудит, переименование/перенос, привязка исходного
скачивания к версии, внешнее обновление во время скачивания результата, очистка
объекта при конфликте, отзыв доступа, удаление, квоты для обычного/chunked ответа.

Ручная приёмка на настоящем DocumentServer: открыть DOCX/XLSX/PPTX, изменить,
дождаться таймера и скачать обновлённый файл из Drive без закрытия вкладки;
перенести/переименовать файл, снова сохранить, затем закрыть все редакторы и
проверить последнюю версию. Такой браузерный прогон пока не выполнен.

[autoAssembly](https://api.onlyoffice.com/docs/docs-api/get-started/configuration/server-config/),
[callback](https://api.onlyoffice.com/docs/docs-api/usage-api/callback-handler/).
