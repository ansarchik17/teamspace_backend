# CNT-003 — Оргструктура компании

## Дерево для интерфейса

`GET /api/v1/organizations/current/tree` (BearerAuth) возвращает оргструктуру
активной компании текущего пользователя. Читать могут все её сотрудники.

```json
{
  "organization_id": "<UUID>",
  "can_manage_structure": true,
  "items": [
    {
      "id": "<UUID>",
      "name": "Разработка",
      "unit_type": "department",
      "display_order": 0,
      "employee_count": 2,
      "subtree_employee_count": 2,
      "children": []
    }
  ],
  "total_units": 1,
  "active_employee_count": 3,
  "unassigned_employee_count": 1
}
```

- items — корневые подразделения; children — дочерние узлы, у листа всегда `[]`.
- Узел также содержит parent_unit_id, description и manager (id, full_name,
  position, avatar_url), если они доступны. Руководитель — только активный,
  неудалённый сотрудник этой же компании; внешние профили не раскрываются.
- employee_count — активные сотрудники непосредственно в узле;
  subtree_employee_count — в узле и всех его потомках. Руководитель не добавляется
  к числу сотрудников автоматически: учитывается только users.team_id.
- active_employee_count — все активные сотрудники компании. unassigned_employee_count
  включает сотрудников без активного подразделения своей компании.
- Соседние узлы сортируются по display_order, имени без учёта регистра, затем UUID.
- can_manage_structure соответствует существующим правам владельца компании/
  глобального администратора и нужен интерфейсу для показа управления.

Структура, профили руководителей и счётчики читаются из одного снимка PostgreSQL;
после чтения дерево строится за O(число подразделений). Нет отдельного запроса
на каждого руководителя/узел. Фото руководителей получают свежие подписанные ссылки
как в CNT-002. Архивные подразделения не возвращаются. Пустое дерево — items=[].
Без активной компании — 404. Существующий цикл или недоступный родитель — 409,
вместо молчаливой потери подразделений; старые данные автоматически не исправляются.

Для интерактивного интерфейса: раскрывать/сворачивать children локально, сохранять
состояние раскрытых узлов по id; при выборе узла запрашивать
`GET /api/v1/contacts?unit_id=<UUID>` для прямых сотрудников (CNT-001), при клике
на сотрудника — `/api/v1/contacts/{user_id}` (CNT-002). После мутации перечитать дерево.
Дерево возвращается целиком, ленивой загрузки и realtime-подписки в этой задаче нет.

## Создание и изменение подразделений

Используются существующие API:

- POST `/api/v1/organizations/current/units` — name, unit_type (по умолчанию team),
  parent_unit_id (пропущено/null — корень), description, manager_id, display_order.
- PATCH `/api/v1/organizations/current/units/{unit_id}` — переименование,
  изменение типа/описания/порядка/руководителя или перенос под parent_unit_id;
  clear_parent=true переносит в корень, clear_manager=true убирает руководителя.
- DELETE `/api/v1/organizations/current/units/{unit_id}` — архивирование пустого узла.
- PUT `/api/v1/organizations/current/users/{user_id}/assignment` — назначение
  сотрудника в unit_id, manager_id; null очищает соответствующее назначение.

Владельцу/глобальному администратору разрешено управление; обычному сотруднику —
403. Чужие ID не дают доступа. Нельзя одновременно передать parent_unit_id и
clear_parent либо manager_id и clear_manager (400); пустой unit_type при PATCH
также 400. Неизвестный/архивный ID при PATCH/DELETE — 404. Для архивации нужно убрать
всех неудалённых сотрудников (включая неактивных) и активные дочерние подразделения.
Имя до 255 символов, тип до 64, порядок >=0 при PATCH; создание сохраняет прежнюю
нормализацию отрицательного порядка в 0.

Исправлена проверка перемещения: перенос узла непосредственно под предка разрешён,
перенос под собственного потомка запрещён (409). Рекурсивная проверка ограничена
компанией и завершается даже при старом цикле.

## Развёртывание и проверки

Применить миграцию `20261001140000_organization_tree_guards.sql` после предыдущих.
Она добавляет триггеры teams/users, защищающие и legacy-записи: чужие/архивные
родители и назначения, самого себя и циклы; неактивные/чужие руководители;
архивирование непустого отдела. Изменения иерархии и назначения в отдел используют
общий advisory-lock по компании; перенос между компаниями блокирует обе компании
в фиксированном порядке. Перенос подразделения в другую компанию требует сначала
убрать его сотрудников/потомков. При переносе сотрудника очистить или сменить team_id.
Старые ошибочные данные не переписываются. Триггеры физического DELETE не добавлены;
штатные API используют архивирование. Новых настроек нет. Фронтенд и production
не менялись: это бэкенд для интерактивного дерева.
