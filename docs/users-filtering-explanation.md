# Объяснение по фильтрации сотрудников через API

Этот текст можно отправлять команде, у которой есть доступ только к API.

## Коротко

Сейчас в системе есть два разных API для работы с сотрудниками:

1. `GET /api/v1/users`
2. `GET /api/v1/users/hr`

Они предназначены для разных сценариев и используют разные поля для фильтрации.

Поэтому если один клиент работает через `/api/v1/users`, а другой через `/api/v1/users/hr`, результаты по одной и той же "организации" или "подразделению" могут отличаться. Это ожидаемое поведение, потому что сравнение идёт не по одинаковым полям.

## Как работает `GET /api/v1/users`

Этот endpoint принимает строковые фильтры:

- `q` или `search`
- `position_name`
- `department_name`
- `organization_name`

Важно: это не фильтрация по идентификаторам организационной структуры. То есть здесь нет логики вида:

- `state_body_id`
- `department_id`
- `division_id`

как основных фильтров списка сотрудников.

Практически это означает, что `/api/v1/users` ищет по текстовым значениям полей, а не по жёсткой организационной привязке.

## Как работает `GET /api/v1/users/hr`

Этот endpoint работает как HR-справочник сотрудников.

Для него используются другие фильтры:

- `q`
- `job_name`
- `sub_name`
- `name_go`
- `iin`
- `limit`
- `offset`
- `cursor`

Именно этот endpoint нужно использовать, если задача состоит в том, чтобы повторить поведение HR-справочника сотрудников, где фильтрация идёт по кадровым полям.

## В чём разница между ними

Основная разница такая:

- `/api/v1/users` работает с полями `position_name`, `department_name`, `organization_name`
- `/api/v1/users/hr` работает с полями `job_name`, `sub_name`, `name_go`

Это не просто разные названия параметров. Это разные наборы данных.

Поэтому нельзя считать, что:

- `organization_name` и `name_go` это одно и то же
- `department_name` и `sub_name` это одно и то же
- `position_name` и `job_name` это одно и то же

На практике значения могут быть похожими визуально, но для API это разные поля и разные источники данных.

## Почему у одного клиента есть результат, а у другого пусто

Если один клиент использует `/api/v1/users/hr`, а другой использует `/api/v1/users`, то ситуация:

- в одном интерфейсе сотрудник находится
- в другом по похожему значению организации не находится

сама по себе не является ошибкой.

Это означает только то, что запросы идут в разные endpoint'ы и фильтрация выполняется по разным полям.

## Что использовать внешней команде

Если нужно получить поведение, похожее на HR-справочник сотрудников, нужно использовать:

- `GET /api/v1/users/hr`
- `GET /api/v1/users/hr/filters/job_name`
- `GET /api/v1/users/hr/filters/sub_name`
- `GET /api/v1/users/hr/filters/name_go`

Если используется `GET /api/v1/users`, тогда нужно ориентироваться именно на его параметры:

- `q`
- `position_name`
- `department_name`
- `organization_name`

и не сравнивать его результат напрямую с `/api/v1/users/hr`.

## Рекомендуемое объяснение для другой команды

Корректно объяснять это так:

В системе есть два разных API для сотрудников. `GET /api/v1/users` и `GET /api/v1/users/hr` фильтруют данные по разным полям. Поэтому результаты между ними могут отличаться даже для визуально одинаковых названий организации или подразделения. Если нужно поведение HR-справочника, следует использовать `GET /api/v1/users/hr` и его HR-фильтры `job_name`, `sub_name`, `name_go`. Если используется `GET /api/v1/users`, тогда нужно работать с параметрами `position_name`, `department_name`, `organization_name` и не ожидать полного совпадения с HR API.
