# Учёт основного AlemAI-чата: задача 22

Подключён маршрут `POST /api/v1/ai/chats/:id/messages` через `AlemService`. Общий `AIPaidCallerService` установлен в `cmd/api/main.go`; отсутствие зависимости закрывает платный путь. Принадлежность чата проверяется до генерации. Пользователь берётся из аутентифицированного обработчика, компания — через серверный `UserRepository.GetByID`; активность и принадлежность повторно проверяются в транзакции резервирования. Компания из формы запроса не используется. Плательщик всегда пользователь, включая автозаголовок.

## Границы фактического вызова

Один экземпляр `alemPaidChat` обслуживает последовательные шаги одного сообщения: обычный ответ, цикл инструментов, переход с native tools на JSON, повтор подготовки пользовательского ответа и fallback модели. Каждый `CreateChatCompletion` отдельно резервирует кредиты, отправляет один HTTP-запрос и закрывает свою попытку. Прямых обращений к chat completion из этой цепочки нет. Чтение локальных источников инструментами не списывает токены; следующий вызов модели включает полученные результаты в свой вход.

Обычный ответ модели совместим с обоими режимами: проверенный JSON-конверт `answer`/`answer_mode`/`card_ids` принимается как с `action: answer`, так и без него. Поддерживается один полный Markdown-блок JSON, включая CRLF и блок без языковой метки. Команды чтения по-прежнему требуют явного `action: read`, строгой схемы и проверки прав; JSON из произвольного текста не извлекается. Ответ по личным данным без прочитанных источников отклоняется. Совместимый ответ не вызывает дополнительную платную генерацию. При отклонении протокола серверный журнал содержит безопасную категорию причины, номер раунда и признак остановки по лимиту выхода; содержимое ответа модели не записывается в эту диагностику.

Для учётного пути используется `CreateChatCompletionOnce`: транспортные повторы и переходы по HTTP-редиректам отключены без изменения общего клиента остальных подсистем. Ошибка/таймаут без подтверждения расхода оставляет резерв для сверки. Доступ к другой модели проверяется отдельным резервом по её коэффициентам; первый неуспешный вызов автоматически бесплатным не считается.

Если шлюз возвращает native-вызовы после перехода в JSON-режим, сервер принимает только корректные `read_user_data` с прежней строгой схемой аргументов и преобразует их в JSON-конверт. Права, каталог и бюджеты чтения проверяются прежним путём. Завершённый ответ (`finish_reason=stop`) с неверным протоколом допускает одну дополнительную генерацию для уточнения формата за всё пользовательское сообщение. Она проходит через тот же `alemPaidChat` с новым резервом и отдельным списанием. Неверный ответ не добавляется в контекст и не исполняется. Таймауты, ошибки провайдера, остановка по лимиту выхода, фильтр содержимого и неизвестная причина завершения не повторяются этим механизмом. При повторной ошибке журнал содержит только структурную диагностику; текст модели и аргументы инструментов туда не попадают.

Учётный ключ шага содержит серверный ID сохранённого пользовательского сообщения и последовательный номер. Автозаголовок использует тот же ID с отдельным суффиксом. Повторное выполнение уже зарегистрированного шага не отправляется провайдеру; отсутствие сохранённого текста ответа в платёжном журнале возвращает конфликт. Эта задача не вводит клиентский ключ идемпотентности HTTP-доставки: два отдельных POST, создавших разные сообщения, остаются разными действиями.

Расход фиксируется до продолжения цепочки и сохранения ответа в истории. Ошибка позднего инструмента, генерации, публикации или записи истории не откатывает предыдущие списания. Удаление истории не удаляет журнал. Автозаголовок получает тот же проверенный контекст плательщика, переживает завершение исходного HTTP-запроса и ограничен 45 секундами; его ошибка не отменяет расход основного ответа.

## Резерв и usage

В резерв входит весь фактически подготовленный JSON: история, системные инструкции, документы, описания инструментов и их результаты. Оценка входа — размер UTF-8 JSON плюс 512 токенов на сообщение и дополнительный запас 32768 на изображение. Выход ограничен переданным `max_tokens`; адаптер принимает 1–16384 и запрос не более 512 КиБ. Это оценка резерва, а не реальный расход или гарантия точной токенизации изображения. Превышение оценки учитывает существующий механизм overrun задачи 17.

Адаптер `nitec-chat-v1` сохраняет присутствие исходного `usage`, не превращая пропущенные поля в нули. `prompt_tokens` и `completion_tokens` обязательны для подтверждения; `total_tokens`, `prompt_tokens_details.cached_tokens` и `completion_tokens_details.reasoning_tokens` необязательны. Все значения декодируются в целые int64. Проверяются суммы, подмножества, отрицательные значения и переполнение калькулятором задачи 08. Фактическая модель берётся только из ответа; известная другая модель рассчитывается по закреплённой политике. Отсутствующая/неизвестная модель, отсутствующий/некорректный usage и нулевой отчёт требуют сверки с удержанием резерва. Оценка текста никогда не подменяет фактические токены.

При отказе резервирования из-за недостаточной ёмкости адаптер может уменьшить `max_tokens` до доступного бюджета за вычетом полной оценки входа. Новый JSON, отпечаток и резерв пересчитываются; выполняется не более трёх корректировок для ограничений компании, недели и пяти часов. Каждый вариант проходит обычную атомарную проверку квот. Это происходит только до принятого резерва и отправки провайдеру: платные запросы автоматически не повторяются. Если не помещается вход и хотя бы один выходной токен, отказ сохраняется. Внутренняя подсказка доступной ёмкости не передаётся клиенту.

Перед отказом проверяются все применимые окна под прежними транзакционными блокировками. Причина относится к окну с минимальным доступным остатком; при равенстве выбирается более поздняя граница восстановления. Положительный остаток, не покрывающий запрос, означает `RESERVATION_TOO_LARGE`, а не `EXHAUSTED`. Удержания, после снятия которых запрос поместится, означают `RESERVATION_PENDING`; фактический расход, достигший лимита, — соответствующий `EXHAUSTED`. Эти правила действуют и при чтении корпоративного статуса через `/ai/limits`.

Если вход и хотя бы один выходной токен не помещаются в доступный бюджет, отказ до отправки возвращает `429 AI_QUOTA_EXCEEDED` с причиной `RESERVATION_TOO_LARGE` и `retry_kind: requires_action`. `retry_at`, `recheck_at` и `resets_at` равны `null`; заголовка `Retry-After` нет. Процент остаётся реальным доступным остатком, а не искусственно обнуляется из-за размера конкретного запроса. Формат API не меняется; фронтенд уточняет сообщение по scope.

Если провайдер завершил ответ с `finish_reason: length`, сервер возвращает обычный завершённый результат с уведомлением об остановке. Проверенная часть JSON-конверта ответа может быть сохранена; незавершённые команды чтения не исполняются. Повторная генерация, публикация ответа и автозаголовок после остановки не запускаются. Если бюджет не позволяет продолжить уже начатую цепочку, сохраняются полученные данные и сообщение об остановке, а не ошибка «сообщение не отправлено». Расход фиксируется только по проверенному usage; оставшийся резерв освобождается штатным settlement. Вход пока оценивается консервативно по полному wire payload, точного API токенизации в текущем контракте нет.

## Ошибки и запуск

После вызова с неизвестным исходом (`unknown`) финансовый резерв сохраняется до подтверждения результата. Пока автоматическая сверка ещё не закончена, такая попытка защищает также допуск к параллельной работе: провайдер может продолжать работу после разрыва HTTP. Если сверка перевела попытку в `manual`, она больше не считается выполняемой генерацией и не блокирует новые явные запросы при достаточном остатке. Резерв `active`, сумма удержания, неопределённый расход и защита от повторного запуска старой операции сохраняются. Живые запросы продолжают ограничиваться общей Redis-арендой и атомарным допуском PostgreSQL; финансовые лимиты проверяются с учётом всех удержаний, включая `manual`. До перехода в `manual` отказ по неопределённой попытке возвращает `RESERVATION_PENDING` со scope `account`, без обещанного срока восстановления. Если запрос отклонён до первого вызова провайдера, удаляется только созданное им пользовательское сообщение с проверкой владельца; уже отправленные и оплаченные попытки остаются в истории. Отказ по частоте или параллельности после выполненного шага возвращает остановленный результат с фактическим usage вместо ложного сообщения «не отправлено».

Используется общий JSON-контракт ошибок ИИ: отказ по бюджету возвращает 429 с `AI_QUOTA_EXCEEDED`, недоступная учётная запись/компания — 403 с `AI_ACCESS_DISABLED`. Тексты есть на ru/kk; клиент получает безопасную причину и статус повторного доступа, суммы компании и ответы провайдера не передаются. Граница периода не обещает восстановление доступа при неразрешённых резервах.

Новых миграций и зависимостей нет; необходимы уже реализованные миграции задач 05–20, настроенный бюджет компании и личные квоты. Пустая настройка или нулевая квота закрывает доступ согласно задаче 02. Фронтенд использует существующий маршрут и обработку ошибок. Notebook, UnifiedAI, Smart Agent, embeddings/rerank и индексация здесь не подключаются.

## Проверки

Unit-тесты покрывают некорректный usage, нулевой отчёт, личность, отсутствие учёта, ошибки поздних вызовов, отсутствие скрытых HTTP-повторов и локализацию. Интеграционные тесты используют отдельную PostgreSQL-схему и локальный тестовый провайдер: история/контекст, native tools, JSON fallback, смена модели, отказ выбранной модели, публикация ответа, ошибка публикации и автозаголовок. Проверяется соответствие количества HTTP-отправок журналу, сохранение предыдущего расхода и независимость от удаления чата. Реальные платные запросы к NITEC тестами не выполняются.
