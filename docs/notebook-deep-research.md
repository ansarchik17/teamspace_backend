# Deep Research (Notebook): анализ документов и Студия

Блокнот (`/web/drive/notebook`) отвечает на вопросы по выбранным документам и готовит материалы Студии: отчёт, презентацию, таблицу, график, карточки, тест, диаграмму, сравнение и аналитические пресеты.

## Пайплайн ответа

```
POST /api/v1/notebook/chats/:id/ask
 ├─ проверка блокнота и Drive ACL (каждый запрос)
 ├─ текст источников из кеша (LRU 256 MB, TTL 30 мин; ключ: file id + content_hash + version + size + updated_at)
 ├─ сумма текстов ≤ 150 000 символов → single: модель читает документы целиком
 └─ иначе → deep (map-reduce):
      1. документы режутся на части по ~60 000 символов по границам строк
         (предпочтительно по метке PDF-страницы или пустой строке; перекрытие 3 строки)
      2. частей больше 8 → начало и конец каждого документа + самые релевантные вопросу части
      3. MAP: каждая часть отдельно (2 параллельно, openai/gpt-oss-120b) → выписки фактов со ссылками [S1:Lx-Ly] или «НЕТ»
      4. реальные строки, на которые сослались выписки (±2 строки), и первые 5 строк документа становятся фрагментами источника
      5. REDUCE: финальный ответ в нужном формате по фрагментам и выпискам; в режиме thinking — модель рассуждения и проверка ответа
 └─ постобработка: проверка цитат по реальным строкам, ссылки, mermaid, арифметика
```

Неподтверждённая ссылка (строки нет среди переданных фрагментов) по-прежнему заменяется на «(ссылка на фрагмент не подтверждена)».

### Лимиты и почему такие

| Параметр | Значение | Причина |
|---|---|---|
| Порог single/deep | 150 000 символов | прежний бюджет контекста |
| Размер части | 60 000 символов | ≈ 20k токенов, payload < 512 KB |
| Максимум частей | 8 | лимитер: 20 платных вызовов в минуту на пользователя |
| Параллельность MAP | 2 | лимитер: 2 одновременные генерации на пользователя |
| Фаза MAP | ≤ 120 с, оставляя 75 с на ответ | общий дедлайн запроса 210 с |
| Один MAP-вызов | 60 с, до 3 попыток при занятом слоте лимитера | |

Сбой сети или провайдера на одной части не роняет ответ: часть помечается непроанализированной, ответ получает `status: "partial"`. Отказ по кредитам, лимиту частоты или учёту прерывает операцию той же ошибкой, что и раньше (`AI_CREDIT_LIMIT`, `AI_CHAT_ACCESS` и т.д.).

### Выбор модели (KazLLM)

| Ситуация | Модель финального ответа |
|---|---|
| режим `thinking` | `Qwen/Qwen3.5-397B-A17B` → `moonshotai/Kimi-K2-Thinking` → `deepseek-ai/DeepSeek-V3.2` (первая доступная) |
| режим `fast`, казахский вопрос / `lang: "kz"` / документы на казахском, промт ≤ 48 000 символов, модель есть в `/v1/models` | **KazLLM** `astanahub/alemllm` |
| остальные случаи | `openai/gpt-oss-120b` |

- Казахский определяется по буквам, которых нет в русском алфавите (ә ғ қ ң ө ұ ү һ і): ≥ 2 в вопросе или ≥ 2% кириллицы в первых 20 000 символах документов.
- Анализ частей больших документов (MAP) всегда идёт на `gpt-oss-120b`: окно контекста AlemLLM не документировано, а части по 60 000 символов могут в него не поместиться.
- Ошибка провайдера KazLLM (контекст, 4xx/5xx, сеть) или пустой ответ повторяются один раз на `gpt-oss-120b` (`fallback: true`). Ошибки учёта и лимитов не повторяются.
- Модель задаётся `ALEM_KAZ_MODEL` (по умолчанию `astanahub/alemllm`); пустое значение отключает KazLLM. Тариф кредитов тот же, что у `gpt-oss-120b`.
- Модель отвечает на языке вопроса; цитаты остаются на языке документа.

### Память диалога

Для форматов `text` и `compare` в промпт добавляются последние 6 сообщений блокнота (до 1 500 символов каждое, до 6 000 всего) как недоверенный контекст. Это позволяет понимать уточнения вроде «а подробнее по второму пункту?». Факты по-прежнему берутся только из документов.

## Контракт API для фронтенда

### `GET /api/v1/notebook/studio/presets?lang=ru|kz`

Каталог карточек Студии (готовые промты). Бесплатный, без вызова модели.

```json
[
  {"id":"report","format":"report","title":"Отчёт","description":"…","prompt":"Составь аналитический отчёт…","min_sources":1},
  {"id":"cards","format":"cards","title":"Карточки","description":"…","prompt":"Создай {{count}} карточек…","min_sources":1,"count":{"default":10,"max":30}}
]
```

Идентификаторы: `report`, `presentation`, `table`, `chart`, `cards`, `test`, `mermaid`, `compare` (нужно ≥ 2 источника), `summary`, `risks`, `timeline`, `checklist`, `faq`.

### `POST /api/v1/notebook/chats/:id/ask`

Запрос (новые поля необязательны, старые клиенты работают как раньше):

```json
{
  "question": "Какой бюджет проекта?",
  "file_ids": ["…"],
  "mode": "fast | thinking",
  "format": "text",
  "preset": "cards",
  "count": 10,
  "focus": "только финансовые разделы",
  "lang": "ru",
  "persist": true,
  "operation_id": "…"
}
```

- `question` или `preset` обязателен. С `preset` вопрос и формат собираются на сервере; введённый пользователем `question` (или `focus`) становится темой пресета. `format` при этом игнорируется.
- `count` ограничивается максимумом пресета.
- `persist: true` — сервер сам сохраняет пару сообщений в историю. Вызывать `/sync` после этого не нужно. В истории пользовательское сообщение пресета — его название и тема.

Ответ:

```json
{
  "content": "…markdown со ссылками…",
  "format": "text",
  "model": "openai/gpt-oss-120b",
  "fallback": false,
  "sources": [ … ],
  "status": "answered",
  "suggestions": ["Составь чек-лист по ответу", "Сравни приоритеты"],
  "stats": {"mode": "deep", "chunks_total": 7, "chunks_analyzed": 7},
  "persisted": true
}
```

`status`:

| Значение | Что показать | Сохранять в «Результаты» Студии |
|---|---|---|
| `answered` | ответ | да |
| `partial` | ответ + пометка «часть документа не проанализирована» (подробности в `sources[].message`) | да |
| `not_found` | ответ «в документах нет сведений» | на усмотрение UI |
| `no_sources` | подсказка выбрать источники | **нет** |
| `unreadable` | список нечитаемых файлов | **нет** |

`suggestions` заменяют статичные кнопки под ответом: по клику отправить текст как новый `question`.

`stats.mode = "deep"` можно использовать для индикатора «Глубокий анализ: N частей». Deep-ответ занимает до ~3 минут; таймаут клиента должен оставаться ≥ 240 с. Для таких запросов лучше использовать фоновые задачи (см. «Асинхронный режим: задачи»).

## Асинхронный режим: задачи

Синхронный `/ask` держит HTTP-запрос до ~3 минут; прокси перед бэкендом может оборвать его раньше. Поэтому есть фоновый вариант того же запроса. Синхронный `/ask` не изменился.

```
POST   /api/v1/notebook/chats/:id/ask/jobs          тело = NotebookResearchRequest → 202 + задача
GET    /api/v1/notebook/chats/:id/ask/jobs/:job_id  статус, прогресс, результат
DELETE /api/v1/notebook/chats/:id/ask/jobs/:job_id  отмена → 200 + задача
WS     notebook.research.progress                   каждое изменение статуса и прогресса
```

### Создание

- До постановки в очередь выполняются те же проверки, что и в `/ask` до вызова модели: формат запроса и пресет, проверенный плательщик (пользователь, `domain.NewAIPaidUserCaller`), владение блокнотом, привязка источников и текущий Drive ACL. Ошибки возвращаются сразу и в том же формате, что у `/ask` (400, 403 `AI_CHAT_ACCESS`, 404 и т.д.).
- `operation_id` берётся из тела, `X-Operation-ID` или `Idempotency-Key` (до 128 символов), иначе равен `job_id`. Повторный POST с тем же `operation_id` возвращает ту же задачу с **200** и не запускает вторую платную генерацию.
- У пользователя одновременно не больше **одной** незавершённой задачи (`queued`/`running`): лимитер ИИ даёт 2 одновременные генерации, и deep-задача использует обе. Вторая задача → **409** `CONFLICT`, в `details.job_id` и `details.chat_id` — активная задача.
- Задача исполняется на том экземпляре, который её принял, под платным контекстом пользователя: `context.WithoutCancel(paidCtx)` сохраняет плательщика, компанию и язык запроса, но не отменяется вместе с HTTP-запросом. Сервисный плательщик не используется. Ключи учёта те же, что у `/ask`: `notebook:<operation_id>:map:…` и `notebook:<operation_id>:1…`.
- На экземпляре одновременно выполняются до 4 задач, остальные ждут в `queued`. Общий таймаут выполнения — 6 минут.

### Задача

```json
{
  "job_id": "…",
  "chat_id": "…",
  "operation_id": "…",
  "status": "running",
  "progress": {"stage": "analyzing", "chunks_done": 3, "chunks_total": 8},
  "result": null,
  "error": null,
  "created_at": "…", "updated_at": "…", "started_at": "…", "finished_at": null
}
```

| `status` | Смысл |
|---|---|
| `queued` | принята, ждёт свободного слота |
| `running` | выполняется |
| `done` | готово, `result` — тот же `NotebookResearchResponse`, что вернул бы `/ask` (включая его собственный `status`: `answered`, `partial`, …) |
| `failed` | ошибка, `error` — см. ниже |
| `cancelled` | отменена через DELETE |

`progress.stage`: `queued` → `reading` (чтение и извлечение текста) → `analyzing` (только deep: MAP по частям, `chunks_done` из `chunks_total` после каждой части) → `answering` (финальный ответ) → `verifying` (только `thinking`) → `done`. У `failed` и `cancelled` этап остаётся тем, на котором задача остановилась. `chunks_total` — число частей, отправленных на анализ (не больше 8); оно может быть меньше `result.stats.chunks_total`, где считаются все части документа.

`error` повторяет ответ, который вернул бы синхронный `/ask`:

```json
{"http_status": 429, "code": "AI_QUOTA_EXCEEDED", "message": "Лимит ИИ-кредитов исчерпан…", "body": { …тело ответа /ask… }}
```

Задача, прерванная перезапуском сервера, получает `code: "NOTEBOOK_JOB_INTERRUPTED"` (`http_status` 503). Повтор с тем же `operation_id` после этого невозможен: уже зарезервированные шаги учёта не переигрываются, нужен новый `operation_id`.

### Отмена

`DELETE` переводит незавершённую задачу в `cancelled` и останавливает вызовы модели (на другом экземпляре — при следующем продлении аренды или обновлении прогресса, не позже 30 с). Уже завершённые платные шаги остаются списанными, как при обрыве синхронного запроса. Завершённая задача возвращается без изменений (200), поэтому DELETE можно повторять.

### Изоляция и хранение

- Таблица `notebook_research_jobs` (миграция `20261023000100_notebook_research_jobs.sql`): каждая выборка ограничена `user_id` и `chat_id`. Чужая задача или задача другого блокнота → 404.
- Пока задача не завершена, исполнитель продлевает аренду (`lease_until`, 2 мин, каждые 30 с). Если процесс остановился, фоновая проверка раз в минуту переводит задачу с истёкшей арендой в `failed` (`NOTEBOOK_JOB_INTERRUPTED`). При штатной остановке сервера свои задачи помечаются так же сразу.
- Завершённые задачи (с результатом, где есть фрагменты документов) удаляются через 7 дней; при удалении блокнота или пользователя — сразу (`ON DELETE CASCADE`). Записи учёта кредитов при этом сохраняются.

### Событие WebSocket

Владельцу задачи (на все его устройства, подключённые к этому экземпляру) отправляется сообщение:

```json
{
  "type": "notebook.research.progress",
  "to": 7,
  "category": "notebook",
  "is_transient": true,
  "timestamp": 1792000000,
  "content": {
    "job_id": "…", "chat_id": "…", "operation_id": "…",
    "status": "running",
    "progress": {"stage": "analyzing", "chunks_done": 3, "chunks_total": 8},
    "error": null
  }
}
```

События идут при старте (`running`/`reading`), после каждой части MAP, на этапах `answering`/`verifying`, при завершении (`done`/`failed`) и отмене. Результата в событии нет: после `done` клиент забирает его через GET. WebSocket — ускоритель, а не гарантия доставки: при подключении к другому экземпляру или разрыве соединения события теряются, поэтому клиент обязан опрашивать GET.

## Учёт кредитов

См. [ai-notebook-accounting.md](ai-notebook-accounting.md). В deep-режиме каждая часть — отдельный платный вызов с ключом `notebook:<operation_id>:map:<source>:<chunk>:<step>`, затем финальный ответ `notebook:<operation_id>:1…`.
