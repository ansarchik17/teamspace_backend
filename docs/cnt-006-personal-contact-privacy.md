# CNT-006 — Приватность личных контактов

Карточка сотрудника разделяет рабочие и личные контакты. `personal_email` и
`personal_phone` — новые отдельные поля в employee_contacts. Существующие
`work_email`, `phone` (рабочий телефон CNT-002), email учётной записи и username
сохраняют прежнюю семантику. Эта задача не определяет автоматически, является ли
email входа личным, и не скрывает идентификаторы учётных записей в старых API.
Личные данные следует записывать именно в новые поля; автоматического переноса
старых контактов нет.

## Настройка через существующий API

`PATCH /api/v1/contacts/{own_user_id}`, BearerAuth, JSON до 4 KiB:

```json
{
  "personal_email": "employee@example.net",
  "personal_phone": "+77011234567",
  "personal_email_visibility": "private",
  "personal_phone_visibility": "managers"
}
```

Успех — 204. Обновлять данные и настройки может только сам активный сотрудник
в активной компании; изменение чужой карточки, в том числе администратором, — 403.
Для каждого личного поля есть независимая настройка:

| Значение | Кто видит данные в своей активной компании |
| --- | --- |
| `private` | Только сам сотрудник |
| `admins` | Сотрудник, владелец компании, роль `admin` |
| `managers` | Сотрудник, владелец, `admin`, роль `manager` |
| `company` | Все активные сотрудники компании, включая `guest` |

Значение по умолчанию — `admins` для обоих полей. `manager` здесь означает роль
учётной записи: назначение manager_id без этой роли дополнительных прав не даёт;
роль manager разрешает доступ ко всем контактам с настройкой managers в своей
компании. Даже администратор чужой компании не получает доступ. Настройка private
не даёт исключения владельцу/администратору.

Пропущенное поле или JSON null сохраняет прежнее значение; пустая строка очищает
контакт. Пустая/неизвестная настройка — 400, без частичного обновления. Email —
один корректный адрес без display name/CRLF, до 254 символов. Телефон нормализуется
в международный формат + и 7–15 цифр. Роли из тела запроса не принимаются.

## Чтение и защита

`GET /api/v1/contacts/{user_id}` возвращает разрешённые `personal_email` и
`personal_phone`. Скрытые и пустые поля отсутствуют в JSON. Только собственная
карточка дополнительно содержит `privacy` с двумя текущими настройками, даже
когда контакты ещё не заполнены. Права берутся из БД при каждом чтении в том же
согласованном снимке, что и карточка; неактивный вызывающий сотрудник — 403.

Маскирование выполняется в SQL до передачи результата сервису. Личные поля не
входят в поиск, total, списки Contacts, подчинённых, вложенных руководителей и
оргдерево. Остальные API не читают новые колонки. Быстрое действие «Отправить
email» использует рабочий email/email учётной записи и никогда personal_email,
даже когда он виден; скрытые данные не попадают в mailto. Для интерфейса отсутствующее
личное поле можно показать как «Не указано или недоступно» без раскрытия наличия.

CSV/Excel/LDAP CNT-005 синхронизируют рабочие контакты; не меняют личные поля и их
настройки. Импорт личных данных/настроек через новые колонки файла не поддерживается:
неизвестные колонки отклоняются штатной строгой валидацией.

## Развёртывание и проверки

Применить миграцию `20261001180000_contact_privacy.sql` после CNT-002.
Миграция добавляет отдельные колонки, defaults и CHECK ограничений, существующие
контакты не переписывает. Down удаляет личные контакты и настройки: перед откатом
нужно учитывать потерю этих данных. Новых переменных окружения нет.

Обновлён Swagger. Фронтенд/production не менялись. Для интерфейса подключить поля
и два селектора видимости к существующему PATCH, перечитывать карточку после
изменения. Проверены Go-тесты и регрессия Contacts CNT-001–006 на одноразовой
PostgreSQL: матрица ролей/владельца/гостей, независимость настроек, отсутствие
личных данных в поиске/списках/actions, отзыв роли/активности, изоляция компаний,
валидация/очистка, сохранение настроек при импорте и миграция Up/Down.
