# DRV-006 — версии файлов и восстановление из корзины

В Drive доступны история ревизий, скачивание конкретной версии, загрузка новой
версии того же формата и восстановление старой версии как новой текущей.
История открывается из панели сведений и окна предпросмотра. Отображаются номер,
автор, дата, размер и отметка текущей версии. Список разбит на страницы по 20.
Восстановление требует подтверждения в интерфейсе. Viewer может читать историю
и скачивать; editor/manager/владелец — добавлять и восстанавливать ревизии.
Права, включая наследование, заново проверяются на каждом запросе.

## API (префикс `/api/v1`)

- `GET /drive/files/{id}/versions?limit=20&offset=0` — массив ревизий, от новых
  к старым. Максимальный limit — 100. Внутренние ключи хранилища не возвращаются.
- `GET|HEAD /drive/files/{id}/versions/{version}/download` — байты ревизии,
  attachment, no-store, application/octet-stream.
- `POST /drive/files/{id}/versions` — multipart `file` и `expected_version`.
  Расширение должно совпадать с текущим файлом, лимит 500 МБ. Ответ 201 `{version}`.
- `POST /drive/files/{id}/versions/{version}/restore` — JSON
  `{"expected_version": 4}`. Ответ 200 `{version: 5}`.

При несовпадении текущей и ожидаемой версии — 409. Для отсутствующей ревизии
или удалённого файла — 404, недостаточных прав — 403. Восстановление не меняет
имя, расположение и ACL. Старая ревизия не удаляется; новая запись ссылается на
её неизменяемый объект. Запись текущего содержимого и новой ревизии атомарна.
Изменение сбрасывает устаревший content_hash и обновляет ключ OnlyOffice.
Сохранение OnlyOffice также проверяет ожидаемую версию, чтобы не перезаписать
результат параллельного восстановления. Изменения попадают в журнал активности
и запускают обновление поискового индекса.

Для ускорения истории и ограничения уникальности `(file_id, version)` добавлена
миграция `20260927120000_drive_version_history_index.sql`. Её нужно применить
штатным механизмом миграций при развёртывании.

## Корзина

`GET /drive/trash` возвращает только объекты, удалённые менее 30×24 часов назад,
с `deleted_at` и `expires_at`. Счётчик корзины использует тот же срок.
`POST /drive/trash/{file|folder}/{id}/restore` доступен владельцу объекта.
На границе 720 часов и после неё восстановление запрещено; срок проверяется
сервисом и повторно запросом БД. Родитель должен быть восстановлен первым.

Восстановление папки транзакционно возвращает потомков, удалённых именно
вместе с ней (общий deleted_at), включая файлы участников. Отдельно удалённые
ранее потомки остаются в корзине. Ревизии файлов сохраняются после удаления
и восстановления. Дата окончания восстановления показана в панели сведений.

30 дней — окно восстановления через Drive. Физическое удаление объектов
MinIO и записей БД по истечении срока эта задача не выполняет: копии файлов
и восстановленные ревизии могут ссылаться на один объект. Для освобождения
хранилища нужен отдельный сборщик с учётом всех ссылок.

## Проверка

`TestDriveVersionsIntegration`: наследуемые права, история и пагинация,
восстановление без потери истории, конкурентные изменения, откат транзакции
при ошибке записи ревизии, отзыв доступа, корзина и сохранность ревизий.

`TestDriveTrashRetentionIntegration`: 719/720/721 час, истечение папки,
согласованность списка и счётчика, запрет чужого восстановления, восстановление
дерева с чужими файлами, сохранение отдельно удалённых потомков.

`TestDriveVersionStorageIntegration`: настоящий S3-клиент с локальной HTTP-
фикстурой хранилища; загрузка новой версии, проверка точных байтов всех ревизий
после восстановления, отсутствие доступа после отзыва. Это не тест реального
сервера MinIO.

Эти тесты требуют `TEST_MESSENGER_DATABASE_URL`, создают изолированную схему
и удаляют её после выполнения. Фронтенд проверяется `npm run build`.
