# BRD-007: права и неизменяемая история задач

Права проектов наследуются от доски, к которой они относятся. Отдельных списков доступа для каждого проекта внутри одной доски нет. Один пользователь может быть Admin на одной доске и Viewer на другой.

## Матрица ролей

| Операция | Viewer | Editor | Admin / владелец |
|---|---|---|---|
| Читать проекты, задачи, комментарии, файлы, чеклисты, историю | Да | Да | Да |
| Создавать/изменять/удалять проекты, цели, спринты, задачи, колонки, метки | Нет | Да | Да |
| Перемещать задачи, менять статус, добавлять время, файлы и пункты чеклиста | Нет | Да | Да |
| Добавлять комментарии; изменять/удалять собственные комментарии | Нет | Да | Да |
| Изменять настройки/фон доски, удалять доску | Нет | Нет | Да |
| Добавлять/удалять участников, менять роли и командные роли | Нет | Нет | Да |
| Переписывать или удалять аудит | Нет | Нет | Нет |

Названия для API: `viewer`, `editor`, `admin` (регистр и пробелы нормализуются). Существующая роль `member` означает Viewer. Владелец (`boards.owner_id`, прежняя роль `owner`) сохраняет полномочия Admin; его нельзя удалить из участников или понизить через API. Присвоить `owner` через API нельзя. Неизвестные роли не дают права редактирования. При назначении участника роль указывается явно.

Авторство задачи, назначение исполнителем и авторство вложения не обходят текущую роль и членство. После удаления пользователя из доски доступ прекращается, даже если он создал задачу. Editor не может назначить себе Admin. Любой Admin может управлять ролями остальных участников, включая других администраторов; владелец защищён отдельно.

Ранее `member` мог менять статус/содержимое, а `editor` — добавлять участников. Эти разрешения отозваны. Тем, кому нужна работа с задачами, следует назначить `editor`; управление доступом требует `admin`.

## API для фронтенда

Используются существующие маршруты:

- `POST /api/v1/kanban/boards/{boardId}/members`: `{"members":[{"user_id":42,"role":"viewer"}]}`.
- `PUT /api/v1/kanban/boards/{boardId}/members/{userId}/role`: `{"role":"editor"}`.
- `DELETE /api/v1/kanban/boards/{boardId}/members/{userId}`.
- `GET /api/v1/kanban/tasks/{taskId}/history`: массив записей, новые первыми; при отсутствии записей `[]`.

Ошибки: 403 при недостаточной роли, 400 при неподдерживаемой роли. API чтения истории доступен всем текущим участникам активной доски, включая Viewer. Он работает и после удаления задачи, в том числе физического. После удаления самой доски REST-доступ закрыт, записи сохраняются в PostgreSQL.

WS `kanban_task_moved` от клиента требует Editor/Admin, как REST-перемещение. Viewer получает события доски, но не может отправлять уведомления о перемещении от своего имени. Callback Documentolog тоже проверяет роль: изменение существующего поручения требует Editor/Admin; создание с автоматическим добавлением исполнителя — Admin на системной доске. Глобальная роль пользователя не заменяет членство в конкретной доске.

## Гарантии аудита

Используется существующая таблица `task_history` и совместимый формат `id`, `task_id`, `user_id`, `action`, `field_name`, `old_value`, `new_value`, `metadata`, `created_at`.

- Создание задачи сохраняет начальное состояние. Изменения полей/назначений, перемещение и удаление сохраняют автора и старые/новые значения.
- Для комментариев, чеклистов, вложений и меток `old_value`/`new_value` содержат JSON-снимки. Действия: `comment_added/updated/deleted`, `checklist_created/updated/deleted`, `attachment_created/deleted`, `label_added/removed`. Учёт времени записывает `worklog_added`.
- Снятие проекта/цели/спринта при их удалении и удаление задач вместе с доской также попадают в историю. Удаление метки записывает её снятие со всех связанных задач.
- Каждая операция репозитория сохраняется в одной транзакции с её записью истории. Если вставка в журнал не удалась, изменение этой операции откатывается. Составной HTTP-запрос с несколькими операциями (например, изменение карточки и загрузка нескольких файлов) не является одной общей транзакцией; каждая успешная операция имеет свой аудит.
- При конкурентном редактировании карточки предыдущие значения считываются под блокировкой строки. История не использует устаревшее значение из предварительного чтения сервисом.
- PostgreSQL запрещает UPDATE, DELETE и TRUNCATE таблицы истории триггерами. Вставка фиксирует время БД и ID исходной доски. Каскадные связи с задачей/пользователем сняты: удаление сущностей не уничтожает записи. ID автора сохраняется; отображаемое имя берётся из текущей записи пользователя и может измениться.

Граница защиты: это append-only журнал приложения с ограничениями PostgreSQL, а не внешнее WORM-хранилище. Владелец таблицы/суперпользователь БД способен удалить или отключить триггеры; production API следует запускать под отдельной ролью без DDL/владения таблицами. Прямое изменение рабочих таблиц администратором БД вне методов приложения не создаёт аудит автоматически. Файлы хранятся отдельно; аудит сохраняет метаданные, а не копию бинарного содержимого.

## Развёртывание и проверки

До запуска новой версии применить `20260925000300_reconcile_kanban_audit.sql` штатным мигратором. Миграция дополняет и сохраняет существующую историю; исходный `board_id` заполняется из задач. CHECK ролей добавляется NOT VALID, чтобы старые неизвестные значения не блокировали выкладку; новые записи и обновления должны использовать разрешённые роли. Проверить старые роли перед последующим VALIDATE CONSTRAINT.

После мержа обнаружен конфликт версии `20260924000500` между аудитом и синхронизацией сообщений. Аудит перенесён на `20260925000100` и допускает повторное применение; `20260925000200_reconcile_message_sync_tracking.sql` восстанавливает объекты синхронизации сообщений, если прежняя версия была записана за аудитом. Обе новые миграции имеют пустой Down: откат не снимает защиту истории и не удаляет объекты, которые могли существовать до исправления. Запустить штатный мигратор до конца, не редактируя версии вручную.

Интеграционные тесты с PostgreSQL проверяют роли, запрет повышения прав, отзыв доступа у автора, совместимость member, изменение проектов, снимки содержимого, конкурентные изменения, запрет изменения/очистки аудита, откат при недоступном журнале и сохранение истории после удаления задачи/пользователя. Фронтенд не изменяется.

После синхронизации с main от 25.09.2026 сохранена миграция аудита `20260925000050` и сделана идемпотентной. Ветка ранее использовала `20260925000100` для аудита, а main — для AI-документов. Поэтому `20260925000300` повторно согласует аудит, а `20260925000400` — AI-таблицы. При уже применённых более поздних версиях требуется контролируемое применение пропущенных миграций (Goose WithAllowMissing) после резервного копирования; менять журнал версий вручную не нужно.
