# Meet в Workspace

Реализованы `/web/meet` и `/web/meet/:meetingId`: список активных и запланированных
встреч, создание, планирование с приглашениями по email, история со стенограммой,
подключение, камера/микрофон, демонстрация экрана и допуск из комнаты ожидания.
Интерфейс использует дизайн Workspace. Код интерфейса QMeet не переносится.

## Архитектура и авторизация

```
Workspace UI → /api/v1/meet/* → Workspace backend → QMeet /api/app/v1/*
Workspace UI → LiveKit QMeet (видео/аудио, токен выдаёт QMeet)
```

Workspace сначала проверяет свою сессию и tenant host обычными middleware.
Backend загружает текущий профиль и подписывает HS256 assertion с `sub = user.id`,
`iss`, `aud = qmeet-workspace`, `iat`, `exp`, email и именем. Срок жизни — 30 секунд.
QMeet проверяет подпись, issuer, audience и срок, затем находит аккаунт по
`(issuer, subject)` в новой таблице `workspace_identities`. ID остаётся стабильным
при изменении email. Отключённый аккаунт не активируется повторным входом.

Секрет и assertion доступны только backend-сервисам. Прокси не передаёт в QMeet
Workspace Bearer token или браузерные cookies; ответы не устанавливают cookies
QMeet в Workspace. Ошибка авторизации QMeet не завершает сессию Workspace.
Маршруты прокси ограничены операциями встреч, календаря и одноразовой привязки.
Внутренний API агента, service accounts и остальные разделы QMeet не открываются.

## Гости по ссылке

Та же ссылка `/web/meet/<UUID>` без сессии Workspace открывает отдельную страницу
с именем гостя. Она не перенаправляет на SSO и не открывает остальные разделы
Workspace. Авторизованные сотрудники продолжают использовать обычный Meet.

Публичный API `/api/v1/meet-guest/<UUID>/*` поддерживает только гостевую сессию,
статус собственного запроса и подключение. Backend использует существующие
QMeet `/auth/guest`, `/calls/<UUID>/join-requests` и `/calls/<UUID>/join`.
Участник создаётся с `is_guest=true`; сначала организатор допускает его через
обычный зал ожидания. До допуска LiveKit-токен не выдаётся. Пароль, email и
аккаунт Workspace гостю не нужны, список встреч и административные API закрыты.

Сессия хранится в подписанной HttpOnly cookie на 4 часа, с SameSite=Strict,
Secure на HTTPS и путём только этой встречи. Она не заменяет авторизацию
Workspace. Переданные браузером Bearer-токены, cookies QMeet, имя роли и ID
участника не пересылаются. Создание ограничено 5 запросами в минуту на IP;
проверка статуса — 120 запросами. Обновление страницы продолжает ожидание того же
гостя; выход очищает cookie и отзывает QMeet-сессию. Даже при сетевой ошибке
выхода клиент не начинает повторное подключение сам.

Новых переменных окружения и изменений QMeet не требуется: используются
существующие QMEET_* и уже включённый для интеграции APP_DEMO_ENABLED в QMeet.
Для публикации этого изменения обновить frontend и backend Workspace.

## Связь с существующими аккаунтами email/password

- Если email ещё отсутствует в QMeet, создаётся аккаунт с недоступным случайным
  паролем и стабильная связь с Workspace. Пользователь повторно не входит.
- Если email уже существует, QMeet возвращает `meet_account_link_required`.
  В Workspace появляется форма: пользователь один раз подтверждает email/password
  существующего аккаунта QMeet. Пароль проверяется QMeet и не сохраняется Workspace.
- Привязка сохраняет QMeet user ID, историю, приглашения и права на встречи.
  Один аккаунт QMeet нельзя связать с двумя разными Workspace identities.
- Простое совпадение email не считается доказательством владения аккаунтом.
  Старые local password и Keycloak входы QMeet продолжают работать.
- Если у пользователя разные email в двух проектах, привязку нужно выполнить
  через `POST /api/v1/meet/auth/workspace/link` до первого автоматического создания
  нового аккаунта. Перепривязка уже созданной identity в первом этапе не предусмотрена.

Привязка защищена ограничением пяти попыток в минуту на Workspace identity.
Секрет следует передавать по HTTPS или по доверенной внутренней сети.

## Подключение

1. Развернуть изменения **обоих backend**, frontend Workspace и серверный API proxy
   frontend QMeet (его allowlist теперь пропускает `X-Workspace-Assertion`).
2. Создать один случайный секрет, например `openssl rand -hex 32`.
3. В backend Workspace настроить:

   ```dotenv
   QMEET_API_URL=https://92-38-49-156.sslip.io
   QMEET_WORKSPACE_SECRET=<один случайный секрет для двух backend>
   QMEET_WORKSPACE_ISSUER=workspace
   QMEET_REQUEST_TIMEOUT=45s
   ```

   URL задаётся без `/api/app/v1`. При прямом доступе к QMeet backend можно
   использовать внутренний origin; тогда frontend proxy QMeet не участвует.
4. В QMeet `.env` задать:

   ```dotenv
   QMEET_WORKSPACE_SECRET=<тот же секрет>
   QMEET_WORKSPACE_ISSUER=workspace
   APP_DEMO_ENABLED=true
   ```

   `APP_DEMO_ENABLED` — существующий переключатель QMeet, открывающий API встреч.
   Таблица связей создаётся при инициализации существующей SQLite базы.
5. Перезапустить изменённые сервисы. В обоих Compose `.env` уже передаётся backend.
6. `livekit_url`, возвращаемый QMeet, должен быть доступен браузеру по `wss://`.
   LiveKit credentials Workspace не используются для встреч QMeet.

Без URL или достаточно длинного секрета раздел показывает состояние
«Meet ещё не подключён», без вымышленных встреч. Issuer — постоянное имя инсталляции;
изменять его без миграции таблицы связей нельзя.

## Проверка после развёртывания

- Войти в Workspace и открыть Meet. Новый пользователь проходит без второго логина.
- Для старого QMeet аккаунта подтвердить пароль, убедиться, что появилась его история.
- Создать встречу, скопировать `/web/meet/<UUID>` и открыть другим пользователем.
- Второй пользователь ждёт допуска; организатор допускает его. Проверить звук,
  камеру, демонстрацию экрана, повторное подключение и выход.
- Открыть ссылку в приватном окне без аккаунта Workspace. Ввести имя, проверить
  ожидание и обновление страницы, допуск/отклонение организатором и выход.
- Запланировать встречу с email участника и проверить её видимость обоим.
- Проверить новую сессию Workspace: связь сохраняется, чужие встречи не появляются.

## Границы первого этапа

Кнопка «Свернуть в окно» и переход в другой раздел Workspace используют одно
системное окно Document Picture-in-Picture: оно сохраняется при дальнейшей
навигации, смене вкладки и сворачивании браузера. Стили встречи встроены в это
окно и не требуют повторной загрузки CSS приложения. Если API недоступен или
браузер отклонил открытие, используется перемещаемое окно внутри Workspace
с пояснением ограничения. Автоматическое открытие при уходе с полноэкранной
встречи на другую вкладку зависит от поддержки и разрешений браузера.
Закрытие системного окна или «Развернуть встречу» возвращает большую встречу,
а выход из встречи освобождает устройства.
Перезагрузка или закрытие исходной вкладки завершает соединение. Пока другая
встреча Meet или звонок Workspace активны, второй звонок заблокирован.
Запись, AI-отчёты, опросы, breakout rooms и общий календарь Workspace
не перенесены. Планирование Meet работает в календаре QMeet; прежний календарь
Workspace и его ссылки остаются самостоятельной интеграцией. Создание новой
встречи в QMeet не означает её автоматическое создание в календаре Workspace.
