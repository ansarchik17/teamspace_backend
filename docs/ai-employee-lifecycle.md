# Жизненный цикл сотрудника и ИИ-квоты

Задача 15. Реализовано миграцией `20261020100400_ai_employee_lifecycle.sql` поверх миграций задач 05–07. Изменений HTTP-контракта нет.

| Событие | Назначенная квота | Расход, периоды и резервы |
| --- | --- | --- |
| Добавление в компанию | Не создаётся автоматически; до явного назначения доступ должен быть закрыт | Новых периодов не возникает |
| Перевод, выход из компании | Q/H исходной компании становятся NULL; строка и revision сохраняются. В новой компании автоматического назначения нет | Недельный расход и операции остаются у исходной компании; пятичасовое окно общее для user_id |
| Блокировка / разблокировка | Q/H и revision не меняются | Расход и активные резервы сохраняются |
| Увольнение (soft delete) | Q/H становятся NULL; revision увеличивается при изменении | История и резервы сохраняются |
| Восстановление / возвращение | Автоматического восстановления Q/H нет; требуется явное назначение с актуальной revision | Повторно используются существующие окна и расход; новый бесплатный лимит не появляется |

Правила работают триггером на изменениях `users.organization_id`, `deleted_at`, `is_active`, включая существующие репозитории и синхронизацию пользователей. Отдельного публичного API восстановления эта задача не добавляет. Повторное сохранение тех же значений не меняет квоту или её версию. Блокировка не запрещает администратору корректировать назначенную квоту.

Изменение сотрудника и освобождение назначения выполняются в одной транзакции. После блокировки существующий механизм открытия периодов отказывает неактивному пользователю. Административная блокировка также сохраняется при попытке синхронизации `is_active=true` существующим триггером блокировок.

Освобождается только назначение: использованные кредиты и активные резервы продолжают занимать бюджет исходной компании по формуле `max(Q, S + R)`. Удаление квоты, смена якоря, обнуление счётчиков и закрытие резервов не выполняются. Завершение уже принятой операции использует исходные идентификаторы компании и периодов из журнала.

Для конкуренции изменения членства и открытия периодов используют порядок «пользователь → бюджет». При переводе оба бюджета блокируются в порядке UUID. Административное изменение квоты использует «компания → авторизация → пользователь → бюджет», как существующая операция блокировки сотрудника. При гонке перевода и назначения квота либо назначается до перевода и освобождается им, либо назначение отклоняется из-за отсутствия сотрудника в компании.

Пример: сотрудник использовал 80 и имеет резерв 20 при Q=600, H=100. После перевода исходная компания продолжает учитывать 100, а назначение 600 освобождается. Новая компания должна явно назначить Q/H; пятичасовые 80 и резерв 20 сохраняются. Возврат или увольнение с восстановлением не меняет эти значения.

Проверки на отдельной PostgreSQL: добавление без квоты; блокировка и синхронизация; перевод A→B→A; повторное увольнение/восстановление; сохранение недельного расхода, глобального пятичасового окна, источника операции и активного резерва; конкурентные блокировка/назначение и перевод/назначение; откат миграции без удаления истории.

Ограничение этапа: проверка доступности непосредственно перед платным вызовом провайдера и полное проведение резервов относятся к последующим задачам. Эта задача сохраняет данные и сериализацию, необходимые для этих проверок; режим административного API остаётся `observe`.
