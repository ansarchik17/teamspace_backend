# Задача 5: контролируемый перенос исторических поручений

Реализован отдельный операторский CLI в ЭДО: `cmd/odo-assignments-backfill`. Фронтенд не меняется. Production-перенос не запускается автоматически при старте сервисов или применении миграций.

## Схема работы

1. `plan` читает четыре базы, проверяет компанию документа, каталог Workspace, пользователей, подразделения и старую проекцию. Записи не изменяются. Результат — JSON с состояниями `ready`/`blocked`, причинами и хешем всего плана.
2. Оператор проверяет JSON и явные сопоставления. `apply` принимает сохранённый план и его точный хеш. Изменённые после планирования исходные данные блокируются.
3. Транзакция в workflow закрепляет проверенные метаданные, сохраняет связи каталогов и создаёт один новый неизменяемый снимок. Revision становится `max(source revision, observed Workspace revision)+1`. При повторе того же плана revision/event ID/тело остаются прежними.
4. Снимок и последующие обычные события этого поручения удерживаются в `held_backfill`. Предыдущие неотправленные события получают `superseded`, их тела не переписываются. Старые lease отзываются.
5. CLI отправляет снимок в защищённый `POST /api/v1/internal/documentolog/assignments/backfill`. Workspace атомарно сохраняет проекцию, обычный receipt и аудит операции.
6. После проверки HTTP-подтверждения **и реальной записи receipt в БД Workspace** CLI переводит удержанные события в `pending`. Обычный воркер получает duplicate для уже принятого снимка и обновляет штатную таблицу соответствий. CLI не подделывает `synced`.

Сбой между этими шагами оставляет `staged`. Повторяется **тот же сохранённый план**, а не создаётся новая операция. Уже завершённые элементы возвращают `already_released`. Неподтверждённый receipt, HTTP 409, недоступность сервиса и ошибки отдельного элемента не выпускают его очередь. Отчёт сохраняется, CLI завершается ненулевым кодом при `blocked`/`staged`.

## Установка и доступ

Сначала применить миграции:

- Workspace: `20261014000400_odo_assignment_backfill_audit.sql` после миграции v1 из задачи 3.
- ЭДО workflow: `000019_workspace_assignment_backfill.sql` после миграции снимков из задачи 4.

Новые таблицы содержат проверенные связи пользователей/подразделений, журнал staged/released в ЭДО и аудит переносов в Workspace. Старые задания и события миграции не переименовывают и не исправляют автоматически.

На Workspace временно включить `ODO_ASSIGNMENTS_BACKFILL_ENABLED=true` (по умолчанию false). Сохраняются все проверки service account из задачи 2: подпись JWT, issuer, audience, azp, subject и разрешённые компании. Обычный пользовательский токен не предоставляет доступ к этому endpoint. После завершения операторского переноса флаг отключить; штатный `/upsert` продолжит работать.

CLI запускается из репозитория ЭДО. Для `plan` нужны:

- `WORKFLOW_DATABASE_URL`: workflow ЭДО, чтение на этапе plan и запись только для apply.
- `DOCUMENT_DATABASE_URL`: чтение компании/состояния документа и ACL.
- `AUTH_DATABASE_URL`: чтение локальных ID, компаний и активности пользователей ЭДО.
- `WORKSPACE_DATABASE_URL`: **только чтение** организаций, модулей, пользователей, подразделений, проекций и receipt. Использовать отдельную read-only роль, а не учётные данные приложения Workspace.
- `ALEM_WORKSPACE_SYNC_IDENTITY_ISSUER`: точный HTTPS issuer Keycloak.
- `ALEM_WORKSPACE_SYNC_ALLOWED_ORGANIZATIONS`: явный список UUID компаний через запятую.
- `ALEM_WORKSPACE_ASSIGNMENTS_TIMEZONE` / `ALEM_WORKSPACE_ASSIGNMENTS_TIMEZONES`, `DOCUMENTOLOG_PUBLIC_URL`: настройки из задачи 4 для старых записей без закреплённых метаданных.

Подключения к document/auth/Workspace и все подключения в режиме plan получают `default_transaction_read_only=on`. Не выдавать дополнительные права на запись этим ролям. DSN и секреты передаются окружением, не аргументами команд.

Для `apply` дополнительно нужны рабочие настройки sender из задачи 4: `ALEM_WORKSPACE_SYNC_ENABLED=true`, `ALEM_WORKSPACE_API_URL`, `ALEM_WORKSPACE_KEYCLOAK_TOKEN_URL`, `ALEM_WORKSPACE_CLIENT_ID`, `ALEM_WORKSPACE_CLIENT_SECRET`. К БД Workspace CLI ничего не записывает: запись выполняет сервисный endpoint после проверок.

## Пример плана и сопоставлений

`bindings.json` — проверенные оператором связи; `evidence` содержит ссылку на согласованный экспорт/заявку. Пример с условными значениями:

```json
{
  "users": [
    {"organization_id":"11111111-1111-4111-8111-111111111111","source_id":"usr_old_author","subject":"real-keycloak-author-sub","evidence":"reviewed directory export ODO-005"},
    {"organization_id":"11111111-1111-4111-8111-111111111111","source_id":"usr_old_executor","subject":"real-keycloak-executor-sub","evidence":"reviewed directory export ODO-005"}
  ],
  "departments": [
    {"organization_id":"11111111-1111-4111-8111-111111111111","source_id":"old-department","target_id":"22222222-2222-4222-8222-222222222222","evidence":"reviewed department mapping ODO-005"}
  ],
  "documents": []
}
```

Известный Keycloak sub проверяется точным совпадением в компании. `workspace:<числовой ID>` разрешается через соответствующий локальный ID Workspace, затем сохраняется реальный sub. Email, ФИО и похожие числовые строки не используются для поиска. Для `usr_*` нужен проверенный binding. Локальные `author_id`/`assignee_id` ЭДО сохраняются: вход пользователя и document ACL не переименовываются. Только исходящий снимок использует канонические sub/UUID подразделений. Последующие штатные события используют те же сохранённые связи.

Компания берётся из документа. Если она пуста, нужен отдельный документный binding с evidence; он не может переопределить уже известную другую компанию. Компания, закреплённый issuer и существующие связи не меняются на основании текущего пользователя. Неизвестная/чужая компания, отключённый модуль и неоднозначные совпадения попадают в blocked. Учётные записи не создаются.

```sh
go run ./cmd/odo-assignments-backfill -mode plan -bindings bindings.json -reason "ODO-005 reviewed historical import" -limit 100 -output plan.json
```

Можно ограничить выборку `-assignment-ids id1,id2` или продолжить следующую порцию через `-after <последний assignment_id>`. Максимум 1000 записей. Без явных ID выбираются старые/failed/held записи и незавершённые staged-переносы. Пустой план означает отсутствие выбранных кандидатов, а не проверку всей production-интеграции.

После проверки `plan.json` скопировать его поле `hash`:

```sh
go run ./cmd/odo-assignments-backfill -mode apply -plan plan.json -confirm-plan <hash> -output report.json
```

Выходной файл должен быть новым; существующий файл не перезаписывается. При возобновлении сохранить отчёт под другим именем. План, bindings и отчёт содержат персональные/служебные данные: хранить ограниченно, не коммитить в Git.

## Старые карточки Workspace

Известная проекция обновляется с большей revision. Общая старая проекция без компании может быть принята только по явным `task_id` и хешу карточки/получателей из плана, при совпадении assignment/document ID и revision=0. Все существующие получатели должны относиться к подтверждённой компании. Нельзя автоматически объединять несколько карточек или переносить контекст Kanban: цели, проекты, спринты, родителей/детей, вложения, комментарии, метки, чек-листы и worklog.

При успешном принятии сохраняются UUID карточки и история; доска/колонка меняются на компанию, отображаемый task key/номер назначается на новой доске. Если карточка изменилась после проверки, возвращается `ODO_BACKFILL_CHANGED`, транзакция откатывается. История не удаляется. Данные с дополнительным контекстом или конфликтом требуют отдельного ручного разбора, а не повторного reset revision/удаления outbox. При конфликте уже staged-операции очередь остаётся закрытой до такого разбора; новая операция не обходит её блокировку.

## Архивные и удержанные поручения

Для действующих поручений исполнитель должен быть активен в своей компании. Архивные `completed`/`closed`/`cancelled` разрешают исторических неактивных/удалённых пользователей той же компании только через операторский backfill. Это не даёт им права входа/чтения. Обычный upsert сохраняет прежние проверки активности. Неизвестные исторические даты выполнения/закрытия остаются null.

Незавершённое создание (`workspace_sync_ready=false`) блокируется по умолчанию. `-recover-held` допускает восстановление только если ACL `reason=assignment` для исходного исполнителя уже записан и документ вышел из незавершённого состояния. CLI не выдаёт ACL, не переводит документы по жизненному циклу и не выдумывает успешное создание. Сначала устранить реальную причину сбоя в ЭДО, затем проверить новый план с этим флагом.

## Проверка

Регрессионные тесты проверяют dry-run без записей, namespace `workspace:`, отсутствие bindings, чужую компанию, отключённый модуль, неактивного исполнителя и архив, held recovery, CAS исходного документа/поручения, конфликт registry, удержание последующих событий, повтор одного event ID после сбоя и отсутствие/подделку durable receipt. Workspace проверяет принятие legacy UUID, отказ при изменении карточки/чужом получателе/контексте, архивный режим, повторный duplicate и закрытый по умолчанию endpoint. Миграционные upgrade-тесты выполняются на отдельном PostgreSQL.

Production Keycloak, реальные справочники и production-перенос оператор должен проверить отдельно. Следующие задачи: обратная команда выполнения (6), интерфейс (7), production-проверка (8).
