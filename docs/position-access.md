# Права должностей Workspace → ЭДО / SenimDesk / iForm

Общая целевая модель, границы административных и рабочих полномочий, а также ещё не исправленные расхождения описаны в [контракте доступа](access-model.md). Этот документ описывает текущие API и порядок подключения; наличие целевого правила не означает, что все потребители уже ему соответствуют.

## Раздел в интерфейсе

«Люди → Структура → Права доступа».

- Системный администратор выбирает компанию: `/platform/organizations/:organizationId/access`.
- Владелец компании открывает `/organization/access` и работает только со своей компанией.
- Обычным сотрудникам и роли `manager` управление правами не разрешено. Роль платформы `admin` определяется сервером, а не выбранной должностью.
- Должности можно создать, переименовать и назначить сотрудникам. У каждой должности три независимых набора: ЭДО, СД и iForm.
- Удаление должности с сотрудниками запрещено. Назначение можно снять или заменить другой должностью.

Настройки компании не пересекаются с настройками других компаний. Доступ определяется назначением сотрудника на ID должности. Миграция `20261003000100_sync_employee_access_position.sql` синхронизирует изменение `users.position` с этим назначением по нормализованному названию внутри компании. Новое название создаёт должность без настроенных наборов; существующее может применить уже сохранённые права. Поэтому создание сотрудника, импорт и редактирование должности профиля должны проверяться как изменение доступа. Название «админ» само по себе не меняет системную роль пользователя.

UI показывает все должности, включая пустые. Порядок подготовки:

1. Создайте должность по названию; сотрудник при создании не требуется.
2. Сохраните нужные наборы ЭДО, СД и iForm. Это можно сделать до назначения людей.
3. Откройте «Управлять сотрудниками» у должности и назначьте сотрудника компании. Выбор человека с другой должностью заменяет прежнее назначение и применяет набор новой должности.
4. После снятия последнего сотрудника должность и её наборы остаются в списке. Пустую должность можно переименовать или удалить; занятую сначала нужно освободить.

Повтор названия при создании возвращает ошибку и не назначает никого на существующую должность. Ошибка сохранения оставляет введённое название в форме. Если операция уже сохранена, а перечитывание списка не удалось, интерфейс сообщает об этом и предлагает обновить данные.

Задача 3 использует существующие API без изменения схемы. Проверки `TestAccessPositions*` в `internal/repository/organization_access_positions_integration_test.go` проходят на отдельной PostgreSQL: пустая должность, подготовка трёх наборов, назначение/перевод/снятие, сохранение прав при переименовании, запрет удаления занятой должности, revision, директор/суперадмин и отказ при попытке изменить чужую компанию. Frontend-сценарии, ошибки, повторные нажатия и устаревшие ответы проверяет `node scripts/test-position-access-flow.cjs` в `workspace-front`.

## Включение управления

Сначала сохраните нужные наборы всех должностей, затем включите «Права управляются в Workspace» отдельно для каждого приложения.

Сохранение набора не включает модуль или управление. В задаче 4 UI разделяет состояния: модуль не разрешён платформой, выключен компанией, отсутствует связь SenimDesk, действуют прежние роли ЭДО/СД, выключен доступ iForm либо включено управление по должностям. Поле `apps.enabled` само по себе не означает доступность приложения: нужны также `available`, `module_enabled` и активная компания. Для iForm прежний режим ролей через этот мост не показывается.

Набор можно подготовить и сохранить для выключенного модуля. Включение управления недоступно, пока модуль не разрешён и не включён, а для СД — пока нет связи. Отключить сохранённое управление можно и после выключения модуля; рабочий доступ от этого не возвращается. Настройки показывают переход в существующее управление модулями компании.

При конфликте сохранения прав UI перечитывает актуальный набор, сохраняя выбранные галочки. Администратор может посмотреть набор с сервера, использовать его или явно нажать «Сохранить мой выбор» с новой revision. Автоматической повторной записи нет. Если режим управления изменён параллельно, подтверждение закрывается, показывается актуальное состояние, а повторное переключение требует нового выбора. Ошибка перечитывания после уже успешной записи блокирует следующие изменения до обновления данных.

Регрессии задачи 4: frontend `scripts/test-position-access-state.cjs` и `scripts/test-position-access-flow.cjs`; backend `TestAccessApplication*` в `internal/repository/organization_access_application_integration_test.go` на отдельной PostgreSQL. Проверяются независимость сохранения и включения, настроенный пустой набор, выключенный/неразрешённый модуль, отсутствие связи СД и конфликты revision. Полный E2E потребителей и исправления их серверных исключений остаются в задачах 6–10.

## Зависимости прав (задача 5)

GET access-management дополнительно возвращает `dependencies` с ключами `odo`, `sd`, `iform`. Значения — массивы `{ "permission": "approval.start", "any_of": ["approval.read"] }`. Каждое правило выбранного права требует хотя бы одну альтернативу; несколько правил для одного права выполняются одновременно. Сервер формирует правила из `internal/domain/access_dependencies.go` с учётом каталога компании. Они описывают согласованные наборы для UI и API; не заменяют проверки объектов и участников в сервисе.

- Действия с обычным документом требуют одного из `document.read`, `document.read_department`, `document.read_all`. При уже выбранной широкой области редактор не добавляет узкую. Отдельные архивные роли не требуют чтения обычных документов; вложения также допускают применимое архивное чтение.
- Действия поручения требуют `assignment.read`, согласования — `approval.read`, подписи — `signature.read`; чтение соответствующих карточек требует чтения документов. `approval.start` дополнительно требует `document.send_to_approval`. Обратная зависимость и автоматическая выдача решения согласующего отсутствуют.
- `report.export` требует `report.read`; `archive.manage` требует `archive.export`, поскольку выгрузка в document-service проверяет этот код отдельно. Ни одно из этих правил не добавляет `archive.view_all`.
- Действия НПА требуют `npa.project.read`, но не открывают обычные документы. Исправление фактических guards НПА и связи sidebar с обычным чтением остаётся задачей 6.
- СД сохраняет существующее правило `resource:read_all` → `resource:read`; журнал компании дополнительно требует базовый `rbac_audit:view_audit`. Клиентский каталог не получает служебные права и зависимости.
- У iForm нет безусловных зависимостей: design и publish самостоятельны, HR/finance/accountant/director — функции маршрута. Для этапа APPROVAL отдельно выбирается `iform.approve`, SIGNATURE — `iform.sign`, запуска employee-процесса — `iform.use`. Это поясняется у соответствующих функций, без автоматической выдачи этих действий.

При выборе действия UI добавляет необходимые права в видимый набор и перечисляет добавления в сообщении. При снятии последней подходящей зависимости снимаются зависимые действия, в том числе транзитивно; сохранившаяся альтернатива удерживает действие. Групповая галочка действует только на видимые строки поиска/фильтра. Общая очистка оставляет пустой набор. Сохранение отправляет ровно показанный набор, с прежним revision.

Новые неполные наборы сервер отклоняет HTTP 400 с `ACCESS_DEPENDENCIES_MISSING` (ru/kk), не меняя политику, revision и аудит. Исключение совместимости: прежняя нормализация СД `read_all` → `read` сохранена и теперь также показывается редактором. Другие зависимые права сервер скрыто не добавляет. Старые сохранённые наборы не переписываются при чтении; UI предлагает явное добавление зависимостей перед сохранением. Это не ретроактивный отзыв уже выданных прав.

Выпускать backend Workspace перед frontend или одновременно. Без `dependencies` новый редактор блокирует изменение/сохранение набора и объясняет необходимость обновления backend. Миграция БД и новые переменные окружения не требуются. Изменения этой задачи не выпускают исправления API отдельных потребителей: обходы owner/admin, экспорт отчётов и неподключённые guards всё ещё требуют задачи 6.

Проверки: `TestAccessDependencies*`, `TestAccessApplication*`, `TestAccessPositions*` на отдельной PostgreSQL; frontend `scripts/test-permission-selection.cjs`, `scripts/test-position-access-flow.cjs`, `scripts/test-position-access-state.cjs`. UI проверяется на тестовом API, включая поиск, снятие базового чтения, сохранение и ширину 390 px; это не общий E2E с работающими ЭДО/СД/iForm.

При включённом режиме:

- Для обычных сотрудников права точно заменяют прежние роли, индивидуальные назначения и автоматические привилегии администратора приложения. Действующий владелец компании получает весь делегируемый каталог прав своей компании без обязательного назначения должности. Для клиентской компании СД остаётся ограничение клиентского каталога.
- У обычного сотрудника пустой набор, отсутствие настроенного набора или отсутствие назначенной должности означают отсутствие прав. Полномочия владельца определяются актуальным organizations.owner_id и активным членством, а не названием должности или ролью платформы.
- Изменения применяются при следующем запросе API. Открытый экран приложения может обновить видимость кнопок после обновления страницы.
- Ограничения по компании, участию в документе/проекте и допустимым операциям над объектом продолжают действовать.
- Права платформы, межкорпоративный системный аудит и управление общим справочником RBAC ЭДО не делегируются через этот каталог.

Правило уточнено пользователем 27.10.2026: действующий владелец получает все рабочие права сервисов своей компании. Автоматические полномочия платформенного администратора и названия должностей по-прежнему не заменяют рабочие права. Административное управление компанией сохраняется отдельно от рабочих действий. Подтверждения и оставшиеся границы проверки описаны в [приёмке задачи 10](access-acceptance.md); наличие локального исправления не подтверждает обновление сервера.

Включение управления правами и включение модуля — разные настройки. `apps[application].enabled` означает управление правами, `available` — разрешение платформы, `module_enabled` — включение модуля компанией. На стороне `current/access` сначала проверяются `active`, затем `managed` и нужное право. `active=true` не означает, что набор непустой. Подробности: [API модулей](company-administration-modules.md).

Для ЭДО и СД отключение режима возвращает прежний RBAC приложения. Наборы должностей сохраняются. UI просит подтвердить переключение. Это не удаление сессии и не выход из Keycloak. Для iForm отключение управления прекращает доступ через текущий мост Workspace; отдельного прежнего режима этот мост не поддерживает.

## Серверное применение прав (задача 6)

При управлении через Workspace рабочая идентичность передаётся с ролью `user`, без переноса платформенного `admin`. Действующий владелец управляет должностями и назначениями и автоматически получает все рабочие роли iForm, включая `TENANT_ADMIN`. Для остальных сотрудников `IFormRoles` возвращает только явно выбранные функции. Имя должности не меняет эти правила. Прежний режим ЭДО/СД вне управления Workspace сохраняется отдельно.

Исправлены проверки реальных операций:

| Сервис | Операция | Условие после исправления |
| --- | --- | --- |
| ЭДО | Экспорт трёх видов отчётов | `report.export` в middleware и HTTP-обработчике; чтение отчёта требует `report.read` |
| ЭДО | История решений/переходов и чтение старых версий | `document.view_history` вместе с доступом к документу; соответствующие вкладки скрыты без права |
| ЭДО | Проверка подписи/целостности | `signature.verify`; обычное чтение не запускает проверку |

| ЭДО | Изменение документа/загрузка вложения | Собственное право `document.update` / `attachment.upload`; создание и авторство не подменяют право. Добавление AI-ответа также требует upload и допустимой роли документа |

| SenimDesk | Типы клиентов | POST без ID — `settings:create`, с ID — `settings:update`, DELETE — `settings:delete`. Только штатный контекст и его запись; upsert не перемещает запись другого tenant. Кнопки разделены по этим правам |

## Состояния и конкурентные операции ЭДО (задача 7)

Изменения продолжают рабочие копии ЭДО `C:/Users/Merey/workspace-odo/access-task6-backend` и `access-task6-front` из задачи 6. Основные checkout, SenimDesk и iForm эта задача не меняет. Код реализован локально; выпуск и общая приёмка всех сервисов ещё не выполнены.

Документ-service и проекция доступных действий BFF используют одну матрицу `internal/document/lifecycle/transitions.go`. Рабочее право проверяется до возврата результата повторного запроса. Произвольным переходом нельзя поставить `signed`: подпись сохраняется отдельной операцией с проверкой содержимого, назначенного подписанта и записью версии. Неизвестный вид документа не получает переходы.

| Действие | Проверка |
| --- | --- |
| Запуск согласования | Зарегистрированный/доработанный документ или допустимое повторное согласование; `document.send_to_approval` либо `approval.start`; для доработки — автор |
| Решение согласующего | `approval.approve`, `approval.return_for_revision` или `approval.reject` по действию; документ ещё `on_approval`, текущий участник/допустимое замещение |
| Поручение | `assignment.create` и этап исполнения; создание во время незавершённого согласования запрещено. Исходящий документ также может проходить исполнение |
| Завершение исполнения | Все поручения документа завершены/закрыты/отменены; очередное открытое поручение не позволяет закрыть весь документ |
| Подписание | Зарегистрированный документ без предшествующего согласования в настроенном маршруте либо завершённые предыдущие этапы; `document.send_to_signing`, затем отдельное `signature.sign` назначенного подписанта |
| Закрытие/архив | Допустимый переход и соответствующее право. Настроенный незавершённый маршрут нельзя закрыть через отдельную кнопку |

Настроенный маршрут не переписывается во время согласования, исполнения, подписания и после завершения. До запуска или после возврата на доработку сохранение требует точный `expected_updated_at` из GET workflow-plan. Поле `updated_at` передаётся без потери долей секунды. Устаревшая/отсутствующая версия существующего плана возвращает HTTP 409, без автоматической перезаписи. UI сохраняет черновик формы и предлагает открыть актуальный маршрут заново. AI-применение плана использует такую же проверку версии и требует право регистратора; чтение всех документов не разрешает AI создавать поручения.

Сохранение, ручной старт согласования/подписания и автоматическое продолжение используют блокировку плана по документу и CAS. Ручной запуск использует текущий этап, а не объединение всех согласующих будущих этапов; замена согласующего или подписанта в запросе не меняет сохранённый маршрут. Автопродолжение выполняется от регистратора, настроившего план, с заново полученными правами и компанией. Завершающий согласующий не получает служебные `read_all`, `assignment.create` или `signature.sign`. Если доступ регистратора отозван/источник недоступен, следующий этап не стартует.

CAS перехода документа проверяет статус и время версии: возвращение документа к прежнему статусу не делает старый запрос актуальным. Переход и история сохраняются в одной транзакции. Изменение поручения дополнительно сравнивает исполнителя, автора и документ под блокировкой: прежний исполнитель не завершает уже переназначенную работу. Сохранённый результат поручения после сбоя RPC безопасно дочитывается повтором; результат и outbox не записываются второй раз. Для согласования восстановление применимо только к уже сохранённому совпадающему решению последнего маршрута, пока документ ещё ожидает его результата. Исторический маршрут не меняет новый цикл.

Дата срока без времени действует до конца дня в UTC+5, как календарь ЭДО. Указанное время документа учитывается отдельно. Просрочка не появляется в начале дня срока; карточка, поручения, SLA и отчёт пересчитывают её при чтении. Законченные/отменённые поручения и завершённые маршруты не становятся просроченными. Конструктор отвергает несуществующие календарные даты.

Проверки: Go unit/HTTP и интеграционные тесты затронутых document/workflow/BFF-пакетов на отдельной PostgreSQL; конкурентное сохранение плана, старый исполнитель, повтор статуса/результата, восстановление решения, UTC+5 и границы времени. `TestIncomingAndOutgoingLifecycleWithActualRepositoriesIntegration` проходит оба вида документа до архива на реальных репозиториях. Для подписи в этом тесте используется синтетический успешный результат криптопровайдера; это не живой прогон NCALayer/ЭЦП. Frontend: `tsc -b`, тест API версии/409 и `localization-check`.

Нужен совместимый выпуск document-service, workflow-service, BFF и frontend ЭДО (с новым полем версии); новых миграций и настроек окружения нет. Сначала backend, затем соответствующий frontend: старый клиент не сможет молча переписать существующий план без версии. Полный браузерный E2E, реальные внешние редакторы/криптопровайдер и аварийное восстановление всей распределённой цепочки остаются частью общей приёмки задачи 10. Выбор участников и отдельный путь Workspace Work остаются задачами 8 и 9.

## Участники и недоступные маршруты ЭДО (задача 8)

Изменения продолжают изолированные рабочие копии ЭДО из задач 6–7. Сотрудник появляется в подборе только при подтверждённом активном членстве в текущей компании, активном доступе ЭДО, допустимом подразделении и полном наборе рабочих прав. Список не требует `user.read` и не подмешивает сохранённые ID либо регистратора в исполнители. Workspace остаётся источником актуальных прав; сотрудники материализуются в ЭДО и до первого входа.

| Участник | Рабочие права помимо чтения документа | Подразделение | Автор своего документа |
| --- | --- | --- | --- |
| Регистратор | `document.register` | Получатель, его предки или потомки; без соседних веток | Разрешено |
| Согласующий | `approval.read`, `approval.approve` | Получатель и его потомки | Запрещено |
| Исполнитель | `assignment.read`, `assignment.complete` | Получатель и его потомки | Разрешено |
| Подписант | `signature.read`, `signature.sign`, `attachment.download` | Текущая компания | Запрещено |

Чтение документа — хотя бы одно из `document.read`, `document.read_department`, `document.read_all`. Право действия без возможности открыть соответствующий этап не делает сотрудника пригодным участником. Права не добавляются должностям автоматически. Исключение явного локального администратора для подразделения регистратора сохраняется только в прежнем режиме управления; при Workspace-managed доступе оно не действует.

GET `/api/v1/documents/{document_id}/workflow-participants` проверяет доступ к документу и право использования подбора. Поддерживает `kind=registration|approval|execution|signing`, поиск и пагинацию. Поле `availability` содержит `counts` по четырём видам участников, `active_employee_count`, действующие флаги самосогласования/самоподписи/самоисполнения и `invalid_participant_ids` сохранённого оставшегося маршрута. Счётчики вычисляются до поиска и пагинации: пустая поисковая страница не означает отсутствие кандидатов. Ответ не раскрывает ИИН, БИН и административные роли.

GET `/api/v1/workflow/participants?department_id=...&kind=registration` под правом `document.create` используется до создания документа. Отсутствие доступного регистратора показывается в форме и отклоняется сервером до создания. Недоступность источника отличается от нулевого количества кандидатов и не позволяет продолжить с устаревшим справочником.

Сохранение плана, регистрация, ручной запуск согласования/подписания, создание поручений, применение AI-плана и автоматический переход повторно проверяют актуальных участников до соответствующей записи/запуска. До пакетного создания поручений проверяются все выбранные исполнители. Завершённые этапы не требуют повторной доступности их бывших участников. Сохранённые недоступные участники остаются видны для исправления, но не возвращаются в списки доступных кандидатов. Формы сохраняются при ошибках, устаревшие запросы отменяются.

**Один сотрудник:** при наличии прав и допустимого подразделения автор может зарегистрировать и исполнить документ. Согласовать или подписать собственный документ он по действующему правилу не может. Для такого этапа нужен другой подходящий сотрудник. Этапы не пропускаются автоматически, исключение для директора/суперадминистратора не вводится, дополнительные обязательные этапы не добавляются. Существующее дополнительное правило AI, запрещающее одному участнику одновременно согласование и подпись, этой задачей не меняется. Новое продуктовое решение о самосогласовании/самоподписи требует отдельного согласования.

Выпуск: обновить BFF и frontend ЭДО совместно; новые миграции, переменные окружения и изменения Workspace/SenimDesk/iForm не нужны. Проверки включают отдельную PostgreSQL, актуализацию прав, материализацию до первого входа, ограничения подразделений, singleton, поиск/пагинацию, запрет запуска с отозванным правом и отмену устаревших запросов UI. Реальная многосервисная приёмка и криптопровайдер остаются задачей общей проверки.

## Поручения ЭДО в разделе «Работа» (задача 9)

Workspace показывает только поручения, назначенные текущему сотруднику. При включённом управлении правами чтение требует `assignment.read` и хотя бы одно из `document.read`, `document.read_department`, `document.read_all`; выполнение дополнительно требует `assignment.complete`. Владение компанией и роль суперадминистратора не заменяют эти права. Назначать должности и права директор/суперадминистратор по-прежнему могут через административный раздел.

Форма результата подключена в карточках и списке поручений. Право выполнения перечитывается перед каждой отправкой, включая повтор. При потере доступа незавершённый запрос отменяется, поздний ответ не меняет интерфейс; текст и неизменяемая команда сохраняются для того же сотрудника/компании. Поле результата остаётся доступным для чтения, но не редактирования при безопасном повторе. Смена компании очищает прежний экран до загрузки нового списка.

Открытая форма сохраняет исходную версию поручения. При изменении версии или HTTP 409 запрос не пересылается автоматически с новой revision: требуется обновлённое активное поручение и отдельное действие «Создать новый запрос». Для выполненного, закрытого, отменённого или переназначенного поручения новый запрос не предлагается. При неопределённом результате повторяются прежние `command_id`, `expected_revision` и `result_comment`.

В ЭДО оба пути выполнения требуют `assignment.read` и `assignment.complete`, доступ к документу и допустимого текущего исполнителя. Команда Workspace также сверяет компанию, issuer, подтверждённый subject, исходное поручение/документ и revision под блокировкой. Старый исполнитель не получает доступ через сохранённое подтверждение после переназначения или отзыва прав.

Выполнение из Workspace использует тот же механизм восстановления статуса документа, что и выполнение внутри ЭДО. Сбой после записи результата не откатывает транзакцию поручения, но не выдаёт клиенту ложный успех продолжения. Повтор той же команды восстанавливает документ/маршрут без второго результата, audit receipt или снимка outbox. Историческое завершение не закрывает новое исполнение с открытыми поручениями. Workspace обновляет статус только после снимка источника, а подтверждение команды показывает отдельным состоянием; запоздалое старое событие не откатывает новый статус.

Проверки: Workspace HTTP-клиент, права обычного сотрудника/директора/admin, отзыв должности, перенос исполнителя, применение снимка и запоздалое событие на отдельной PostgreSQL; ЭДО — repository/workflow/protobuf/BFF, конкурирующие команды, повтор, версия, доступ, восстановление после сбоя; frontend — политика, реальные обработчики модели, неизменяемый повтор, старая открытая форма, поздний ответ после отзыва доступа, отображение формы. Форма проверена в локальном браузере на обычном и узком экране с синтетическими данными. Живые production-сессии, сеть и непрерывный многосервисный E2E отдельно не проверены.

Выпуск требует backend/frontend Workspace и workflow-service/BFF/frontend ЭДО из рабочих копий `access-task6-*`. Новых миграций и переменных нет; существующие флаги `ODO_COMMANDS_ENABLED`, `ODO_WORKSPACE_COMMANDS_ENABLED` и доставка outbox должны быть настроены по [контракту выполнения](odo-assignments-completion.md). Legacy-режим сохраняет прежнюю проверку источником; автоматические рабочие права административных ролей не возвращаются в managed-режим.

## Связь с SenimDesk

Связь настраивает только системный администратор Workspace, выбирая действующую компанию из каталога СД. Сопоставление выполняется по UUID, а не по названию или поддомену. Один UUID компании СД может быть связан только с одной компанией Workspace.

Для клиентской компании СД каталог автоматически ограничивается разрешёнными действиями клиентской компании. Для штатной компании доступны операции штатного тенанта. При изменении связи на клиентскую компанию неподдерживаемые права удаляются из подготовленных наборов. Для изменения действующей связи сначала отключите управление СД.

Пользователь сопоставляется по подтверждённому `sub` Keycloak либо по серверному handoff Workspace с subject `workspace-user:<id>`. Парольный вход в старый аккаунт СД без подтверждённой привязки не выдаёт права Workspace при включённом управлении. Привязка создаётся поддерживаемым общим входом; обычные изменения логина, email или профиля её не меняют.

Первый поддерживаемый общий вход нового сотрудника создаёт аккаунт в связанной компании СД. Существующий аккаунт в другой компании автоматически не переносится; исправить принадлежность должен администратор. При смене контекста СД дополнительно проверяется локальное членство, а права разрешаются для выбранной компании.

## Настройки серверов

Используйте один новый случайный серверный токен для этой интеграции (например, результат `openssl rand -hex 32`). Не передавайте его фронтендам.

Workspace `/opt/workspace/.env`:

```dotenv
SD_ACCESS_API_URL=http://sd-backend:18080
SD_ACCESS_INTERNAL_TOKEN=<общий серверный токен>
```

SenimDesk, production `.env`:

```dotenv
WORKSPACE_ACCESS_API_URL=http://workspace-api:8080
WORKSPACE_ACCESS_INTERNAL_TOKEN=<тот же серверный токен>
```

ЭДО `/opt/odo/.env`:

```dotenv
WORKSPACE_ACCESS_ENABLED=true
WORKSPACE_API_BASE_URL=https://teamspace.kz
```

В предоставленных production compose SD и Workspace используют сеть `workspace_workspace`. При другом размещении укажите реально доступные backend URL. Адрес SD_ACCESS_API_URL должен вести непосредственно на backend СД, без префикса страницы `/sd`. При входе через Keycloak SD и Workspace должны использовать один доверенный realm Keycloak.

## Порядок обновления

1. Обновить backend Workspace с миграцией `20261002000100_organization_access.sql` и frontend Workspace.
2. Обновить backend СД с миграцией `20261002000100_workspace_identity.sql`, добавить обе переменные интеграции; обновить frontend СД.
3. Обновить auth-service и BFF ЭДО с миграцией `000024_workspace_position_access.sql`; добавить WORKSPACE_ACCESS_ENABLED=true; обновить frontend ЭДО.
4. В новом разделе связать компанию с СД, проверить назначения сотрудников, подготовить наборы прав. Выполнить поддерживаемый общий вход существующих пользователей СД для привязки аккаунтов.
5. Включить управление для нужных приложений компании. Проверить работу под сотрудником с минимальным набором прав и под сотрудником без прав перед массовым включением.

Миграции запускаются штатными средствами деплоя соответствующего backend. Изменение `.env` требует пересоздания контейнера: простой `docker restart` не загружает новые значения environment. Первым обновляется Workspace; потребители с включённой интеграцией при недоступном источнике прав отказывают в доступе, а не переключаются на старые привилегии.

## API и хранение

- GET `/api/v1/organizations/current/access-management` — данные владельца своей компании.
- PUT `/api/v1/organizations/current/access-management/:action` — position, delete, policy, application, member, unassign.
- GET/PUT `/api/v1/platform/organizations/:organization_id/access-management[/:action]` — аналогичные действия с серверной проверкой системного администратора; дополнительно link.
- GET `/api/v1/platform/organizations/:organization_id/access-management/sd-companies` — реальный каталог компаний СД для системного администратора.
- GET `/api/v1/organizations/current/access?application=odo` — собственное подтверждённое членство и права для ЭДО, под bearer текущего пользователя.
- Параметр `application` собственного endpoint также поддерживает `sd` и `iform`; для рабочего доступа iForm используются его proxy и серверный контекст.
- GET `/api/v1/organizations/current/users?application=odo` — сотрудники своей компании с политиками ЭДО для подбора участников.
- POST `/api/internal/iform/context` — подтверждённый контекст компании и сотрудников для iForm, под серверной авторизацией.
- POST `/api/internal/access/resolve-sd` — права по компании СД и подтверждённому subject Keycloak или `workspace-user:<id>`, только под серверным токеном.
- POST `/api/internal/access/identity-sd` — компания для первого SSO-входа сотрудника СД, только под серверным токеном.
- GET backend СД `/api/internal/workspace/companies` — каталог для настройки связи, только под серверным токеном.

Данные: organization_access_positions, organization_access_assignments, organization_position_permissions, organization_access_apps, organization_app_links. Все изменения владельца и системного администратора транзакционно записываются в organization_access_audit. Политики и переключение режима используют revision для защиты от перезаписи параллельных изменений.

Каталог разрешённых кодов хранится в `internal/domain/access_catalog.go`. При добавлении нового делегируемого права в сервис его нужно также добавить в каталог Workspace; произвольные коды и системные права отклоняются сервером. В задаче 2 каталог сверён с API/UI ЭДО, СД и iForm: добавлены шесть существующих `archive.*` ЭДО; теперь доступны 49/68/11 кодов соответственно. [Матрица операций, зависимостей и ещё не исправленных проверок](access-permission-catalog.md) отделяет регистрацию кода от реальной авторизации действия. Новые права не добавляются в сохранённые политики автоматически.

ЭДО сохраняет последний полученный набор в workspace_user_access для справочника. Это снимок: живая авторизация текущего сотрудника всегда использует ответ Workspace. В СД эффективный набор разрешается один раз на запрос и заменяет локальные роли до проверки операций.

## Начальные настройки сервисов и владелец

Миграция `20261027000300_company_service_defaults.sql` добавляет недостающие настройки ЭДО, SenimDesk и iForm только компании с slug `tts` и создаёт эти настройки автоматически для будущих компаний. Существующие записи, включая явно отключённые модули и режим управления правами, сохраняются. Остальные существующие компании не меняются. Перед созданием новых компаний обновите backend с этой миграцией; новые переменные окружения и изменения frontend не требуются.

Владелец получает все реализованные рабочие права своего тенанта при включённом управлении доступом и доступном включённом модуле. В iForm это все роли компании, включая HR, DIRECTOR, SIGNER и APPROVER, плюс TENANT_ADMIN. Права платформы и доступ к чужим компаниям не выдаются. Передача владения, смена компании, удаление или отключение пользователя и приостановка компании, дата начала работы и отмена допуска проверяются при новых запросах. Внешние сервисы сохраняют свои проверки конкретных документов и операций. Для СД остаётся штатное создание и связывание пространства по UUID при первом открытии; отсутствие конфигурации внешней интеграции не обходится.
