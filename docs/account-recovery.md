# Резервная почта и восстановление пароля

Резервный адрес хранится в `user_recovery_emails` отдельно от `users.email`, почтового ящика и идентификатора Keycloak. Адрес, подтверждённый при регистрации по приглашению, сам по себе не включает восстановление: пользователь явно привязывает резервную почту в профиле.

## Пользовательские сценарии

- **Привязка или замена:** текущий пароль → письмо на новый адрес → шестизначный код и текущий пароль → сохранение. До подтверждения работает прежний резервный адрес.
- **Отвязка:** текущий пароль → код на действующий резервный адрес → подтверждение. После отвязки восстановление по почте недоступно.
- **Забытый пароль:** логин, рабочая или резервная почта → одинаковый публичный ответ → письмо на подтверждённый резервный адрес → новый пароль → обычный вход. Неоднозначный логин не запускает восстановление нескольких аккаунтов.

Код действует 10 минут, допускает 5 ошибок; повторная отправка — через 60 секунд, максимум 5 писем в час. Ссылка восстановления одноразовая, действует 30 минут. Сервер учитывает ограничения в PostgreSQL независимо от необязательного общего HTTP rate limiter. Клиент не повторяет изменяющие запросы автоматически после сетевой ошибки.

Код хранится как HMAC-SHA256 с ключом сервера; ссылка содержит 256 бит случайности, в базе находится только SHA-256 токена. Секрет передаётся в URL-фрагменте, затем в теле POST. Пароли, коды и токены не записываются в логи или браузерное хранилище. Письма на восстановление отправляет фоновый обработчик: время ответа публичного API не зависит от SMTP и наличия аккаунта.

При замене или отвязке аннулируются прежние доказательства восстановления. На прежний и новый адреса приходят уведомления о соответствующем изменении. Уведомления имеют отдельную очередь и повторяются при временном сбое почты. Рабочий адрес, организация и роли не меняются. Адрес другого пользователя или почтового ящика системы нельзя назначить резервным.

## HTTP API

Все пути начинаются с `/api/v1`. Запросы и ответы содержат `Cache-Control: no-store`; язык сообщений и писем — RU/KK через `Accept-Language`.

| Метод и путь | Данные | Доступ |
|---|---|---|
| `GET /auth/recovery-email` | `email`, `verified_at`, `pending` | Текущий пользователь |
| `POST /auth/recovery-email/code` | `{email, purpose: "bind" или "remove", password}` | Текущий пользователь |
| `POST /auth/recovery-email/confirm` | `{id, code, password}` | Текущий пользователь |
| `POST /auth/recovery/request` | `{login}` → `{ok:true}` | Публичный |
| `POST /auth/recovery/preview` | `{token}` → `{ok:true}` без данных аккаунта | Публичный |
| `POST /auth/recovery/complete` | `{token, new_password}` → `{ok:true}` | Публичный |

`pending` содержит `id`, `email`, `purpose`, `expires_at`, `retry_at`. Ошибки имеют коды `RECOVERY_INVALID`, `RECOVERY_CODE_INVALID`, `RECOVERY_REAUTH_FAILED`, `RECOVERY_EMAIL_CONFLICT`, `RECOVERY_LIMITED`, `RECOVERY_PASSWORD_POLICY`, `RECOVERY_PENDING`, `RECOVERY_UNAVAILABLE`. Неверный текущий пароль возвращает 400, чтобы форма не завершала рабочий сеанс пользователя. 503 `RECOVERY_PENDING` означает: повторить действие по той же ссылке; пароль мог уже измениться.

## Сбои и старые сеансы

Общая блокировка пользователя в PostgreSQL сериализует смену пароля, изменение резервной почты и восстановление между процессами. Перед изменением пароля сохраняется `reset_pending`; до завершения операции сервер запрещает использование старых и выпуск новых токенов. Этот запрет сохраняется при перезапуске API и временной недоступности Redis или Keycloak.

Состояния запроса: `pending → processing → password_set → completed`. До передачи пароля проверяются длина 8–128 символов и формат запроса; политику сложности дополнительно проверяет Keycloak. Достоверный отказ политики не блокирует аккаунт. Если результат изменения неизвестен из-за обрыва связи, пользователь повторяет запрос. При отказе истории паролей сервер проверяет новый пароль через доверенный Keycloak, чтобы распознать уже выполненное изменение. Открытый пароль для продолжения операции не сохраняется.

Для `password_set` фоновый обработчик завершает отзыв сеансов без участия пользователя. Для `processing` нужен повтор по действующей или новой ссылке; автоматически снимать защиту при неизвестном результате нельзя. Письмо с новой ссылкой разрешено и в этом состоянии. Администратору при ручном разборе следует сначала убедиться в фактическом состоянии пароля и отозвать сеансы; простое удаление `reset_pending` не является восстановлением.

После восстановления удаляются локальные access/refresh-токены, завершаются WebSocket-соединения, деактивируются PIN-сеансы и неподтверждённые выдачи браузерных сеансов. Keycloak отзывает online-сеансы; offline-сеансы всех настроенных клиентов удаляются отдельно через Admin API. На каждом запросе сервер проверяет время исходной аутентификации относительно сохранённой границы. Оно переносится через обновление токенов, SSO bootstrap и обмен токенов, поэтому обновление старого refresh-токена не создаёт новый сеанс в обход отзыва. Старый локальный bcrypt-пароль больше не служит запасным входом для аккаунта, связанного с Keycloak.

Обычная смена пароля и её веб-форма больше не требуют ключей шифрования чатов. Необязательный `e2ee_backup` оставлен только для совместимости со старыми клиентами; прежняя компенсация при ошибке сохранения такого backup сохранена.

## Выпуск и проверка

1. Применить миграцию приглашений `20261025000100`, затем `20261025000200_account_recovery.sql` **до запуска нового backend**: новая проверка токенов использует таблицу состояния паролей.
   На выпущенной базе с версией `20261023000100` возможен проверенный пропуск `20261022100600_ai_audio_measurements.sql`. Мигратор отдельно разрешает эту независимую миграцию и четыре ранее выпущенные миграции новостей; остальные пропуски по-прежнему блокируют обновление. Репетиция `TestAudioMeasurementUpgradeFromReleasedResearchIntegration` воспроизводит этот ledger, проверяет сохранение завершённой истории начислений, повторный запуск и отказ при соседнем непроверенном пропуске. Записи `goose_db_version` вручную не удалять.
2. Проверить действующий SMTP и `APP_PUBLIC_URL` с доверенным HTTPS-адресом платформы. Ссылки ведут на `/web/recover#token=…`; входящие `Host` и `Origin` не используются для их построения. Секрет подписи JWT также защищает коды; его ротация аннулирует неподтверждённые коды.
   Для Stalwart submission на 465 задать `SMTP_IMPLICIT_TLS=true`, `SMTP_USE_TLS=true`, `SMTP_SKIP_TLS_VERIFY=false`. При внутреннем маршруте `SMTP_HOST=host.docker.internal` имя сертификата указывается отдельно: `SMTP_TLS_SERVER_NAME=mail.teamspace.kz`. Production compose предоставляет адрес шлюза хоста. Пароль SMTP хранится только в защищённом серверном `.env`.
3. У сервисного аккаунта Keycloak должны работать просмотр клиентов, просмотр пользовательских сеансов, смена пароля, logout и удаление offline-сеансов. Настроенные web/mobile клиенты должны соответствовать клиентам, через которые выдаются токены.
4. Выпустить backend, затем frontend. Проверить доставку письма на принадлежащий тестировщику адрес, смену пароля и отказ старых сеансов. Таблицы миграции сохранять при откате приложения до согласованного решения по отозванным сеансам.

Автотесты: `go test ./...`; проверки PostgreSQL запускаются при `TEST_MESSENGER_DATABASE_URL`, настоящего Keycloak — дополнительно при `TEST_INVITATION_KEYCLOAK_URL`, `TEST_INVITATION_KEYCLOAK_ADMIN`, `TEST_INVITATION_KEYCLOAK_PASSWORD`. Тест создаёт и удаляет отдельный realm и SQL-схему; Keycloak допускается только на loopback. Фронтенд: `npm run build`, `npm run i18n:check`, `node --test tests/accountRecovery.test.mjs tests/organizationInvitations.test.mjs`.
