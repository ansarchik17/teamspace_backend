# Сотрудник до передачи рабочего места в SD

Локальная реализация от 22.10.2026. Обновляется новая версия основы `employee-onboarding`; существующие опубликованные версии и запущенные заявки автоматически не переписываются.

## Порядок и данные

После `completed` того же документа и завершения его маршрута выполняется `workspace.employee.create`. Компания берётся из серверного контекста заявки, платформа назначает обычную роль `user`. ФИО, email, ИИН и должность берутся из обязательных полей заявки; подразделение совпадает с подразделением согласования, руководитель определяется из его структуры. При создании действуют текущие проверки компании и подразделения. Существующий триггер должностей связывает профиль с должностью именно этой компании; чужие права и права HR не копируются новому сотруднику.

Только после подтверждённого числового `employee_id` запускается `workspace.sd.create`:

```json
{
  "employee_id": {"result": {"step": "createEmployee", "key": "employee_id"}},
  "start_date": {"field": "startDate"},
  "workplace_requirements": {"field": "workplaceRequirements"}
}
```

Это дополнительные входы серверного моста Workspace, а не новые поля API SD. Остальные обязательные настройки SD (`project_id`, `object_id`, UUID исполнителя `worker_id`, категория, приоритет и заголовок) сохраняются. UUID исполнителя IT не заменяется числовым ID принятого сотрудника.

Если проект и оборудование принадлежат отдельному клиенту SenimDesk, в `inputs` нужно передать `company_id: {"value": "UUID клиента SD"}`. Это необязательное существующее поле API SD, не UUID организации Workspace. Литерал проверяется при публикации, мост Workspace проверяет UUID и передаёт его без подмены. SenimDesk проверяет актуальный доступ инициатора к клиенту и область проекта. Без поля сохраняется выбор компании из контекста SD. Изменение настройки применяется только к новой опубликованной версии и новым заявкам; параметры уже запущенной операции не переписываются.

Перед первым внешним вызовом Workspace находит успешную квитанцию создания сотрудника для **этой компании, заявки и исходного HR**, сравнивает ID и проверяет актуальный профиль: активность, компанию, ключ приёма, обычную роль, доступность подразделения, активного руководителя той же компании и наличие должности. Без успешного создания сотрудника, с чужим или заблокированным профилем передача в SD останавливается. Обычные процессы SD без кадровых входов сохраняют прежний контракт.

SD получает существующее поле `start_date` в формате `YYYY-MM-DD`. ID сотрудника, дата и требования гарантированно добавляются в читаемое описание заявки. Дополнительное описание сохраняется. В базе SD не появляются выдуманные поля; пароли и ИИН в описание не добавляются. Ответ моста содержит `ticket_id`, подтверждённые `employee_id` и `start_date`; iForm проверяет их до перехода к ожиданию SD.

Публикация кадровой основы запрещает обойти ожидание ЭДО, переставить SD до аккаунта, подставить другой источник сотрудника или убрать обязательные дату/требования. Дата и требования проверяются до запуска; результат создания аккаунта и подтверждение связи SD проверяются при исполнении.

## Повторы и частичные сбои

- iForm автоматически повторяет и восстанавливает после инцидента ту же операцию с теми же ID, occurrence, ключом и параметрами. Повтор не создаёт новый шаг процесса.
- Workspace сериализует одинаковые операции и возвращает сохранённый результат по компании, заявке, шагу и occurrence. Другой актор или изменённые параметры с тем же ключом вызывают конфликт.
- Если сотрудник уже сохранён, но квитанция/ответ потерялись, детерминированный логин `onb.<request UUID без дефисов>` позволяет вернуть тот же локальный профиль. Сверяются данные и назначения; пароль повторно не сбрасывается. Заблокированный или изменённый профиль вызывает конфликт.
- SD получает тот же `Idempotency-Key`; уникальность и hash тела в SD обеспечивают возврат прежней заявки при потерянном ответе и конкурентных повторах. Изменённое тело с тем же ключом вызывает конфликт. Уведомление о назначении на повторе не отправляется заново существующим кодом SD.
- Если удалось создать только запись SSO, а локального профиля ещё нет, чужая/осиротевшая SSO-запись автоматически не присваивается. Требуется сверка HR/администратора; второй аккаунт не создаётся. Это отдельное состояние частичного сбоя, а не подтверждённое создание сотрудника.
- Отмена процесса после внешних изменений не удаляет аккаунт и заявку автоматически. Требуется разбор ответственного.

## Обновление

1. Проверить применение существующих миграций Workspace `20261003000100_sync_employee_access_position.sql`, `20261019000100_iform_operation_receipts.sql` и SD `20261019000100_ticket_idempotency.sql`. Новых миграций в этой задаче нет.
2. Обновить Workspace backend, затем iForm backend. Совместимые старые процессы продолжают работать; новый кадровый контракт требует обновлённого моста.
3. Создать новую версию кадрового процесса из обновлённой основы, заполнить реальные шаблон/маршрут ЭДО и настройки SD, проверить права HR и назначения IT, затем опубликовать по решению администратора.
4. На тестовой компании пройти completed ЭДО → сотрудник → SD, проверить карточку сотрудника и описание/дату SD, повторить после потери ответа. Рабочие процессы и реальные заявки в рамках этой локальной реализации не менялись.

Фронтенд и дизайн не изменены. Допуск с даты выхода реализован отдельно: см. onboarding-employment-admission.md.

При первом входе созданного iForm сотрудника требование смены временного пароля сохраняется после SSO и обновления токенов независимо от значения временного пароля. Общий endpoint завершения приветственных экранов не снимает это требование для такого сотрудника. Workspace показывает обязательную форму смены до открытия защищённых страниц и повторно проверяет серверный профиль после смены; обычная работа разрешается после подтверждённого снятия `is_first_login` сервером.

## Проверки

Проверены серверные пакеты auth/handler/i18n Workspace; создание аккаунта через HTTP-стаб SSO с потерей квитанции и тремя повторами; реальная тестовая PostgreSQL для квитанций Workspace, создания профиля с триггером должности/изоляцией компаний и 12 конкурентных созданий SD. В iForm прошли 42 теста, включая реальный Flowable/PostgreSQL и восстановление после трёх потерянных ответов на этапах создания сотрудника и SD. Внешние сервисы в тестах iForm заменены контролируемым HTTP-стабом. Приёмка на рабочем сервере и реальном SSO/SD не проводилась.
