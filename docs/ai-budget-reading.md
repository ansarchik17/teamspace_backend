> Изменение 20.10.2026: отдельная служебная квота отменена. Актуальные правила и совместимость: [Фоновый расход из общего бюджета](ai-background-shared-budget.md). Указания Qservice ниже относятся к предыдущей версии.

Добавлены доменная модель `AIBudgetSummary`, `OrganizationRepository.AdministrationAIBudget` и одноимённый метод `OrganizationService`. HTTP-маршрутов пока нет: их подключает задача 14. Это внутренняя типизированная модель, не готовый JSON DTO; строки микрокредитов/revision и enforcement_mode будут формироваться на границе API по контракту задачи 04.

## Доступ и снимок

`actor` — проверяемый пользователь; `org=nil` означает компанию директора, явный org разрешён только администратору платформы. Используется существующий accessScope с проверкой актуальных роли, активности и владельца компании. Директор suspended-компании не получает доступ, платформа может читать её бюджет.

Все проверки доступа, настройки, периоды, назначения, расход и резервы читаются в одной Repeatable Read / Read Only транзакции. Метод не создаёт якоря или периоды и не меняет revision. Отсутствие настройки возвращается как Configured=false, Revision=0, B/Hmax=nil и отсутствующие Available/Unallocated/Overcommitted/RemainingPercent, а не как бесплатный безлимит. Служебная квота без настройки — 0.

## Источники данных

- B, Hmax, Qservice и revision — organization_ai_budgets.
- Выделения — действующие записи organization_ai_user_quotas текущих неудалённых сотрудников. Неактивные/заблокированные сотрудники продолжают занимать выделенную квоту.
- Подтверждённый расход текущей недели — materialized used_microcredits компании и детализации сотрудник/служба из таблиц задачи 06. После перевода личный расход не переносится в другую компанию.
- **Удержания — активные строки ai_usage_reservations**, через attempt/operation, закреплённые за исходной компанией. Закрытые резервы исключаются. Старые незавершённые резервы включаются как carried, даже если новое окно ещё не материализовано.
- Поля reserved/carried таблиц периодов — зеркальные счётчики будущего write-сценария и не прибавляются к журналу повторно. Подтверждённый расход из attempts также не суммируется поверх materialized used. Сервис завершения должен обновлять журнал и счётчики в одной транзакции; ручные несогласованные записи не являются поддерживаемым способом учёта.

Текущая неделя вычисляется относительно сохранённого якоря. Если якорь есть, но после простоя ещё нет строки окна, Window содержит актуальные границы, PeriodID=nil, used=0. Незавершённые удержания сохраняются. Это внутреннее различение вычисленного и сохранённого окна; при подключении HTTP нужно явно уточнить представление id такого окна в контракте, не создавать его через GET. При отсутствии якоря Window=nil.

## Расчёт

Для каждой записи сотрудника, включая бывших сотрудников с расходом/резервом, обязательство — max(Q,S+R). Служебное обязательство — max(Qservice,Sservice+Rservice). Их сумма — Committed. Allocated — сумма действующих Q + Qservice, без подмены обязательствами.

- Available=max(0,B−Used−Reserved): сколько доступно для новых вызовов при одновременной проверке личных квот.
- Unallocated=max(0,B−Committed): сколько можно дополнительно распределить.
- Overcommitted=max(0,Committed−B).
- Service.Available=max(0,Qservice−Service.Used−Service.Reserved).
- Процент — floor(100×Available/B), при B=0 отсутствует. Умножение считается целочисленно через big.Int, без overflow/float.

Отдельные SQL-суммы считаются в NUMERIC и приводятся к BIGINT с проверкой PostgreSQL; переполнение возвращает ошибку, а не частичный/обрезанный баланс. Сложение allocated и вычисления остатков защищены от int64 overflow. Реальный расход выше текущего лимита сохраняется, остаток ограничивается нулём.

Capabilities: настройки компании и службы — платформе; личные квоты — при настроенной и активной компании. Это описание полномочий будущих write-endpoint, не разрешение обойти их проверку бюджета.
