> Изменение 20.10.2026: отдельная служебная квота отменена. Актуальные правила и совместимость: [Фоновый расход из общего бюджета](ai-background-shared-budget.md). Указания Qservice ниже относятся к предыдущей версии.

Миграция: `20261020100100_ai_budget_settings.sql`.

Спецификации находятся в репозитории фронтенда: `docs/ai-budget-period-rules.md`, `docs/ai-credit-calculation-spec.md`, `docs/ai-budget-api-contract.md`.

## Таблицы

- `organization_ai_budgets`: одна настройка на компанию, B/Hmax/Qservice в целых микрокредитах, revision. Отсутствие строки означает ненастроенный бюджет; существующим компаниям миграция ничего не выдаёт. Qservice по умолчанию 0.
- `organization_ai_user_quotas`: составной ключ `(organization_id,user_id)`, Q/H в микрокредитах, revision. Обе суммы заданы вместе либо обе NULL. NULL/NULL — освобождённое назначение, сохранённое для монотонности версии. Явные нули — настроенный запрет, не unlimited.

Все настраиваемые суммы ограничены диапазоном 0–1000000000000000 включительно. Внешние ключи требуют существования компании, её бюджета и пользователя. Удаление referenced-компании/пользователя/бюджета запрещено RESTRICT, а не каскадно стирает назначения. Мягкое удаление пользователя поддерживается.

Перед ненулевым или нулевым назначением проверяется текущая принадлежность пользователя компании и отсутствие deleted_at. Пользователь блокируется FOR SHARE на время проверки, чтобы перевод не мог одновременно оставить действующее чужое назначение. При переводе/мягком удалении триггер освобождает Q/H прежней компании, но сохраняет строку и увеличивает её версию. Обычная блокировка is_active не освобождает квоту. Исторические NULL-записи не дают права использовать ИИ.

## Версии

Первое создание — revision=1 (виртуальное отсутствие записи API представляет как 0). Версия автоматически увеличивается БД только при реальном изменении сумм. Повтор одинаковых значений версию не меняет. Прямое изменение revision и перенос ключа строки запрещены. Сервис не должен выполнять `SET revision=revision+1`: он проверяет ожидаемую версию в WHERE/транзакции, а новую получает через RETURNING. Переполнение версии завершает изменение ошибкой.

Пример будущего repository UPDATE:

```sql
UPDATE organization_ai_user_quotas
SET weekly_quota_microcredits = $3, five_hour_limit_microcredits = $4
WHERE organization_id = $1 AND user_id = $2 AND revision = $5
RETURNING revision;
```

Для API с проверкой company_revision дополнительно блокировать и проверять строку бюджета в той же транзакции. Проверка revision не заменяет проверку полномочий/сумм/принадлежности.

## Границы этой задачи

Нет API, начисления кредитов, периодов, расхода, резервов или пользовательского доступа к таблицам. Проверки B против суммы обязательств, H/Hmax при назначении, Qservice против B, ролей и атомарного административного аудита добавляются сервисом следующих задач. Здесь намеренно нет статического CHECK H≤Q: утверждённые правила разрешают снижение Q ниже сохранённого H. Аналогично B=0 допускает сохранённые выделения. Нельзя включать пользовательские записи в эти таблицы до реализации административных проверок.

Триггер освобождения — минимальная гарантия принадлежности настроек. Полный сценарий перевода с расходом/резервами и аудитом относится к дальнейшей задаче жизненного цикла. Следующим таблицам журнала следует ссылаться на сохранённые настройки без каскадного удаления. Прямой DELETE назначений не должен использоваться приложением: он уничтожает сохранённую версию.

## Проверки

```powershell
# Только отдельная disposable БД; URL задаётся вне документа.
go test ./db/migrations -run TestAIBudgetSettingsMigration -count=1 -v
```

Тест читает `TEST_MESSENGER_DATABASE_URL`, создаёт уникальную схему, минимальные родительские таблицы и применяет сам файл миграции через Goose. Проверяет ограничения, defaults, принадлежность, версии, перевод/возврат, мягкое удаление, блокировку, rollback/reapply. После теста схема удаляется. Без переменной тест явно пропускается.

Проверено 16 октября 2026 года: `go test ./db/migrations -count=1 -v` прошёл на отдельном временном PostgreSQL 16, включая конкурентное назначение во время перевода, Up/Down/reapply. Экземпляр после проверки остановлен; production-БД не использовалась. Тест использует минимальные users/organizations и не проверяет взаимодействие со всеми существующими триггерами полного production-набора миграций. API и суммарное распределение ещё не реализованы и этим тестом не проверяются.

Down удаляет новые таблицы/триггеры, не меняя исходные users/organizations. После появления реальных настроек откат уничтожит именно эти настройки; не выполнять его на production как обычную проверку. Миграцию Up применять штатным процессом обновления бэкенда. Обновления фронтенда для этой задачи не требуется; ограничение ИИ пока не реализовано.
