# Периоды учёта ИИ: миграция задачи 06

Актуальное правило с 2026-10-22: новое пятичасовое окно открывается первым принятым запросом после истечения предыдущего, без привязки к постоянной сетке. Старые резервы остаются в исходном пятичасовом окне и в недельном финансовом учёте. Подробности и миграция: [контракт лимитов](ai-user-limits-contract.md#пятичасовое-окно-после-простоя).

Миграция `20261020100200_ai_accounting_periods.sql` применяется после `20261020100100_ai_budget_settings.sql`. Контракты и утверждённые правила находятся в репозитории фронтенда в `docs/ai-budget-period-rules.md`, `docs/ai-credit-calculation-spec.md`, `docs/ai-budget-api-contract.md`.

## Структура

| Таблица | Назначение / ключ |
| --- | --- |
| `organization_ai_weekly_anchors` | Один неизменяемый якорь на компанию, FK к настроенному бюджету |
| `user_ai_five_hour_anchors` | Один неизменяемый якорь на userID, независимо от компании |
| `organization_ai_weekly_periods` | UUID периода, компания, якорь, starts_at/ends_at, общие счётчики компании |
| `organization_ai_user_weekly_usage` | Счётчики сотрудника: PK (organization_id, period_id, user_id), FK к периоду компании и сохранённой записи назначения |
| `organization_ai_service_weekly_usage` | Счётчики Qservice: PK (organization_id, period_id), FK к периоду компании |
| `user_ai_five_hour_periods` | UUID персонального периода, userID, якорь, starts_at/ends_at, пятичасовые счётчики |

Миграция не создаёт ни якорей, ни периодов для существующих пользователей. Позднее первый успешно принятый резерв создаст якорь и нужный период в одной транзакции. GET не должен открывать якорь. После простоя разрешено пропустить неиспользованные окна, сохранив постоянную сетку.

Якоря и границы — конечные TIMESTAMPTZ. Неделя строго 604800 секунд, пятичасовое окно — 18000 секунд. CHECK проверяет точную длительность и смещение начала от якоря на целое число окон без float. starts_at не предшествует anchor_at. Уникальность `(organization_id,starts_at)` / `(user_id,starts_at)` вместе с одним якорем и фиксированной длительностью запрещает дублирующиеся и пересекающиеся окна. Исключающее GiST-ограничение и новые расширения не требуются.

Периоды полуоткрытые: `starts_at <= момент AND момент < ends_at`. Ровно на ends_at операция принадлежит следующему окну. TIMESTAMPTZ хранит моменты времени независимо от локального отображения; длительность задаётся часами, не календарными днями и не локальной неделей.

## Счётчики и инварианты

У всех четырёх таблиц периодов/расхода:

- `used_microcredits` — подтверждённый расход данного периода;
- `reserved_microcredits` — всё удержание, включая перенесённые обязательства;
- `carried_reserved_microcredits` — часть reserved из предыдущих периодов, не дополнительное слагаемое.

Все значения BIGINT NOT NULL DEFAULT 0, неотрицательные; carried ≤ reserved. Сумма used+reserved не превышает signed int64, CHECK вычисляет сумму через NUMERIC без переполнения. Верхнего ограничения по текущей квоте нет: подтверждённый перерасход нельзя отбрасывать. Сервис должен использовать проверенную арифметику до записи и сообщать об overflow, а не обрезать числа.

FK по `(organization_id,period_id)` не позволяет отнести личные или служебные счётчики к неделе чужой компании. FK к сохранённому назначению сотрудника намеренно не проверяет его текущую принадлежность: после перевода старый расход должен остаться у старой компании. Право новой операции будет проверяться сервисом резервирования. Персональные пятичасовые периоды вообще не имеют organization_id и сохраняются при переводе.

Триггеры UPDATE запрещают изменение владельца, UUID, якоря и границ уже созданных записей. Изменять можно только счётчики. Учёт не увеличивает revision настроек компании и пользователя. FK используют RESTRICT, без каскадного уничтожения истории. Приложение не должно удалять якоря/периоды для сброса ограничений; неизменяемость UPDATE не является запретом привилегированного прямого DELETE пустых записей.

Индексы: PK по UUID периодов; уникальные индексы владельца и starts_at для поиска актуального/соседнего окна; составной уникальный ключ company/id для безопасных FK; PK недельного расхода для списка сотрудников данного периода; дополнительный индекс `(user_id,organization_id,period_id)` для истории пользователя и проверок FK назначения. Точное равенство идентификаторов позволяет читать уже привязанные к резерву периоды без диапазонного поиска.

## Повторное создание

Будущий repository может создавать окно идемпотентно:

```sql
INSERT INTO organization_ai_weekly_periods
    (organization_id, anchor_at, starts_at, ends_at)
VALUES ($1, $2, $3, $4)
ON CONFLICT (organization_id, starts_at) DO NOTHING;
```

Затем отдельный SELECT получает существующий UUID и счётчики. Не применять `DO UPDATE SET used_microcredits=0`: повтор не должен сбрасывать расход. Создание якоря и открытие первого окна должны входить в ту же транзакцию, что и успешный резерв; при отказе всё откатывается. SQL выше не заменяет этот сценарий и проверку доступа.

## Что добавляется следующими задачами

Здесь нет журнала попыток/резервов, функции открытия окон, блокировок лимитов и HTTP API. Общие счётчики компании и детализация сотрудник/служба должны обновляться согласованно в одной транзакции будущего сервиса; БД этой миграции не сверяет их суммы автоматически.

Перенос старого незавершённого резерва в удержание нового периода также ещё не реализован: предусмотрены только поля хранения. Журнал задачи 07 должен сохранять исходные окна попытки, а сервис — транзакционно поддерживать carried и не допускать повторного списания. Снижение квот не меняет эти периоды. Режим наблюдения и включение ограничений не задаются этой миграцией.

## Проверка

`go test ./db/migrations -count=1 -v` при заданном `TEST_MESSENGER_DATABASE_URL` запускает тесты задач 05 и 06 в уникальных схемах отдельной disposable БД. Тест 06 применяет оба настоящих SQL-файла через Goose, использует минимальные родительские users/organizations.

Проверены 16 октября 2026 года на отдельном временном PostgreSQL 16:

- отсутствие автоматически открытых окон;
- создание, duplicate error и 8 одновременных идемпотентных созданий;
- точная правая граница, пропуск окон, микросекундные смещения, неправильная длительность, начало до якоря, бесконечные даты;
- работа через смену DST в timezone America/New_York: неделя остаётся 168 часами;
- изоляция компаний, неизменяемость владельца/границ;
- defaults, null/negative, carried > reserved, максимум int64 и переполнение суммы;
- сохранение исторического недельного и личного пятичасового расхода при переводе;
- неизменность revision настроек от изменения счётчиков;
- Down только новой миграции сохраняет настройки, Up после Down и повторный Up проходят.

Результат: все тесты пакета прошли, временный сервер остановлен. Полный исторический production-набор миграций и будущий сервис списания не проверялись. Для обновления бэкенда потребуется штатно применить новую миграцию; фронтенд и окружение приложения для этой задачи менять не нужно. Down удаляет данные новых таблиц; использовать его для проверки только на disposable БД. Commit, push и развёртывание не выполнялись.
