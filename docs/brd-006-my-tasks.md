# BRD-006 — Мои задачи и уведомления

`GET /api/v1/kanban/tasks/my` возвращает задачи, назначенные авторизованному
пользователю, по всем доступным ему доскам. Авторство само по себе не включает
задачу в список. Удалённые задачи/доски и доски без доступа исключаются.
Завершённые задачи входят в общий список.

Фильтры: `board_id`, `project_id` (UUID), `status` (точный статус или ключ колонки),
`priority` (`low/medium/high/critical`), `overdue=true`, `limit` (1–100,
по умолчанию 50), `offset` (от 0). Просроченные — незавершённые задачи с прошедшим сроком.
Порядок: ближайший срок первым, без срока в конце, затем дата создания и ID.

```json
{"tasks": [], "limit": 50, "offset": 0, "has_more": false}
```

Список содержит поля карточки и `assignee_ids`; вложения и метки загружаются
через существующий `GET /api/v1/kanban/tasks/:id`. Старые `my-todo`, `my-by-status`
и `my-summary-by-board` остаются доступными.

Назначение нового исполнителя при создании/редактировании уже отправляет
`kanban_task_assigned`; повторное сохранение того же списка исполнителей его не
повторяет. По существующему правилу автор действия не уведомляется о собственном
назначении. Теперь этот тип включён в стандартный список email-уведомлений.

Новый фоновый обработчик запускается вместе с API и раз в минуту обрабатывает
до 200 получателей:

- `kanban_task_due_soon` — срок наступает в течение 24 часов;
- `kanban_task_overdue` — срок уже наступил.

Получатели — текущие исполнители с доступом к доске. Завершённые, отменённые,
удалённые задачи, удалённые доски и задачи без срока не обрабатываются.
В metadata передаются `task_id`, `board_id`, `task_key`, `due_at` и `action`.
Напоминания сохраняются в общих уведомлениях и передаются в WS, push и email.

Миграция `20260924000200_kanban_deadline_deliveries.sql` обязательна до запуска.
Она хранит отметки по задаче, исполнителю, сроку и типу события. Несколько экземпляров
API конкурируют за временную блокировку; успешный проход не повторяется. Смена срока
создаёт новый ключ напоминания. Ошибки сохранения уведомления повторяются, зависшая
блокировка освобождается через 2 минуты. При аварии между созданием уведомления и
отметкой возможен повтор (доставка не exactly-once).

Для реальных push нужны Firebase credentials и зарегистрированное устройство.
Для email нужны `MAIL_ENABLED=true`, SMTP и корректный email получателя.
Если `MAIL_NOTIFICATION_TYPES` задан явно, добавьте `kanban_task_assigned`,
`kanban_task_due_soon`, `kanban_task_overdue`, сохранив остальные нужные типы.
Явные настройки доставки не переопределяются кодом.

Используется существующий общий транспорт уведомлений: push ставится в очередь,
email отправляется асинхронно. Отметка обработки означает принятие общим сервисом,
а не подтверждение получения устройством/почтовым ящиком. Ошибки SMTP/FCM логируются;
этот обработчик не повторяет отдельно отправку по каждому каналу.

Проверка БД: `TEST_MESSENGER_DATABASE_URL=... go test ./internal/repository -run TestKanbanPersonalIntegration -v`
(только отдельная тестовая БД). Тест создаёт и удаляет изолированную схему.
