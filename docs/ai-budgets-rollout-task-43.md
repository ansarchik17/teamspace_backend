# Инструкция обновления и включения ИИ-бюджетов

> Изменение 20.10.2026: отдельная служебная квота отменена. Актуальные правила и совместимость: [Фоновый расход из общего бюджета](ai-background-shared-budget.md). Указания Qservice ниже относятся к предыдущей версии.

Инструкция описывает текущий код ветки `ai-tokens`. Она не подтверждает готовность production-среды: до запуска владелец среды должен проверить резервные копии, доступность миграционной команды, секреты, версии сервисов и фактические ответы провайдеров. Здесь приведены только обнаруженные в репозитории команды, настройки и HTTP-операции. Развёртывание и изменение production-настроек этой задачей не выполнялись.

## 1. Перед обновлением

1. Зафиксируйте версии backend, миграционного образа, фоновых процессов и frontend. Backend и мигратор должны содержать один и тот же набор SQL-файлов. Сверьте текущую версию схемы по `goose_db_version` и проверьте полный список ожидающих миграций. Мигратор включает все ожидающие миграции каталога, а не только таблицы ИИ.
2. Проверьте, что целевая база — именно нужная компания/среда, доступно место, соединение устойчиво, а учётная запись мигратора имеет необходимые DDL-права. Тестовые миграции выполняйте только на отдельной PostgreSQL-БД.
3. Сделайте и проверьте восстановление резервной копии PostgreSQL по процедуре оператора среды до применения миграций. Репозиторий не содержит проверенной production-команды резервного копирования или восстановления; используйте утверждённый DBA способ, включающий данные и журнал ИИ.
4. Согласуйте окно обновления и совместимость образов. Схема расширяется миграциями до выкладки нового API. Не запускайте новый код против старой схемы. Во время частичной выкладки API все экземпляры должны получить одинаковые `AI_ACCOUNTING_ENABLED` и `AI_ENFORCEMENT_MODE`; смешанный режим приведёт к разному решению о допуске.
5. Сверьте переменные мигратора: `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_SSL_MODE`, `MIGRATIONS_DIR`, `RUN_DB_MIGRATIONS`. Пароль не помещайте в командную строку, shell history, тикеты или журнал выкладки.

## 2. Миграции и порядок выкладки

AI-схема в репозитории формируется последовательностью миграций:

Перед первым production-релизом версии AI-миграций перенесены в диапазон
`20261020100100`–`20261020101000`. Версия `20261019000100` уже выпущена
как `20261019000100_iform_operation_receipts.sql`; этот файл сохранён
без изменений из main. Старые AI-версии от 16–20 октября не применять:
они пересекались с выпущенной миграцией и попадали ниже текущего номера БД.
Мигратор сохраняет запрет неожиданных пропусков; расширять allowlist ради AI
не требуется. Не менять вручную `goose_db_version` и не откатывать iForm.

Если тестовая среда уже применяла старые AI-версии, этот порядок не является
её автоматической конвертацией. Для одноразовых тестов создать новую БД;
для среды с нужными данными сначала сохранить копию и разработать отдельный
проверенный переход по фактической схеме. Не удалять журнал расхода.

`scripts/test-ai-release.ps1` проверяет обновление с полной схемы до
выпущенной iForm-миграции, сохранность существующей квитанции iForm,
применение десяти AI-миграций, повторный запуск без изменения журнала
и сохранение отказа на неожиданный пропуск. Это синтетическая репетиция,
не замена проверке на восстановленной копии production-БД.

Это не полный список миграций приложения. Запускайте штатный миграционный процесс для всего каталога, проверив порядок и статус остальных pending-файлов. В коде есть отдельный мигратор `cmd/migrate`: в контейнере каталог по умолчанию `/app/db/migrations`, локально передайте `MIGRATIONS_DIR=db/migrations`; он применяет ожидающие миграции и проверяет допустимые пропуски старых миграций. В Makefile также есть `make migrate-status` и `make migrate-up`, но их DSN строится из переменных Makefile/`.env`, а `migrate-status` жёстко использует локальную тестовую БД `messenger`; не используйте эту цель для проверки production.

Рекомендуемый порядок:

1. Сначала сделать snapshot/backup и проверить миграционный план на копии production-схемы.
2. Запустить один миграционный job с правильными `POSTGRES_*` и `MIGRATIONS_DIR`. Проверить код завершения и таблицу `goose_db_version`; не считать запуск успешным только по старту контейнера. В `cmd/migrate` значение `RUN_DB_MIGRATIONS` по умолчанию включает миграции; `false`, `0`, `no` или `off` отключают их.
3. После успешных миграций обновить API-экземпляры. Не запускать параллельные миграционные jobs. Сохранить общий серверный режим на всех экземплярах.
4. Обновить отдельный AI document worker, если он развёрнут: текущий backend запускает worker-only режим через `AI_DOCUMENT_WORKER_ONLY=true`. Это отдельная роль процесса обработки документов, не отдельный процесс сверки резервов.
5. Обновить frontend совместимой версией после API. Frontend не управляет режимом блокировок. Операции администрации должны быть доступны через backend независимо от того, показывается ли новый интерфейс.

Сверка резервов сейчас запускается как фоновая горутина внутри API при `AI_RECONCILIATION_ENABLED=true`, а не как отдельная команда/бинарник. Если API масштабирован, worker запускается в каждом экземпляре; распределённые leases защищают обработку от одновременного захвата одной операции.

## 3. Коэффициенты и проверка usage

Текущая политика расчёта задаётся кодом `internal/domain/ai_credits.go`: версия `credits-v1`, суммы хранятся целыми микрокредитами (1 кредит = 1 000 000 микрокредитов). Коэффициенты не являются env-настройками. Не меняйте их вручную в БД или конфигурации. Изменение шкалы/моделей требует изменения кода и версии политики; новые операции должны записывать свою версию и снимок коэффициентов, уже учтённые операции не пересчитываются.

До включения блокировок проверьте для каждого реально используемого провайдера/endpoint/model, что серверный usage-адаптер передаёт подтверждённые входные и выходные токены, а при наличии — cached input и reasoning output. Проверяйте реальный безопасный тестовый ответ/контракт провайдера, включая потоковый ответ, fallback и повторные попытки. Отсутствующий счётчик не равен нулю. `verified`/`derived` usage должен иметь доказуемый источник; любое иное состояние остаётся неизвестным и не тарифицируется нулём.

В `credits-v1` точное сопоставление провайдера, endpoint и model обязательно; неизвестная комбинация отклоняется как `AI_MODEL_UNPRICED`. В коде есть chat-модели Nitec и `openai-direct/gpt-4o`, а также BAAI embeddings/rerank. Для embeddings/rerank комментарий политики прямо требует подтверждённый usage-контракт до enforcement. Перед запуском составьте allowlist используемых моделей из production-конфигурации и отдельно подтвердите каждую. Неизвестная модель или неполный usage не становятся бесплатными даже в `observe`.

**Ограничение текущей реализации:** `cmd/api/main.go` создаёт worker сверки с пустым реестром lookup-адаптеров. Поэтому запущенный worker не умеет получить usage по ID запроса у внешнего провайдера; отправленные операции с неизвестным исходом направляются в ручную обработку. Значение `AI_RECONCILIATION_ENABLED=true` само по себе не означает автоматическую сверку у провайдера. Не включайте блокировки, пока неизвестные исходы не сведены к приемлемому уровню и не определена операционная ручная процедура.

## 4. Бюджет компании и квоты

Настройки задаются через существующие защищённые административные маршруты; публичный клиент не может переключать enforcement.

| Операция | Метод и путь | Полномочие |
| --- | --- | --- |
| Читать бюджет и сводку | `GET /api/v1/organizations/current/administration/ai-budget` | Директор активной компании |
| Читать бюджет выбранной компании | `GET /api/v1/platform/organizations/:organization_id/administration/ai-budget` | Платформа |
| Установить недельный бюджет компании | `PUT /api/v1/platform/organizations/:organization_id/administration/ai-budget` | Только платформа |
| Список квот сотрудников | `GET .../ai-budget/users?limit=25&offset=0` | Директор своей компании / платформа |
| Прочитать квоту сотрудника | `GET .../ai-budget/users/:user_id` | Директор своей компании / платформа |
| Установить квоту сотрудника | `PUT .../ai-budget/users/:user_id` | Директор своей компании / платформа |

Для изменения бюджета обязательны JSON-строки `weekly_budget_microcredits`, `max_five_hour_microcredits`, `service_weekly_quota_microcredits`, `revision`. Для сотрудника — `weekly_quota_microcredits`, `five_hour_limit_microcredits`, `revision`, `company_revision`. Отправляйте revision из последнего GET: конфликт версии нужно перечитать и согласовать заново, а не повторять PUT вслепую. Изменения возвращают `204`. Все денежные величины и revision — десятичные строки, значения ограничены серверной валидацией. Детали ответа см. в `docs/ai-administration-http.md`.

Сначала задайте компании недельный бюджет и максимальный личный пятичасовой лимит, затем распределите квоты сотрудникам с учётом уже использованного и зарезервированного объёма. `service_weekly_quota_microcredits` в текущем контракте задаётся платформой в той же форме бюджета; начальное значение по утверждённым правилам — 0. Распределение сотрудникам ограничивается остатком бюджета компании. Перед массовой настройкой проверьте сводку: бюджет, распределено, committed/used, резервы, доступный и нераспределённый остаток. Не используйте `0` как «наследовать»: ноль — заданное значение без доступной квоты; отсутствие настройки (`configured=false`/`null`) — отдельное состояние. В `enforced` ненастроенная компания/сотрудник не должны считаться имеющими бесплатный бюджет.

Периоды определяются серверным временем. Компания использует недельное окно, сотрудник — недельное и последовательные пятичасовые окна; окна полуоткрытые, точная граница относится к следующему периоду. Реализация и точные границы описаны в `docs/ai-accounting-periods.md`; утверждённые продуктовые правила и спецификация расчёта находятся во frontend-репозитории в `docs/ai-budget-period-rules.md` и `docs/ai-credit-calculation-spec.md`. Активные резервы переносятся через границы окон. Не удаляйте/не пересоздавайте настройки ради сброса периода.

## 5. Наблюдение и критерии готовности к блокировкам

Начальная безопасная последовательность для финансовых ограничений: `AI_ACCOUNTING_ENABLED=true`, `AI_ENFORCEMENT_MODE=observe`, `AI_RECONCILIATION_ENABLED` — по принятому плану ручной сверки (по умолчанию `false`). Проверяйте, что все API-инстансы имеют одинаковые значения. Учет и блокировки — разные переключатели: observe пропускает платную операцию мимо финансового запрета, но всё равно резервирует и записывает фактический расход. Аутентификация, доступ компании, проверка корректности/цены и rate/concurrency limiter продолжают действовать.

Перед переходом в `enforced` владелец продукта и эксплуатации должны подтвердить все пункты:

- все платные пути, реально используемые в этой версии, проходят через общий учёт; неподключённые интеграции остаются вне его покрытия;
- у каждой включаемой компании и сотрудника есть корректные бюджеты/квоты, а `0` и отсутствие настройки проверены отдельно;
- usage-адаптеры подтверждены для всех реально разрешённых моделей и категорий; неизвестные модели, incomplete usage и таймауты не теряются;
- за согласованное окно наблюдения нет необъяснимого расхождения между вызовами и журналом, ошибок фиксации/резервирования и роста unknown/stale резервов;
- проверены конкуренция нескольких API, перенос резервов через период, лимитер, интерфейс сообщений об отказе и процедура ручного разбора unknown;
- команда знает, кто согласует размер бюджета, кто меняет квоты и кто реагирует на сигналы мониторинга.

Наблюдение не тестирует отказ провайдера и не делает неизвестный исход бесплатным. Проведите пилот в отдельной среде с отдельной БД и тестовыми провайдерами. `AI_ENFORCEMENT_MODE` глобален: выборочного включения enforcement по компаниям в текущем коде нет. Бюджеты и права не являются переключателями режима. В общей среде включайте enforced только после подготовки всех обслуживаемых компаний, включая ранее ненастроенные. Публичного или административного API для переключения режима нет; режим меняется только серверной конфигурацией оператора.

## 6. Сверка, неизвестный расход и мониторинг

Фактические параметры reconciliation в `.env.example`:

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `AI_RECONCILIATION_ENABLED` | `false` | Запуск фонового worker внутри API |
| `AI_RECONCILIATION_INTERVAL` | `1m` | Период опроса |
| `AI_RECONCILIATION_STALE_AFTER` | `15m` | Возраст для попадания в обработку |
| `AI_RECONCILIATION_LEASE` | `2m` | Lease worker-claim |
| `AI_RECONCILIATION_LOOKUP_TIMEOUT` | `30s` | Таймаут lookup |
| `AI_RECONCILIATION_RETRY_DELAY` | `5m` | Пауза перед повторной попыткой |
| `AI_RECONCILIATION_BATCH_SIZE` | `25` | Размер пачки |
| `AI_RECONCILIATION_MAX_CLAIMS` | `10` | Максимум claims за цикл |

`STALE_AFTER` — только критерий обнаружения, не время жизни резерва. **Истечение TTL/порога stale не освобождает неизвестный расход и не возвращает кредиты.** Резерв остаётся удержанным, пока провайдерский расход не подтверждён и не проведён как settlement, либо достоверно подтверждено, что вызов не был отправлен. Отмена клиентом, разрыв соединения, timeout и HTTP 5xx не доказывают отсутствие расхода. Повторная сверка должна быть идемпотентна.

Для неизвестного исхода: оставьте резерв; проверьте журнал попытки/операции и безопасные метаданные провайдера; получите подтверждение провайдера через утверждённый канал; затем используйте операторскую CLI `go run ./cmd/ai-accounting resolve` с точным именем БД и файлом доказательства. По умолчанию это preview, применение требует `--apply`. Lookup-адаптеры по-прежнему отсутствуют: CLI не выдумывает результат и не вызывает провайдера. Полные команды, формат подтверждения, проверка готовности `preflight`, разовый sweep и тест восстановления описаны в [ai-production-readiness.md](ai-production-readiness.md). Не исправляйте статус прямым SQL и не удаляйте запись.

`METRICS_ENABLED=true` включает уже защищённый существующей авторизацией `/metrics`, включая глобальные DB gauges. Читайте таблицу метрик и примеры alert-условий в `docs/ai-accounting-metrics-task-41.md`. Gauge из нескольких API-инстансов агрегируется `max`, event counters суммируются по инстансам. В метки не должны попадать user/company/operation IDs, модель, URL, тексты, provider request ID, ключи и тексты ошибок. Мониторьте unknown/stale/unresolved reservations, ошибки фиксации/резервирования, ошибки и manual-результаты сверки, частоту quota denial и успешность DB sampler. Внешняя система мониторинга в рамках этой реализации не подключена.

## 7. Последовательное включение ограничений и проверки

1. Выкатите schema и API с `AI_ACCOUNTING_ENABLED=true`, `AI_ENFORCEMENT_MODE=observe` на всех экземплярах. Не включайте enforced на одном экземпляре за другим.
2. Убедитесь по метрикам и журналу, что резерв → каждый provider attempt → settlement сохраняются раздельно, повторы не создают повторное списание, а сбой сохранения ответа не теряет расход.
3. Настройте бюджет и квоты на тестовой/пилотной компании административными маршрутами. Проверьте чтение сводки и список сотрудников под директором и платформой, запрет чужой компании, revision-конфликт, ноль, ненастроенные значения и активный резерв.
4. В отдельной пилотной среде включите `AI_ENFORCEMENT_MODE=enforced` на всех API одновременно, наблюдая ошибки лимитов, provider errors и латентность. Пользовательский отказ по лимиту должен иметь безопасную причину и время следующего доступа, когда оно вычислимо.
5. После успешного пилота подготовьте все компании общей среды, затем согласованно включите enforced на всех её API. Это затронет все компании одновременно; неподготовленные компании будут получать финансовые отказы. Сравните журнал и usage провайдера, текущие остатки и метрики. Пилот на части компаний общей среды требует отдельной реализации серверной политики выбора компаний и не поддерживается текущим переключателем.
6. Проверьте `/health` и `/ready`, если они включены в конкретной конфигурации сервера; запросите `/metrics` аутентифицированным способом и выполните административные GET/PUT в пилотной компании. Наличие маршрута само по себе не подтверждает корректную настройку ролей среды.

Frontend выкладывайте только с совместимым API: перед включением пользовательского UI проверьте `GET /api/v1/ai/limits`, потому что он возвращает личные окна и enforcement-режим. Административные маршруты выше уже существуют в backend; наличие или актуальность фронтенд-форм проверяется отдельно по выпускаемому frontend build.

## 8. Отключение финансовых блокировок

Для временного снятия финансовых блокировок задайте на всех API `AI_ENFORCEMENT_MODE=observe`, оставив `AI_ACCOUNTING_ENABLED=true`. Это сохраняет авторизацию, rate/concurrency limit, проверку модели/usage, резервирование, фактическое списание, журнал и наблюдения, но не отклоняет запрос исключительно из-за финансового лимита. Не отключайте worker сверки и мониторинг только потому, что выключены блокировки.

`AI_ACCOUNTING_ENABLED=false` — другой, аварийный режим: новый платный вызов и `/api/v1/ai/limits` вернут `503 AI_ACCOUNTING_UNAVAILABLE`; используйте его лишь по отдельному операционному решению. Завершение и reconciliation уже открытых операций не должны трактоваться как возврат резерва.

При rollback приложения используйте предыдущий совместимый API-образ поверх уже расширенной схемы только после проверки совместимости. **Откат приложения не должен удалять журнал или применённые данные учёта.** Не выполняйте `make migrate-down`, DROP/TRUNCATE таблиц учёта, сброс периодов или ручной возврат unknown-резервов. Миграции append-only для целей этого rollout; восстановление backup — отдельная аварийная процедура с потерей более новых записей и требует оценки владельцем БД.

## 9. Частичное обновление и сбои

**Миграция завершилась ошибкой.** Остановите продвижение API/worker/frontend, сохраните логи мигратора без секретов, проверьте статус Goose и состояние схемы на копии. Не запускайте `down` автоматически и не удаляйте частично созданные объекты вручную. Если транзакция миграции была откатана, устраните причину и повторите штатный `up` после проверки; если статус/схема расходятся — привлеките DBA и восстановите согласованное состояние по backup-плану.

**Выкатана только часть API.** Не меняйте режим на лету и не начинайте массовую настройку лимитов. Остановите дальнейший rollout, выровняйте конфигурацию и версию всех экземпляров; если необходимо продолжать обслуживание, верните совместимый код на все экземпляры, сохранив новые таблицы и данные журнала.

**Frontend обновлён, API ещё нет.** Откатите/удержите frontend на совместимой версии до обновления API. Не считайте доступность интерфейса доказательством наличия серверных маршрутов.

**Провайдер недоступен или timeout.** Возвращайте безопасную ошибку пользователю, но оставляйте исход попытки unknown, если отправка могла состояться. Не освобождайте резерв только по TTL. Когда провайдер восстановится, сверяйте подтверждённые результаты; при отсутствии lookup-поддержки направляйте операцию на ручную проверку.

**Пошёл рост отказов или unknown.** Снимите финансовые блокировки переключением всех API в observe; сохраните `AI_ACCOUNTING_ENABLED=true`, журнал и метрики. Не пытайтесь скрыть проблему отключением сборщика или чисткой таблиц. Разберите причины, исправьте конфигурацию/адаптеры и возвращайтесь в enforced после повторной проверки пилотом.

## Требует ручной проверки перед production

- Утверждённый способ backup/restore и время восстановления; соответствие production-версии миграций и полный план всех pending-миграций.
- Конкретные образы, orchestration manifests, health/readiness routes и порядок rollout в инфраструктуре компании: этот репозиторий не определяет production deployment platform.
- Фактический allowlist моделей, тарифные веса и usage-ответы провайдера на production account; наличие адаптера в коде не подтверждает покрытие каждого provider edge.
- Получение подтверждений провайдера и назначение оператора ручной CLI: production lookup-адаптеры не зарегистрированы; неизвестный результат без доказательств остаётся удержанным.
- Конкретные суммы бюджета, пилотные компании, владельцы квот, длительность окна наблюдения, пороги алертов и канал реакции.
- Доступ к `/metrics`, аутентификация администраторов, доступность миграционного DB пользователя и согласованность env во всех API/processes.
- Наличие/готовность фронтенд-экранов в релизном frontend: документирован контракт, но production сборка/интеграция здесь не развёртывалась.

Эта инструкция проверена по коду ветки и документации, но не запускалась на production или production-копии. Никакие production-настройки не менялись.
