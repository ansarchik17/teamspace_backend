# Автоматический кадровый документ ЭДО

Реализация задачи от 22.10.2026: после согласований найма iForm создаёт заполненный кадровый PDF и документ ЭДО с выбранным регистратором и маршрутом подписи. Выбор шаблона выполняется **по ID утверждённого шаблона iForm текущей компании**. Это существующий каталог `/api/v1/templates`, а не каталог НПА ЭДО. Текст приказа и юридические реквизиты компания утверждает сама.

## Однократная настройка компании

1. Администратор добавляет HTML-шаблон через существующий `POST /api/v1/templates`, затем утверждает через `POST /api/v1/templates/{id}/approve`. Для кадрового оформления требуется `approved=true`, `demo=false`. В демо-окружении тестовые шаблоны остаются демо; их нельзя выдавать за утверждённые кадровые документы.
2. В конструкторе iForm → «Интеграции» → шаг создания кадрового документа выбирается шаблон из каталога. Сохраняются его ID и версия. Конкретный производственный ID пользователем пока не передан и в исходники не подставлен.
3. В том же блоке выбираются регистратор и подписант компании, способ подписи и завершение оформления после последней подписи. Можно использовать поле сотрудника из заявки вместо константы. Компания с одним сотрудником не получает исключение из запрета самоподписи.
4. Сохраняются настройки подразделения и срока из заявки: `recipient_department_id ← targetDepartment`, `due_date ← startDate`. Дополнительные поддерживаемые реквизиты, например `document_type_id`, задаются существующими типизированными `inputs`; ЭДО проверяет код по своему справочнику. Регистрационный номер и дата регистрации по-прежнему назначаются при регистрации в ЭДО, а не придумываются генератором PDF.
5. Согласование руководителя и директора уже проходит в iForm. В кадровой основе маршрут ЭДО содержит подпись. Этап `approval` в ЭДО допустим только при `repeatHiringApproval=true`, установленном по отдельному требованию компании. Работы IT остаются в SD.
6. Настраиваются оставшиеся параметры SD и роли, очищаются действительно решённые `unresolvedItems`, проверяется и публикуется **новая версия**. Старые заявки сохраняют старую неизменяемую версию.

Пример настроек (ID и сотрудники ниже — только иллюстрация, не реальные значения компании):

```json
{
  "operation": "workspace.odo.create",
  "odoDocument": {
    "templateId": "approved-template-id",
    "templateVersion": 1,
    "repeatHiringApproval": false
  },
  "inputs": {
    "kind": {"value": "outgoing"},
    "title": {"parts": [{"value": "Приём на работу: "}, {"field": "lastName"}, {"value": " "}, {"field": "firstName"}]},
    "recipient_department_id": {"field": "targetDepartment"},
    "registrar_id": {"value": "workspace:10"},
    "due_date": {"field": "startDate"},
    "is_controlled": {"value": true}
  },
  "odoRoute": {"stages": [{
    "id": "hrSignature", "kind": "signing", "name": "Подписать кадровый документ",
    "signer_id": {"value": "workspace:11"}, "signing_method": "eds",
    "completion_status": "completed"
  }]}
}
```

## Заполнение и права

Метки шаблона соответствуют ID полей: `{{firstName}}`, `{{lastName}}`, `{{iin}}`, `{{position}}`, `{{email}}`, `{{targetDepartment}}`, `{{manager}}`, `{{startDate}}`; доступны `{{requestId}}` и `{{organization}}`. Для подразделения и сотрудника подставляются названия из справочника текущей компании. Передача в сам ЭДО использует проверяемые идентификаторы. Значения экранируются как текст; внешние ресурсы и исполняемый HTML запрещены. Неизвестные метки блокируют публикацию, незаполненные значения останавливают подготовку до внешнего создания. Основной PDF ограничен 1 МБ. Используется существующий PDF-движок и MinIO iForm; новых зависимостей нет.

Перед созданием ЭДО заново загружает актуальных сотрудников и их права Workspace, проверяет компанию и подразделение. `workspace:<id>` разрешается в действующий профиль ЭДО, включая профиль, материализованный до первого входа пользователя. Регистратор должен быть активным, иметь чтение документа, `document.register` и права запуска настроенных этапов, для подписи — `document.send_to_signing`. Для завершения после подписи нужно `assignment.close` либо `assignment.complete` по существующей модели ЭДО. Подписанту нужны `signature.sign`, `signature.read`, чтение документа и `attachment.download`; автор не может быть своим подписантом. HR-создателю нужны актуальные права iForm HR и ЭДО `document.create`, чтение, `attachment.upload` и `attachment.download`. Платформенная роль/название должности не подменяет эти права.

HR получает черновик с основным PDF, реквизитами, назначенным регистратором и маршрутом. Регистрация и сама подпись остаются действиями ответственных. Перед их запуском существующие проверки прав выполняются снова. После успешной **последней** подписи с явным `completion_status=completed` документ переводится `signed → completed` от текущего регистратора с повторной проверкой его прав. Одновременно завершается маршрут; только затем iForm разрешает создание сотрудника.

## Частичные сбои и совместимость

При потере ответа iForm повторно отправляет тот же файл из своего хранилища, с теми же SHA-256 и ключом операции. ЭДО сериализует сохранение маршрута и файла, восстанавливает недостающие метаданные и не добавляет второй основной файл. Файл, изменённый вручную, повтор не перезаписывает. После регистрации повтор создания не сбрасывает действующий маршрут.

Workspace и iForm требуют явных подтверждений `route_confirmed`, `main_file_confirmed` и совпадения SHA-256. Старый сервис, проигнорировавший новые поля, не считается успешным. Если подпись сохранена, а завершение не удалось, ожидание iForm вызывает узкий идемпотентный `POST /api/v1/documents/{id}/workflow-plan/finish`. Этот запрос доступен только автору или регистратору документа, проверяет сохранённую последнюю подпись/политику и текущие права регистратора. Он не подписывает, не регистрирует и не редактирует маршрут. У ограниченного токена iForm добавлен только этот адрес; прочие операции записи закрыты. Чтение документа остаётся без побочных действий.

Маршруты без явного `completion_status` не получают автоматическое завершение. Generic-процессы без `odoDocument` сохраняют создание обычной карточки. Новые публикации кадровой основы требуют шаблон, регистратора и настроенный маршрут; незаполненная основа не публикуется.

## Выпуск и проверка

Порядок обновления: **ЭДО backend → Workspace backend → iForm backend и frontend → настройка компании → новая версия процесса**. Обновление front Workspace не требуется. Новых миграций и переменных окружения нет: используется JSON существующей последовательности маршрута, действующий каталог шаблонов и хранилище iForm. Production-настройки, публикация компании, коммиты, push и развёртывание в этой задаче не выполнялись.

Локально проверены Go-пакеты Workspace и ЭДО, локализация Workspace, 29 Java-тестов iForm с PostgreSQL/Flowable и подставным Workspace, `npx tsc -b`, два браузерных сценария Edge на широком экране и ширине 390 px. Проверены недоступный/чужой участник, самоподпись, потеря ответа, единственный основной файл, отсутствие повторного согласования по умолчанию, отзыв права регистратора и восстановление частичного завершения. Использовалась отдельная одноразовая PostgreSQL. Реальная ЭЦП, MinIO компании и производственный маршрут ЭДО/SD сквозным запуском не проверялись.
