# Общая модель доступа Workspace и приложений

Workspace хранит назначения должностей и наборы прав для ЭДО (`odo`), SenimDesk (`sd`) и iForm (`iform`). Приложение проверяет доступ к своим объектам и допустимость действия в текущем состоянии процесса.

Статус: задача 1 фиксирует целевой контракт; задача 2 добавляет [сверку каталога с API и UI трёх сервисов](access-permission-catalog.md). Раздел «Расхождения реализации» перечисляет ещё не выполненные исправления. Этот документ сам по себе не меняет рабочие права, API, миграции и настройки серверов.

Growy использует отдельные `growy-role-mappings`. Настройки других модулей, квоты и доступ к отдельным объектам Workspace не становятся правами должности автоматически. Их подключение требует проверки собственного контракта.

## 1. Сущности и полномочия

| Понятие | Источник | Полномочия |
| --- | --- | --- |
| Администратор платформы | Актуальные `users.role = 'admin'`, `is_active`, `deleted_at` | Администрирование платформы и выбранной компании через platform API |
| Владелец компании | `organizations.owner_id` и активная учётная запись | Управление своей компанией, структурой, должностями и правами |
| Сотрудник | Подтверждённая идентичность и текущее членство | Доступ в пределах своей компании и приложения |
| Должность | `organization_access_positions` | Общий набор возможностей назначенных сотрудников компании |
| Назначение | `organization_access_assignments` | Одна должность сотрудника, независимые наборы `odo`, `sd`, `iform` |
| Подразделение и руководитель | Структура компании | Область данных и подбор участников, без самостоятельной выдачи прав действий |
| Участник процесса | Маршрут, поручение, назначенный подписант | Действие над конкретным объектом при наличии нужного разрешения |

Названия «админ», «директор» и «руководитель» не присваивают системную роль. `manager` не даёт права изменять назначения и политики компании. По решению пользователя от 27.10.2026 действующий владелец автоматически получает все реализованные рабочие права сервисов своей компании. Это не отменяет проверки модуля, допуска сотрудника, ACL, состояния объекта и назначения на этап.

Новая сущность роли и несколько одновременно назначенных должностей для этой модели не требуются. Автор, регистратор, согласующий, исполнитель и подписант — функции процесса. Одна должность может содержать права нескольких функций; назначение на конкретный этап хранится в приложении.

## 2. Источники истины

- Workspace подтверждает активность сотрудника и компании, доступность модуля, назначенную должность и набор прав приложения.
- ЭДО отвечает за компанию документа, ACL, маршрут, поручения, подпись и состояния документа.
- SenimDesk отвечает за тип и границы своего тенанта, локальное членство, доступные проекты/объекты/заявки и их состояния.
- iForm отвечает за права над процессами и заявками, назначенных участников и переходы задач; Workspace передаёт подтверждённый контекст сотрудника и компании.
- Браузер отображает серверный результат. Скрытая кнопка, переданные клиентом роли и идентификаторы не заменяют авторизацию API.

Для обычного сотрудника в управляемом режиме набор должности заменяет локальные рабочие роли и индивидуальные права. Для действующего владельца применяется полный доступный каталог компании; передача владения проверяется при каждом запросе. ACL, группа и назначение на этап определяют доступные объекты в сочетании с разрешением действия. Они не создают отсутствующее разрешение и не открывают другую компанию.

## 3. Модуль и режим управления

Существующие поля имеют разные значения; задача 1 не переименовывает их.

| Значение | API модулей | `access-management.apps[application]` | `current/access` |
| --- | --- | --- | --- |
| Платформа разрешила модуль | `available` | `available` | `module_available` |
| Компания включила модуль | `enabled` | `module_enabled` | `module_enabled` |
| Правами управляет Workspace | Отдельная настройка | `enabled` | `managed` |
| Подтверждён активный доступ сотрудника к модулю | Не определяется этим API | Не определяется этим API | `active` |

`active=true` не означает наличие рабочих прав: при `managed=true` массив `permissions` может быть пустым. `configured=false` означает отсутствие сохранённого набора, `configured=true` с пустым массивом — сохранённый запрет. Оба случая запрещают рабочие действия в управляемом режиме.

| Результат проверки | Решение приложения |
| --- | --- |
| Компания/сотрудник неактивны, модуль запрещён или выключен | Запретить рабочие действия независимо от прежних ролей |
| Источник прав недоступен, ответ повреждён или компания не совпала | Не выполнять действие; отличать техническую ошибку от отсутствия прав, не возвращаться к прежним ролям |
| `active=true`, `managed=false` | Только явно поддержанный прежний RBAC ЭДО/СД; сохранённые наборы Workspace ещё не применяются |
| `active=true`, `managed=true`, у обычного сотрудника нет должности/набора/нужного права | Запретить соответствующее действие; владелец получает полный реализованный каталог своей компании, платформенный администратор этого исключения не получает |
| Право есть, но объект чужой, участник/этап/статус не подходит | Запретить соответствующее действие |
| Все проверки выполнены | Разрешить действие |

Для iForm текущий мост требует включённого управления (`organization_access_apps.enabled=true`); самостоятельный прежний RBAC для него этим контрактом не вводится. При отключённом модуле Workspace возвращает `active=false`, `managed=true`, пустые `permissions`, чтобы потребитель не использовал локальные привилегии.

## 4. Назначение и отзыв доступа

Целевой административный flow:

1. Платформа разрешает модуль, владелец или администратор включает его для компании.
2. Уполномоченный администратор создаёт должность, в том числе без сотрудников.
3. Настраивает и сохраняет независимые наборы приложений; пустые наборы допустимы.
4. Назначает сотруднику должность и подразделение своей компании.
5. После подготовки назначений и наборов включает управление отдельно для ЭДО/СД. Для iForm включение управления является условием работы моста.
6. Проверяет сотрудника с минимальным набором и сотрудника без рабочих прав.

Перевод заменяет должность, старые права не копируются. Переименование сохраняет ID и политики. Снятие назначения убирает права должности; удаление должности разрешено после снятия всех назначений. Пустая должность сохраняет наборы и остаётся видимой администратору.

Изменение должности через профиль, импорт или создание сотрудника — изменение доступа и должно проходить проверку административных полномочий. Текущая миграция `20261003000100_sync_employee_access_position.sql` синхронизирует `users.position` с назначением по нормализованному названию внутри компании. Новое название создаёт должность без наборов, существующее может применить уже сохранённые права. Поле нельзя считать только отображаемым текстом.

Наборы и переключение управления используют `revision`; конфликт не должен перезаписывать чужое изменение. Назначения и политики должны сохраняться вместе с аудитом и согласованным профилем сотрудника. Аудит фиксирует автора, компанию, действие и изменения до/после без секретов.

После успешного сохранения новый запрос обязан использовать актуальную политику. Открытая вкладка и прежний токен не сохраняют отозванное право. UI обновляет доступные действия, сохраняет черновик при исправимой ошибке и показывает успех после подтверждения сервера. Отзыв не отменяет исторические решения, завершённые подписи и уже выполненные действия.

Отключение управления ЭДО/СД — явная административная операция с возвратом к прежнему RBAC. Сетевой сбой, пустой набор и отсутствие должности не переключают режим. Отключение модуля сохраняет настройки и наборы.

## 5. Проверка рабочего действия

Для действия над объектом одновременно необходимы:

```text
подтверждённый активный сотрудник и компания
  + доступный и включённый модуль
  + нужное рабочее разрешение
  + объект в разрешённой области компании
  + допустимый участник процесса, если требуется назначение
  + допустимые статус, этап и версия объекта
```

Чтение всех документов компании не позволяет согласовывать за других, исполнять чужие поручения, подписывать без назначения или менять завершённый документ. Список, карточка, вложения, экспорт и прямой API соблюдают одинаковую область данных.

Замещение дополнительно требует действующего назначения заместителя и разрешённого объёма замещения; оно не создаёт отсутствующие у сотрудника разрешения. Машинная интеграция использует отдельный проверенный серверный контекст с ограниченной областью операций. Сервисный токен не превращает браузерный запрос в произвольное действие от администратора.

Зависимости прав должны быть явными и проверяться сервером. Сценарию подписи нужен доступ к назначенному документу, исполнению — к поручению. Точное соответствие кодов действиям, зависимостям и допустимому наследованию фиксируется в задаче 2; задача 1 не вводит новые коды и не считает все галочки независимыми.

## 6. Участники ЭДО

| Функция | Основание | Дополнительная проверка |
| --- | --- | --- |
| Автор | Права создания/изменения | Авторство и редактируемое состояние документа |
| Регистратор | `document.register` | Допустимость принятия, подразделение и назначенный регистратор; управление маршрутом закрепляется за регистратором |
| Согласующий | `approval.approve`, `approval.return_for_revision`, `approval.reject` для соответствующего решения | Назначение на активный этап и порядок согласования |
| Исполнитель | `assignment.complete` | Назначенное активное поручение и актуальная версия |
| Подписант | `signature.sign` | Назначенный подписант, ожидание подписи и проверка выбранного способа подписи |
| Наблюдатель/аудитор | Соответствующие разрешения чтения | Область документов, проектов или журнала, без добавления рабочих действий |

Текущий подбор участников ЭДО исключает автора из согласующих и подписантов своего документа; автора можно назначить исполнителем. Ограничение сохраняется до отдельного решения о самосогласовании и самоподписи. Компания с одним сотрудником не получает автоматическое исключение. При отсутствии допустимого участника UI должен объяснить, почему маршрут нельзя запустить.

Обязательность согласования, исполнения и подписи зависит от вида документа и маршрута. Все этапы не становятся обязательными для каждого документа. Полная матрица переходов, доработок, закрытия и архива относится к задаче 7; выданное право не разрешает пропускать этапы.

## 7. Подключение приложений

Используются существующие контракты; новые маршруты и поля задача 1 не добавляет.

| Потребитель | Источник | Правило применения |
| --- | --- | --- |
| ЭДО | `GET /api/v1/organizations/current/access?application=odo` под проверенным пользовательским bearer | Точный набор Workspace при управлении, затем ограничения объекта/процесса; локальный `workspace_user_access` — снимок, не замена живой проверке текущего пользователя |
| Подбор участников ЭДО | `GET /api/v1/organizations/current/users?application=odo` | Права, активность, компания, подразделение и допустимость участия; первый вход кандидата в ЭДО не является условием назначения |
| SenimDesk | `POST /api/internal/access/resolve-sd` под серверным токеном | Связанная компания и подтверждённый subject; набор Workspace вместо локальных рабочих ролей, с ограничениями типа компании СД |
| iForm | `IFormIdentity` в proxy и `POST /api/internal/iform/context` | Разрешённое сопоставление `iform.*` с ролями; авторизация процесса и задачи на стороне iForm |
| Поручения ЭДО в Workspace | Политика `odo`, серверная проверка поручения и пользовательская команда ЭДО | Те же рабочие права и ограничения, что в ЭДО; проекция Workspace не становится источником статуса |

В СД компания связывается по UUID. Пользователь сопоставляется по подтверждённому subject Keycloak либо по серверному handoff Workspace с идентификатором `workspace-user:<id>`. Email, логин и название компании не являются основанием выдать доступ. Смена контекста повторно подтверждает членство и права выбранной компании.

В iForm `iform.director` — разрешение функции процесса, `organizations.owner_id` — владение компанией. Техническое администрирование тенанта должно быть отделено от создания/публикации процессов, аудита, исполнения, согласования и подписи. Рабочие роли в целевой модели выводятся из разрешённых `iform.*`.

## 9. Матрица приёмки последующих исправлений

Это критерии будущих тестов, а не отчёт о проверенном production.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Сотрудник или `manager` меняет политику/назначение | Отказ сервера |
| Владелец управляет своей компанией / выбирает чужую через platform API | Разрешение первого действия, отказ второго |
| Должность называется «админ» или «директор» | Системные полномочия не появляются |
| Владелец без должности выполняет действие приложения | Полный реализованный каталог своей компании; объектные проверки и активность сохраняются |
| Платформенный администратор без рабочих прав выполняет действие приложения | Отказ; административная роль сама по себе не выдаёт рабочие права |
| У обычного сотрудника нет должности, набор не настроен или сохранён пустым | Рабочие действия запрещены; UI различает причины |
| Право выдано и все объектные условия выполнены | Действие успешно, в том числе через прямой URL |
| Право снято при открытой вкладке / сотрудник переведён на должность без этого права | Следующий запрос использует новый набор; старое действие запрещено |
| Компания/сотрудник отключены или модуль запрещён/выключен | Рабочие действия запрещены, локальные роли не восстанавливают доступ |
| Источник прав недоступен или ответ неполный | Техническая ошибка, без действия и возврата к прежним привилегиям |
| Право есть, но объект другой компании, чужое поручение или неактивный этап | Отказ сервера |
| Есть чтение всех документов, назначения согласующим/подписантом нет | Чтение в своей компании возможно, решение/подпись запрещены |
| Пустая должность подготовлена, назначен первый, снят последний сотрудник | Набор сохраняется, права применяются по назначению, должность остаётся видна администратору |
| Одна операция выполняется через ЭДО и через Workspace | Одинаковые права, область объекта и итоговое состояние источника |
| В компании с одним сотрудником нет допустимого участника этапа | Понятное объяснение, без автоматического снятия ограничений |
