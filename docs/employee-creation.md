# Создание сотрудника без изменения существующих профилей

`POST /api/v1/users` и `POST /api/v1/external-admin/users` создают отдельную
локальную запись и новую учётную запись Keycloak. `organization_id` задаёт
компанию, `team_id` можно не передавать: сотрудник остаётся в списке компании
без подразделения.

Публичный `POST /api/v1/users` проверяет актуальное право на сервере: создание
разрешено активному администратору платформы или владельцу активной компании.
Обычный сотрудник и бывший директор получают HTTP 403. Проверки области компании
и допустимой роли нового пользователя сохранены. У external-admin и iForm
остаются их отдельные проверки доступа.

Создание не использует `UpsertFromKeycloak`, автоматическое связывание профилей
или восстановление существующей SSO-учётной записи. Совпадение ИИН, email или
логина, включая нормализованные значения и пользователей других компаний,
возвращает HTTP 409 с кодом `USER_IDENTITY_CONFLICT`. Сообщение доступно на ru/kk
и не раскрывает данные существующего пользователя или его компании.

Проверка выполняется до обращения к Keycloak и повторяется перед вставкой
в транзакции. Параллельные создания с совпадающими идентификаторами
сериализуются. Пароль, роли, профиль и принадлежность существующего пользователя,
а также `organizations.owner_id` не изменяются. Конфликт Keycloak также
останавливает операцию без изменения существующей SSO-записи.

При ошибке локального сохранения удаляется только новая SSO-запись текущего
запроса. Повтор iForm с уже завершённым ключом приёма по-прежнему обрабатывается
его отдельной проверкой совпадения параметров.

Исправление подмены учётной записи требует выпуска бэкенда; новые миграции
для него не нужны. Исправления формы ниже требуют также выпуска фронтенда.
Уже повреждённые данные автоматически не исправляются: восстановление
требует проверки исходных ID, аудита и SSO-связей.

## Создание, структура и должностные права

1. В разделе «Сотрудники» директор создаёт новую учётную запись своей компании.
   Форма предлагает логин по имени/фамилии и почту в домене компании; оба значения
   можно исправить. Подразделение и должность необязательны.
2. После успешного создания сотрудник входит в список компании. Без `team_id`
   он остаётся без подразделения; в структуре доступен в общей команде и окне
   распределения сотрудников. В выбранном подразделении появится после назначения.
3. Триггер `users_sync_access_position` связывает указанную должность с записью
   этой компании. Существующая должность использует её настроенные права;
   новая должность создаётся без настроенных политик. При включённом управлении
   по должностям сотрудник без должности не получает рабочих прав приложений.
4. Назначение подразделения меняет `team_id`, но не компанию, владельца или
   должностную политику. Область документов подразделения при этом может меняться.
5. Назначение другой должности через «Права доступа» заменяет прежнюю должность
   и набор её прав. Одинаковые названия должностей разных компаний независимы.
6. Владелец компании определяется `organizations.owner_id`, руководитель
   подразделения — `teams.manager_id`. Текст должности «Директор» не меняет эти
   поля, но может давать широкие права приложений, если так настроена её политика.

В разных разделах «Добавить сотрудника» означает разные операции: создать
учётную запись, распределить существующего сотрудника в подразделение или
назначить существующему сотруднику должность.

## Проверка и оставшиеся ограничения

21 октября 2026 проверены форма, список, структура, окно распределения и
назначения должностей в браузере под директором Sultan Corp. Создание записей,
изменение подразделений и прав на сервере не выполнялись. Проверка рабочего
сохранения исправленным API и первого входа нового сотрудника с реальным SSO
остаётся после выпуска бэкенда.

На отдельной PostgreSQL проверен путь `CreateNewUser` → триггер должности →
список компании → эффективные права → назначение/снятие подразделения →
переназначение должности, включая отказ для чужой компании и обычного сотрудника.

В существующей модалке создания сотрудника поле «Должность» предлагает
список должностей выбранной компании и пункт «Создать новую». При создании
новой появляется поле названия; одноимённая должность из загруженного списка
сравнивается без учёта регистра и внешних пробелов. Новая должность создаётся
серверным триггером вместе с сотрудником. Порядок остальных полей и поведение
списка и структуры сохранены. Права настраиваются в разделе «Права доступа».

Регрессии выбора должности: node scripts/test-employee-creation-flow.cjs.

Оставшиеся особенности интерфейса:

- После создания сохраняются фильтры и текущая страница списка.
- В распределении выбор подразделения сразу сохраняет его.
- API создания принимает название должности, которое сервер разрешает внутри
  компании при вставке. Параллельные изменения должностей и политик применяют
  актуальную серверную запись.
- При обрыве ответа после успешного сохранения повтор создания вернёт конфликт;
  перед повторной попыткой с другими данными следует проверить список сотрудников.
