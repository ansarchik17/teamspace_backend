# Правила процесса приёма сотрудника

## Сообщения об отказе публикации

Прокси iForm сохраняет безопасный контракт `validation` для отказа публикации
`POST /processes/{id}/publish` со статусом 422. Принимаются только известные коды
`publication_issues` от iForm; сообщения для подключения, шаблона, назначений,
параметров процесса и подтверждения настроек формируются в Workspace на ru/kk.
Тексты исключений, произвольные поля и исходный `validation` upstream не пересылаются.
Для старого iForm без этих кодов, неизвестных кодов, других маршрутов и статусов
остаётся общий безопасный ответ. Изменение требует сначала обновить iForm.

Версия правил: 1. Решение пользователя от 22.10.2026: оформление ЭДО считается завершённым по статусу **`completed`**. Правила отражены в новой основе процесса iForm `employee-onboarding` и проверяются перед публикацией. Это локальная реализация; опубликованный процесс компании на сервере не изменён.

## Утверждённый порядок

1. HR заполняет одну заявку: ФИО, ИИН, корпоративная почта, должность, подразделение, руководитель, дата выхода и требования к рабочему месту.
2. Руководитель подразделения кандидата согласовывает решение о найме.
3. Директор согласовывает решение о найме.
4. Создаётся кадровый документ ЭДО; iForm ждёт `completed` именно этого документа и завершения настроенного маршрута.
5. Создаётся сотрудник Workspace с компанией, подразделением, руководителем и должностью.
6. Создаётся одна SD-заявка с идентификатором уже созданного сотрудника, датой выхода и требованиями к рабочему месту.
7. iForm ждёт фактического выполнения SD.
8. HR готовит первый вход и завершает отдельную задачу подготовки доступа.
9. HR отдельно подтверждает общую готовность сотрудника.
10. Инициатор получает уведомление; заявка завершается.

Подготовка первого входа и подтверждение HR — разные задачи. Операция создания сотрудника не завершает приём автоматически. Согласования найма проходят в iForm; повторять их в ЭДО без отдельного требования компании не нужно. IT выполняет одну SD-заявку; то же задание не следует дублировать поручением ЭДО.

## Решения и остановка

| Событие | Поведение |
| --- | --- |
| Руководитель или директор согласовал | Переход только на следующий предусмотренный этап |
| Возврат на исправление | HR меняет ту же заявку; затем повторно проходят руководителя и директора |
| Отказ руководителя или директора | Приём прекращается; кадровые операции ещё не запускаются |
| ЭДО `draft`, `registered`, `on_approval`, `approved`, `in_execution`, `waiting_for_signature`, `signed` | Ожидание; сотрудник и SD-заявка ещё не создаются |
| ЭДО `completed`, настроенный маршрут завершён | Разрешено создание сотрудника и последующее создание SD-заявки |
| ЭДО `completed`, но в настроенном маршруте остаются этапы | Ожидание; промежуточное завершение исполнения не открывает создание сотрудника |
| ЭДО `rejected`, `cancelled`, `withdrawn` | Операция неуспешна; процесс останавливается с инцидентом для ответственного |
| Впервые получен `closed` или `archived` вместо требуемого `completed` | Не считать доказательством завершения нужного этапа; остановить с инцидентом для сверки |
| SD-заявка создана, но не выполнена | Ожидание IT; задачи первого входа и подтверждения HR ещё не доступны |
| SD-заявка отменена | Остановка с инцидентом; не считать рабочее место готовым |
| Отмена самой заявки приёма | Новый процесс приёма прекращает следующие шаги, включая после внешней записи; уже созданные объекты сохраняются для ручной сверки |
| Сервис недоступен или ответ не подтверждён | Текущий шаг не считается успешным; существующий механизм безопасного повтора сохраняется |

Для ЭДО настроен точный статус, а не набор взаимозаменяемых завершений. Если `completed` был подтверждён и сохранён раньше, последующий штатный переход документа не отменяет историю успешного этапа. Если polling впервые увидел более поздний статус, автоматического вывода о пропущенном `completed` нет. Требуется ручная проверка; документ нельзя менять ради обхода условия.

При отмене после внешней записи создаётся инцидент. Отмена не удаляет кадровый документ, учётную запись и SD-заявку автоматически и не отзывает уже выполненные действия. Продолжение по позднему outbox-событию отменённой/отклонённой заявки заблокировано. Неизвестный исход уже начатого внешнего вызова требует сверки ответственного.

## Настройки версии процесса

В `config` начального шага хранится:

```json
{
  "onboardingRules": {
    "version": 1,
    "odoCompletionStatus": "completed",
    "externalFailure": "stop"
  }
}
```

Шаг ожидания документа использует:

```json
{
  "operation": "workspace.odo.wait",
  "completionStatus": "completed",
  "inputs": {
    "document_id": {"result": {"step": "createDocument", "key": "document_id"}}
  }
}
```

iForm передаёт в Workspace `inputs.completion_status="completed"`. Workspace проверяет это правило по статусу документа и `workflow_plan.phase` для настроенного маршрута; промежуточный `completed` не завершает ещё активный маршрут. Ответ содержит `completion_status`, `source_status` и `source_phase`. iForm требует подтверждение выбранного правила и сверяет исходный статус, чтобы старый мост не выдал ложный успех. Отсутствие подтверждения блокирует продолжение. Старые опубликованные процессы без настройки продолжают прежнюю семантику ожидания. Процессы и запущенные заявки не переписываются чтением или обновлением сервисов.

Публикация варианта с `onboardingRules` проверяет порядок, наличие отдельных этапов, роль директора, руководителя выбранного подразделения, ожидание именно созданных объектов, подготовку первого входа и повторное согласование после доработки. Переставить SD раньше сотрудника, пропустить ожидание ЭДО или объединить две задачи HR в этой версии правил нельзя.

## Применение и оставшиеся задачи

Основа находится в iForm: `backend/src/main/resources/processes/onboarding.json`; ключ существующей команды `APPLY_BLUEPRINT` — `employee-onboarding`. Пример команды для нового пустого черновика:

```json
{
  "baseRevision": 1,
  "proposedChanges": [
    {"type": "APPLY_BLUEPRINT", "payload": {"key": "employee-onboarding"}}
  ]
}
```

Использовать актуальную revision черновика и существующий `PATCH /api/v1/processes/{id}/draft` iForm. В настроенный процесс основу поверх существующей формы применять нельзя. Для переноса действующего процесса нужен проверенный новый черновик/версия; старые заявки сохраняют прежнюю версию.

Основа намеренно содержит `unresolvedItems` и пустые значения SD: ID компаний/услуг и сотрудников не выдумываются. До заполнения публикация заблокирована. Нужно настроить маршрут ЭДО с ответственными, достижимость `completed`, параметры SD и назначения согласующих. Настроенный маршрут ЭДО обязан реально приводить документ к `completed`; окончание подписи со статусом `signed` этот договор не выполняет.

Допуск с даты выхода реализован в Workspace и iForm: см. onboarding-employment-admission.md. Дата также задаёт срок кадрового документа и передаётся IT. Подготовленный пароль не записывается в поля процесса.

В следующей задаче добавлена автоматическая подготовка PDF по ID утверждённого шаблона iForm, назначение регистратора и маршрута, а также явное завершение после последней подписи. Настройки и ограничения описаны в [employee-document-automation.md](employee-document-automation.md). Теперь порядок выпуска: ЭДО backend → Workspace backend → iForm backend и frontend → настройка компании → новая версия. Новых миграций БД и переменных окружения нет. Production-публикация, изменение действующего процесса Sultan Corp и применение настроек на сервере этими задачами не выполнялись.

## Проверка

Go: `go test ./internal/domain ./internal/handler -run TestIForm -count=1`.

iForm: `mvn '-Dtest=OnboardingDocumentTest,OnboardingRulesTest,WorkspaceOperationsTest,DocumentRouteTest,WorkspaceIntegrationTest,WorkspaceSecurityTest' test` с `IFORM_TEST_JDBC_URL`, `IFORM_TEST_DB_USER`, `IFORM_TEST_DB_PASSWORD` отдельной одноразовой PostgreSQL, JDK 21+.

Интеграция использует настоящий Flyway/Flowable/PostgreSQL и локальный источник Workspace с синтетическими внешними результатами. Проверяет опубликованную конфигурацию, оба согласования, ожидание до `completed`, порядок сотрудник → SD, отдельные задачи HR, отказы обоих согласующих, отказ/отмену документа и отмену заявки после создания документа. Это не живой E2E кадрового документа, Keycloak или SD компании.

При фиксации правил прошли 26 Java-тестов, Go-проверки и локализация. В задаче автоматического документа набор расширен до 29 Java-тестов; дополнительно проверены TypeScript и настройки в браузере на широком и узком экране. Описание состава проверок находится в документе автоматизации выше.
