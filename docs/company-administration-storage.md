# BAS-017 BE-06: бюджет диска компании

Платформа задаёт общий бюджет Drive компании. Директор распределяет личные квоты
только её сотрудников. Роль платформы — актуальная `users.role='admin'`,
директор — `organizations.owner_id`. Обычные сотрудники административного
доступа не получают. Новая роль не вводится.

## API

Префиксы:

- Директор: `/api/v1/organizations/current/administration`.
- Платформа: `/api/v1/platform/organizations/:organization_id/administration`.

| Метод и путь после префикса | Директор | Платформа |
| --- | --- | --- |
| `GET /storage` — бюджет и расход компании | Своя компания | Выбранная компания |
| `PUT /storage` — бюджет компании | Нет | Да |
| `GET /storage/users?limit=25&offset=0` — личные квоты | Своя компания | Выбранная компания |
| `PUT /storage/users/:user_id` — личная квота | Своя компания | Выбранная компания |

GET `/storage`:

```json
{
  "quota_bytes": 32212254720,
  "allocated_bytes": 21474836480,
  "used_bytes": 1073741824,
  "free_bytes": 31138512896,
  "unallocated_bytes": 10737418240,
  "revision": 1
}
```

Все объёмы — целые байты. `allocated_bytes` — сумма личных квот всех
неудалённых сотрудников, включая директора и заблокированных сотрудников.
При отсутствии индивидуальной квоты применяется существующая глобальная
политика Drive: по умолчанию 5 GiB на сотрудника.
`used_bytes` включает файлы всех пользователей текущей компании, в том числе
удалённых, их версии и восстанавливаемую корзину. Общий файл расходует квоту
владельца; доступ к чужому файлу дополнительное место не занимает.

Пока бюджет не настроен, `quota_bytes`, `free_bytes`, `unallocated_bytes`
равны `null`: действуют личные ограничения Drive. Платформа может настроить
личные квоты до задания бюджета; директор распределяет их после настройки
общего бюджета. Новый бюджет не может быть меньше распределённых квот или
занятого места. Например, компания с двумя сотрудниками по 5 GiB требует
бюджета минимум 10 GiB. Для меньшего бюджета платформа сначала уменьшает
личные квоты, сохраняя уже занятые файлы.

GET `/storage/users` возвращает:

```json
{
  "items": [{"user_id": 123,"full_name":"Сотрудник","quota_bytes":10737418240,"used_bytes":1024,"revision":0}],
  "total":1,"limit":25,"offset":0
}
```

`limit` — 1–100, `offset` — неотрицательный. Заблокированные сотрудники
остаются в списке и продолжают занимать выделенную квоту.

Оба PUT принимают обязательные `quota_bytes` и `revision` из последнего GET:

```json
{"quota_bytes": 5368709120, "revision": 0}
```

Успех — HTTP 204. `quota_bytes` от 0 до 1 PiB включительно; 0 запрещает
увеличение объёма. Личная квота может стать меньше уже занятого места:
чтение, скачивание, переименование и удаление сохраняются, рост запрещён.
Изменение личной квоты не меняет ограничение размера одного файла.

Версия общего бюджета не меняется при загрузках. Версия личной квоты использует
существующий `drive_storage_accounts.revision`: загрузка тоже может изменить
её, поэтому при конфликте обновите GET. Изменения и события
`storage.quota.update` / `storage.user_quota.update` записываются вместе
в административный аудит; ошибка аудита откатывает изменение.

## Серверные ограничения

Сумма личных квот не может превысить бюджет. Проверки выполняются также
при добавлении сотрудника, изменении его компании и восстановлении удалённой
учётной записи. Если новая квота сотрудника не помещается в бюджет, назначение
отклоняется целиком. Для назначения сначала освободите квоту или увеличьте
бюджет. Личные файлы следуют за текущим владельцем при переводе между компаниями.

Общий расход проверяется триггерами БД вместе с личным расходом: загрузки,
копии, версии, импорты, восстановление и смена владельца не могут обойти
ограничение. Параллельные изменения сериализуются; конфликт требует повтора
запроса. Запросы чтения и операции, уменьшающие объём, сохраняются.
Квота относится к Drive Workspace, а не к внешним почтовым ящикам или
хранилищам интеграций. Квота количества сотрудников в этой задаче не вводится.

Обычный endpoint статистики Drive сохраняет личные `quota_bytes` и `used_bytes`
и добавляет `company_quota_bytes`, `company_used_bytes`, `company_free_bytes`
(null без общего бюджета). `free_bytes` — минимум личного и общего свободного
места, `can_upload` учитывает оба лимита.

Ошибки: `VALIDATION_ERROR` / 400 — неверное тело, диапазон или пагинация;
`FORBIDDEN` / 403 — нет административного права;
`NOT_FOUND` / 404 — сотрудник отсутствует в выбранной компании;
`CONFLICT` / 409 — версия устарела, бюджет не настроен, недостаточно бюджета
для распределения или компания приостановлена;
`DRIVE_QUOTA_EXCEEDED` / 507 — занят общий или личный объём;
`FILE_TOO_BIG` / 413 — превышен размер файла.
Коды стабильны, сообщения используют общую локализацию ru/kk.

## Миграция и проверки

Перед обновлением API применить `20261012000400_company_storage_quotas.sql`.
Существующие личные квоты и данные сохраняются; общий бюджет по умолчанию
не задан. При откате сохраняются личные квоты и восстанавливаются личные
проверки Drive. После настройки компаний общую политику Drive нужно менять
с учётом суммарных выделенных квот.

```sh
TEST_MESSENGER_DATABASE_URL='postgres://.../test?sslmode=disable' \
  go test ./internal/repository ./internal/service -run 'TestAdministrationStorage|TestDrive' -count=1
```

Тесты используют изолированные схемы PostgreSQL и проверяют роли, чужие
компании, бюджеты, конкурентное распределение, перенос сотрудников и данных,
аудит и откат, общий расход, версии, корзину и откат миграции.

## Проверка бюджета по ёмкости MinIO

PUT бюджета компании использует доступные метрики MinIO. Бэк читает свежий
снимок `/minio/v2/metrics/cluster` через внутренний `MINIO_ENDPOINT`:
`minio_cluster_capacity_usable_total_bytes` и `minio_cluster_capacity_usable_free_bytes`.
Не суммирует одинаковые cluster-метрики разных узлов. Неизвестные, неполные,
некорректные метрики, таймаут и отказ авторизации делают проверку физической ёмкости недоступной.
В этом случае логический бюджет можно сохранить; проверки личных квот и общего
расхода продолжают действовать. GET /storage/capacity возвращает 409.
Редиректы не выполняются, bearer token не выдаётся клиентам.

Настроить `MINIO_METRICS_TOKEN` токеном из `mc admin prometheus generate <alias>`.
Использовать учётную запись с правом чтения Prometheus-метрик MinIO.
`MINIO_CAPACITY_RESERVE_PERCENT` — целое число 0–99, по умолчанию 10.
Это резерв физической полезной ёмкости, не процент бюджета компании.
Для production использовать TLS либо защищённую внутреннюю сеть. Метрики должны
описывать тот же кластер, в который Workspace пишет файлы. Для другого S3
провайдера без этих метрик физическая ёмкость не проверяется; это отражается в серверном журнале.

Новый platform-only API:
`GET /api/v1/platform/organizations/{organization_id}/administration/storage/capacity`.
Ответ: `total_bytes`, `free_bytes`, `reserve_bytes`, `observed_at`,
`other_committed_bytes`, `other_remaining_bytes`, `max_quota_bytes`.
Директор и сотрудник физическую ёмкость платформы не получают.
`max_quota_bytes` — максимально допустимый полный бюджет выбранной компании,
а не величина прибавки. PUT по-прежнему требует `quota_bytes` и `revision`.
Ответ GET является подсказкой: PUT повторно читает метрики и проверяет бюджет.

Для остальных компаний обязательство — максимум бюджета (или суммы личных
квот, если бюджет не настроен) и использованного объёма. Неиспользованная часть
обязательства — максимум бюджета/личных квот минус расход, минимум ноль.
Приостановленные компании тоже учитываются. Верхний предел бюджета выбранной
компании — минимум двух величин, ограниченный снизу нулём:

- Полезная ёмкость − резерв − обязательства остальных компаний.
- Физически свободное место − резерв − неиспользованные обязательства остальных
  компаний + текущий расход выбранной компании.

Сохраняются прежние проверки бюджета относительно личных квот и расхода.
Глобальная транзакционная advisory-блокировка сериализует выдачу бюджетов разных
компаний на всех экземплярах API; отказ не изменяет бюджет и не создаёт аудит.
Миграция не требуется: используются существующие таблицы квот.

Это контроль назначения бюджетов по наблюдаемой ёмкости, а не физическая
резервация дисков в MinIO. Метрики имеют внутреннюю задержку обновления;
внешние приложения, прямые S3-загрузки, новые сотрудники компаний без бюджета,
удаление дисков и Docker/WSL thin provisioning могут менять доступную ёмкость.
Рабочие загрузки сохраняют существующие проверки квот; настройка бюджета не
предотвращает физическую ошибку MinIO при заполнении диска другим процессом.
Нужен мониторинг физического хранилища. На Docker Desktop значения относятся
к файловой системе VM и не заменяют проверку свободного места Windows-хоста.


## Бюджет только для Drive

Весь `quota_bytes` доступен для Drive в MinIO. Бюджет и расход не включают почту.
Например, бюджет 100 GiB позволяет директору распределить до 100 GiB личных
квот между сотрудниками своей компании. Обычный сотрудник не меняет квоты.

`PUT /storage` принимает `quota_bytes` и `revision`. Поле `mail_quota_bytes`
больше не используется. Почтовые доли, показатели синхронизации и маршруты
`/storage/mailboxes` удалены из API Workspace. Доступность AxisMail и его
настройки не влияют на чтение бюджета, его сохранение и загрузки Drive.

Перед запуском нового API необходима миграция
`20261014000100_company_drive_only_budget.sql`. Она исключает почтовую долю
из `organization_storage_usage` и снимает ограничение между старой почтовой
долей и бюджетом. Общая квота компании, личные квоты, файлы и история аудита
сохраняются. Старые почтовые поля остаются в БД для отката, но новый код их
не использует. При откате нужно проверить бюджеты относительно сохранённых
почтовых резервов перед возвращением старого API.

Для отказов настройки бюджета используются локализованные коды:

- `COMPANY_BUDGET_BELOW_USAGE` / 409 — бюджет меньше квот сотрудников или расхода.
- `COMPANY_BUDGET_CAPACITY_EXCEEDED` / 409 — недостаточно наблюдаемой ёмкости MinIO.
- `CONFLICT` / 409 — устаревшая версия или другое конкурентное изменение.
