# Раздельное серверное включение учёта и блокировок ИИ (Задача 40)

## 1. Назначение и контекст

Система тарификации и учёта расходов ИИ в Alem Workspace обеспечивает гарантированный учёт потребления микрокредитов, защищая платформу от финансовых перерасходов и гарантируя сохранность аудиторского следа.

Данный документ определяет архитектуру и правила раздельного серверного управления двумя независимыми механизмами:
1. **Учёт расходов (`AI_ACCOUNTING_ENABLED`)** — физический процесс резервирования, создания записей в неизменяемом журнале операций `ai_usage_operations`, попыток `ai_usage_attempts`, резерваций `ai_usage_reservations` и списания фактической стоимости в `ai_usage_settlements`.
2. **Принудительные финансовые блокировки (`AI_ENFORCEMENT_MODE`)** — политика отклонения клиентских запросов при исчерпании лимитов или отсутствии настроек бюджета.

> [!IMPORTANT]
> Публичные API-запросы клиентов **никогда** не имеют доступа к управлению этими переключателями. Режим задаётся строго на уровне сервера через проверенные переменные окружения и применяется ко всем входящим запросам.

## 2. Конфигурация и режимы работы

### 2.1. Переменные окружения

| Переменная | Тип | По умолчанию | Допустимые значения | Описание |
| :--- | :--- | :--- | :--- | :--- |
| `AI_ACCOUNTING_ENABLED` | `bool` | `true` | `true`, `false`, `1`, `0` | Включает конвейер учёта и резервирования кредитов. Если `false`, платные вызовы ИИ и запрос `/api/v1/ai/limits` возвращают `503 AI_ACCOUNTING_UNAVAILABLE`. |
| `AI_ENFORCEMENT_MODE` | `string` | `"enforced"` | `"enforced"`, `"observe"` | Режим принудительного применения финансовых лимитов. Валидируется при старте сервера: любые другие значения вызывают фатальную ошибку конфигурации. |

---

### 2.2. Сравнение режимов `enforced` и `observe`

| Проверка / Поведение | Режим `enforced` (по умолчанию) | Режим `observe` (наблюдение) |
| :--- | :--- | :--- |
| **Аутентификация и контекст вызова** | Блокирует (`401` / `403 AI_ACCESS_DISABLED`) | **Всегда блокирует** (`401` / `403 AI_ACCESS_DISABLED`) |
| **Блокировка аккаунта (`is_active`, `deleted_at`, `is_blocked`)** | Блокирует (`403 AI_ACCESS_DISABLED`) | **Всегда блокирует** (`403 AI_ACCESS_DISABLED`) |
| **Приостановка компании (`COMPANY_SUSPENDED`)** | Блокирует (`403 AI_ACCESS_DISABLED`) | **Всегда блокирует** (`403 AI_ACCESS_DISABLED`) |
| **Принадлежность компании (`NO_ORGANIZATION`)** | Блокирует (`403 AI_ACCESS_DISABLED`) | **Всегда блокирует** (`403 AI_ACCESS_DISABLED`) |
| **Параллелизм и частотные лимиты (`AIGenerationLimiter`)** | Блокирует (`429 AI_RATE_LIMIT` / `AI_CONCURRENCY_LIMIT`) | **Всегда блокирует** (`429 AI_RATE_LIMIT` / `AI_CONCURRENCY_LIMIT`) |
| **Идемпотентность (`idempotency_key`, replay)** | Replay возвращает записанный результат, dispatch не дублируется | **Работает идентично**: replay возвращает результат, dispatch не дублируется |
| **Нетарифицированная модель (`ErrAICreditUnknownModel`)** | Отклоняет (`503 AI_MODEL_UNPRICED`) | **Всегда отклоняет** (`503 AI_MODEL_UNPRICED`): неизвестные модели **не становятся бесплатными**! |
| **Ненастроенный бюджет компании (`COMPANY_BUDGET_UNCONFIGURED`)** | Отклоняет (`403 AI_ACCESS_DISABLED`) | **Разрешает**: открывает периоды компании, создаёт попытку, фиксирует расход |
| **Ненастроенная квота сотрудника (`USER_QUOTA_UNCONFIGURED`)** | Отклоняет (`403 AI_ACCESS_DISABLED`) | **Разрешает**: создаёт попытку, фиксирует расход сотрудника |
| **Отключенный бюджет компании (`COMPANY_BUDGET_DISABLED`, 0)** | Отклоняет (`403 AI_ACCESS_DISABLED`) | **Разрешает**: фиксирует перерасход сверх нуля |
| **Отключенная квота сотрудника (`USER_QUOTA_DISABLED`, 0)** | Отклоняет (`403 AI_ACCESS_DISABLED`) | **Разрешает**: фиксирует перерасход сверх нуля |
| **Исчерпание 5-часового лимита (`FIVE_HOUR_EXHAUSTED`)** | Отклоняет (`429 AI_QUOTA_EXCEEDED`) | **Разрешает**: фиксирует перерасход в текущем периоде |
| **Исчерпание недельной квоты (`USER_WEEKLY_EXHAUSTED`)** | Отклоняет (`429 AI_QUOTA_EXCEEDED`) | **Разрешает**: фиксирует перерасход в текущем периоде |
| **Исчерпание бюджета компании (`COMPANY_WEEKLY_EXHAUSTED`)** | Отклоняет (`429 AI_QUOTA_EXCEEDED`) | **Разрешает**: фиксирует перерасход в текущем периоде |
| **Вызов провайдера (`AIPaidCallerService`)** | Выполняется через общий исполнитель | **Выполняется через общий исполнитель**: никакого обхода конвейера |
| **Списание и запись фактического расхода (`SettleSuccess`)** | Полный расчёт токенов и списание microcredits | **Полный расчёт токенов и списание microcredits**: никаких фиктивных 0 кредитов |

## 3. Гарантии безопасности и целостности данных

1. **Нетарифицированные модели никогда не становятся бесплатными**:
   Если для запрашиваемой модели отсутствуют подтверждённые коэффициенты тарификации (`domain.AICreditRatesForModel` возвращает `ErrAICreditUnknownModel`), запрос немедленно отклоняется с ошибкой HTTP 503 `AI_MODEL_UNPRICED` как в режиме `enforced`, так и в режиме `observe`. Невозможно выполнить запрос с фиктивным нулевым расходом.

2. **Общий исполнитель (`AIPaidCallerService`) не обходится**:
   В режиме наблюдения запрос проходит все фазы жизненного цикла:
   `ResolveCaller` → `AIGenerationLimiter.Acquire` → `Reserve` → `MarkSent` → `dispatch` → `SettleSuccess`.
   Все фактические токены и кредиты записываются в журнал.

3. **Ненастроенные компании (`COMPANY_BUDGET_UNCONFIGURED`)**:
   Миграция `20261020100900_ai_enforcement_mode_unconfigured.sql` переводит внешние ключи таблиц учёта (`organization_ai_weekly_anchors`, `ai_usage_operations`, `organization_ai_user_quotas`, `organization_ai_user_weekly_usage`) на прямую связь с `organizations(id)` и `users(id)`. Это позволяет создавать периоды и вести точный учёт потребления даже для компаний, где суперадминистратор ещё не настроил лимиты бюджета. При этом статус `Configured = false` сохраняется в сводке бюджета компании до явной настройки администратором.

4. **Переключение режимов без потерь (`Zero Data Loss on Mode Switch`)**:
   Переключение режима между `observe` и `enforced` (например, через изменение переменной окружения и перезапуск пода) не затрагивает существующие записи в базе данных:
   - Журнал `ai_usage_operations` и попытки сохраняются полностью.
   - Активные и завершённые резервы не удаляются и не изменяются.
   - Периоды и накопленные счётчики `used_microcredits` не сбрасываются.
   - Если компания превысила лимит во время работы в режиме `observe`, при переключении в `enforced` последующие запросы немедленно начнут отклоняться с `429 AI_QUOTA_EXCEEDED`, опираясь на ранее накопленный расход.

5. **Безопасность параллельных запросов и нескольких инстансов**:
   Блокировки PostgreSQL `SELECT ... FOR UPDATE` в `OpenForReservation` и `Reserve` гарантируют строгую сериализацию открытия периодов и предотвращают состояние гонки при одновременных запросах от нескольких подов API.


## 4. Эксплуатационные режимы и переключение

| AI_ACCOUNTING_ENABLED | AI_ENFORCEMENT_MODE | Эффективное поведение |
| --- | --- | --- |
| true | enforced | Учёт и финансовые ограничения включены. |
| true | observe | Учёт включён, финансовые отказы записываются, но не блокируют. |
| false | enforced или observe | Новые платные вызовы запрещены с 503 AI_ACCOUNTING_UNAVAILABLE; это остановка допуска, а не бесплатная работа ИИ. |

Оба параметра читаются из окружения при старте API. У AI_ACCOUNTING_ENABLED допустимы только true/false/1/0 (регистр и пробелы нормализуются); опечатка прерывает запуск. Никакие query/body/header публичного запроса не меняют параметры. Изменение режима выполняется серверным rollout с одинаковыми значениями на всех API-инстансах. При смешанных настройках во время rollout каждый инстанс применяет свою политику допуска, но все используют один журнал и блокировки БД; для единого момента переключения сначала остановите новый трафик и завершите rollout.

Отключение учёта закрывает только новый допуск. Завершение, подтверждённая сверка и запись расхода уже существующих операций продолжаются. Не отключайте worker сверки вместе с блокировками. Переключение конфигурации не запускает миграции, DELETE, сброс периодов или освобождение unknown-резервов. После возврата enforced учитывается весь ранее записанный расход. Откат блокировок: оставить AI_ACCOUNTING_ENABLED=true и установить AI_ENFORCEMENT_MODE=observe.

Неизвестная модель до вызова остаётся запрещённой с AI_MODEL_UNPRICED, даже в observe. Спецификация 03 допускает, но не требует расширенный unpriced-dispatch в наблюдении; текущий адаптер не выдаёт такое разрешение. Эта задача не добавляет обход существующего реестра моделей или вымышленные коэффициенты. Если фактическая модель/usage неизвестны после отправки, общий исполнитель сохраняет unknown и активный резерв; ни отсутствие usage, ни 5xx, ни отмена запроса не означают нулевые токены.

## 5. Запись наблюдений без содержимого запросов

Дополнительная миграция 20261020101000_ai_budget_observations.sql создаёт ai_usage_budget_observations. Для каждой новой попытки в observe атомарно с резервом сохраняются снимки scope (company/weekly/five_hour/service), настроенного лимита (NULL, если настройки нет), расхода и удержаний до допуска, запрошенного резерва. NULL отличается от настроенного 0. Повтор операции возвращает прежний резерв и не дублирует снимки. При отказе записи снимка транзакция откатывается, провайдер не вызывается.

Представление ai_usage_budget_exceedances показывает причины unconfigured/disabled/exhausted, exceeded_at_admission и exceeded_with_actual_usage. Последнее сравнивает фактический расход данной попытки с условиями её допуска; это не повторная тарификация и не текущий суммарный расход периода. charged_microcredits и exceeded_with_actual_usage остаются NULL при неизвестном расходе. Перерасход сверх оценки также сохранён в ai_usage_settlements.overrun_microcredits. Нельзя суммировать строки view как расход: одна попытка имеет несколько scopes. Источник денежных счётчиков — существующий журнал и периоды.

В таблице нет текста промптов, сообщений, сырых ответов или секретов. Это внутренние данные БД, новые публичные маршруты не добавляются.

## 6. Обновление

1. Применить миграции существующего учёта, затем 20261020100900_ai_enforcement_mode_unconfigured.sql и 20261020101000_ai_budget_observations.sql на целевой БД штатным процессом обновления. В этой задаче проверяется только отдельная тестовая БД.
2. Развернуть обновлённый backend с AI_ACCOUNTING_ENABLED=true, AI_ENFORCEMENT_MODE=observe и действующей настройкой AI_LIMITER_*; включение observe не изменяет rate/concurrency limiter.
3. Проверить журнал и ai_usage_budget_exceedances, настроить бюджеты и квоты явно. Фиктивные бюджетные строки для ненастроенной компании не создаются.
4. Согласованно переключить все API на enforced. Фронтенд получает действующий enforcement_mode через существующий GET лимитов и сводку бюджета. Перерасход компании после наблюдения может потребовать увеличить бюджет или дождаться новой недели.

Откат FK-миграции 20261020100900 безопасно отклоняется, если накоплены данные без бюджетов/квот; не удалять журнал ради rollback. Отключение финансовых блокировок не требует отката схемы.


## 7. Проверки реализации

На отдельной PostgreSQL-БД проверены: превышение недельной/пятичасовой квоты; компания и сотрудник без настроек; запись снимков и фактического перерасхода сверх оценки; переключение observe/enforced; отключение нового допуска без освобождения неизвестного резерва; подтверждённое завершение после отключения; неизвестный usage через настоящий общий исполнитель; неизвестная модель до вызова; два инстанса с разными сотрудниками одной ненастроенной компании; replay без повторного снимка; сохранение активного резерва через следующую неделю; численные границы хранения. Служебная квота продолжает применяться в enforced. Производственные провайдеры и production-БД не использовались.

Флаги относятся к интегрированным путям общего исполнителя. Оставшиеся неподключённые интеграции из сверки задачи 26 не становятся покрытыми учётом от одного включения этих флагов; их интеграция остаётся самостоятельной работой.
