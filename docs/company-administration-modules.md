# BAS-017 BE-05: модули компании

Каталог: `crm`, `growy`, `iform`, `odo`, `sd`. `growy` — обучение;
`crm` — CRM и связанная переписка WhatsApp/Telegram/Meta. Модули Workspace без существующего
контракта управления доступом не добавляются автоматически.

Администратор платформы определяется актуальной ролью `users.role = 'admin'`.
Директор — `organizations.owner_id`. Email и название должности прав не дают.

## API

| Действие | Директор своей компании | Администратор платформы |
| --- | --- | --- |
| Получить модули | `GET /api/v1/organizations/current/administration/modules` | `GET /api/v1/platform/organizations/:organization_id/administration/modules` |
| Изменить модуль | `PUT /api/v1/organizations/current/administration/modules/:application` | `PUT /api/v1/platform/organizations/:organization_id/administration/modules/:application` |

GET возвращает массив, например:

```json
[{"application":"iform","available":true,"enabled":true,"effective":true,"revision":2}]
```

- `available`: разрешение платформы; меняется только через platform API.
- `enabled`: выбор компании; директор может включить только разрешённый модуль.
- `effective`: `available && enabled && компания активна`.
- `revision`: общая версия настройки, обязательна при PUT; отсутствие записи — 0.

Администратор разрешает модуль новой компании:

```json
{"available":true,"revision":0}
```

Директор включает модуль после обновления GET:

```json
{"enabled":true,"revision":1}
```

Успех PUT — 204. Платформа может передать оба флага одним запросом.
Отзыв `available` немедленно делает `effective=false`, сохраняя выбор директора.
Повторное разрешение восстанавливает доступ, если `enabled=true`.
Изменения и аудит `module.update` записываются одной транзакцией.

Ошибки: `VALIDATION_ERROR` / 400 — неизвестный модуль, отсутствующие флаги или
версия, отрицательная версия; `FORBIDDEN` / 403 — нет роли или включается
запрещённый модуль; `CONFLICT` / 409 — устаревшая версия либо компания
приостановлена. При конфликте фронт повторяет GET и предлагает обновить выбор.
Тексты ошибок локализуются общим механизмом ru/kk; коды стабильны.

## Совместимость с вкладкой «Права доступа»

`access-management` продолжает управлять должностями, назначениями и правами
iForm/ОДО/СД. Обучение и CRM используют существующие `growy-role-mappings`,
но разрешение и включение этих двух модулей независимы. CRM не добавляется
в каталог детальных прав iForm/ОДО/СД: конкретные операции проверяет Growy.
Старое `apps[application].enabled` означает **режим управления правами**,
а не включение модуля. Его смысл и версия не меняются.
В `apps` добавлены `available` и `module_enabled`. Включение режима управления
правами запрещено, когда модуль недоступен или отключён. Настроенные права
сохраняются при отключении модуля.

`current/access?application=...` и выдача прав сотрудников добавляют поля
`module_available`, `module_enabled`. Для отключённого модуля сервер возвращает
`active=false`, `managed=true`, пустые `permissions`, чтобы интеграция не
переключалась на локальные права. При обработке ответа сначала проверяйте
`active`, затем `managed` и права.

Проверки применены к iForm proxy/context, Growy proxy/handoff/access-check,
СД handoff/identity/resolve и созданию/обмену кода ОДО. Прямые API внешних
приложений должны использовать актуальные проверки Workspace: собственные
ранее созданные сессии внешнего сервиса Workspace сам не отзывает.

## Миграция и проверка

Миграция `20261012000300_company_modules.sql` сохраняет доступ существующих
компаний, добавляя четыре модуля с `available=true`, `enabled=true`.
Существующие права и режимы управления ими не изменяются.
Для новых компаний действуют актуальные миграции дефолтов сервисов;
доступ к новым модулям `crm`/`growy` требует явного разрешения платформы.
Перед запуском новой версии API необходимо применить миграции.

`20261103000100_crm_company_module.sql` добавляет `crm` в ограничение БД и
однократно переносит его `available`/`enabled` из прежнего `growy` у существующих
компаний. Так сохраняются прежние разрешения и отказы. Существующая настройка CRM
не перезаписывается, обучение не изменяется. Новая компания получает карточку CRM
с `available=false`, `enabled=false`, `revision=0`, пока платформа её не разрешит.
Миграция Down удаляет настройки CRM и возвращает прежнее ограничение БД.

Сервер выбирает допуск по фиксированному маршруту:

- `/api/platform/v1/...` (CRM, WhatsApp, Telegram, Meta и context) требует `crm`;
- учебные GET и browser handoff требуют `growy`, с provisioning именно LMS;
- внутренний `/api/internal/growy/access-check` проверяет `crm`, чтобы отзыв
  доступа применялся и к ранее выданным CRM-токенам. LMS этот callback не использует.

Локальная приёмка: после миграции и запуска backend/frontend ветки `ansar-branch`
открыть «Модули» в platform- и company-режимах. Проверить пятую карточку CRM,
разрешение платформой, включение директором и независимость от обучения.
Отдельно проверить отказ CRM-запросов после выключения, включая существующую
сессию. HTTP 409 `external_identity_conflict` от удалённого Growy означает
необходимость подтверждённой привязки аккаунта; переключатель модуля её не выполняет.

Интеграционные тесты проверяют разграничение ролей и компаний, включение и
отзыв доступа, конфликт версий, аудит и откат при ошибке аудита. Тест iForm
проверяет запрет proxy/context даже директору. Для запуска требуется
`TEST_MESSENGER_DATABASE_URL`; iForm использует `IFORM_TEST_DATABASE_URL`.
Тест обмена кода ОДО выполняется без PostgreSQL.
