# Регистрация и подключение по персональному приглашению

## Поведение

В разделе управления сотрудниками frontend показывает панель приглашений владельцу компании и администратору платформы в выбранной компании. Приглашение привязано к email и необязательному подразделению. Ссылка действует 7 дней. Администратор может отправить её повторно или отозвать. После успешной повторной отправки прежняя ссылка и код подтверждения недействительны.

Страница `/web/join#token=…` доступна до входа и после входа. Открытие страницы показывает название компании и маску email, не создавая аккаунт. Для регистрации и принятия приглашения нужен отдельный шестизначный код из письма: срок 10 минут, максимум 5 неверных попыток, повторная отправка через 60 секунд. Владение скопированной ссылкой само по себе не подтверждает email.

Новый пользователь вводит имя, фамилию, ИИН, логин и пароль с подтверждением. Компания и подразделение определяются приглашением, роль — `user`. Он задаёт собственный пароль, поэтому `is_first_login=false`. После регистрации выполняется обычный вход. Существующий пользователь входит, возвращается на приглашение и подтверждает подключение.

При возврате через парольный вход или SSO в redirect передаётся только `/web/join`. Секрет хранится в sessionStorage текущей вкладки на срок до часа; при успехе удаляется. На исходной ссылке секрет находится во fragment, не отправляемом HTTP-серверу. Публичные API принимают его только в POST body; ответы имеют `Cache-Control: no-store`.

## Границы доступа

- Административные запросы проверяют действующие права по БД; должность не даёт права приглашать сотрудников.
- `/organizations/current/…` определяет компанию по пользователю. Явный ID компании допускается только в платформенном API.
- Пользователь из другой компании, владелец другой действующей компании даже без `users.organization_id`, заблокированный, неактивный и удалённый пользователь не подключаются.
- У существующего сотрудника этой компании организация, подразделение и права не меняются.
- У обычного аккаунта без компании назначаются организация и выбранное подразделение; прежние должность и руководитель очищаются. Привилегированные аккаунты без компании требуют административного подключения.
- Публичный старый `POST /api/v1/auth/register` отвечает `403 INVITATION_REGISTRATION_REQUIRED`. Доверенные административные и HR-процессы сохраняют свои точки входа.
- JSON регистрации не принимает `organization_id`, `team_id`, `role`, `email` и другие неизвестные поля.

## Keycloak, рабочая почта и повторные запросы

Новая SSO-учётная запись создаётся отключённой. После установки пароля и роли локальный профиль и принятие приглашения сохраняются одной транзакцией. Затем учётная запись активируется. Если Keycloak временно недоступен после commit, API возвращает `503 INVITATION_ACTIVATION_PENDING`; фоновая задача повторяет активацию каждую минуту, проверяя состояние пользователя и компании. Задание хранится в БД и переживает перезапуск API.

При повторном запросе после принятия приглашения пароль и роль не устанавливаются заново. После ошибки до сохранения профиля повтор может продолжить только отключённую SSO-запись с серверным маркером незавершённого приглашения той же компании и email. Это работает также после отзыва старого и выдачи нового приглашения. Активные и посторонние учётные записи не присваиваются и не изменяются.

Логин незавершённой SSO-записи сохраняется: не все realm разрешают менять username. При несовпадении возвращается `INVITATION_REGISTRATION_LOGIN`; frontend подставляет первоначальный логин и предлагает повторить отправку. При Keycloak PUT передаются email, имя, фамилия, username, статус подтверждения email и атрибуты, чтобы частичное обновление не стирало профиль.

Перед первой подтверждённой регистрацией сервис проверяет настройки профиля Keycloak и добавляет отсутствующие управляемые атрибуты `iin` и `workspace_invitation_id`. Маркер приглашения доступен для просмотра и изменения только администратору. Остальная конфигурация профиля и политика unmanaged attributes сохраняются. Сервисной учётной записи нужны разрешения на работу с пользователями и настройками user profile; если атрибуты уже подготовлены, сервис не меняет конфигурацию повторно.

Компания пользователя хранится в существующей локальной модели. Регистрация не записывает постоянный `workspace_organization_id` в SSO-профиль: такой атрибут мог бы впоследствии вернуть старую компанию при обычном входе после административного изменения.

Рабочий ящик создаёт почтовый сервис при подключении через «Почта» или синхронизации сотрудников компании. Для нового ящика используется тот же генератор, что и в форме сотрудника: первая буква имени, точка, транслитерированная фамилия и домен компании; при занятости добавляется суффикс `2`, `3` и т.д. Список сотрудников возвращает отдельные `first_name` и `last_name`: отображаемое ФИО нельзя надёжно разделить для формирования адреса. Уже назначенные адреса, включая незавершённое создание ящика, не переименовываются при повторном входе или изменении имени/логина. Массовой миграции старых ящиков нет.

Подтверждённый внешний контакт хранится отдельно в `user_verified_contacts` и переживает изменение основного рабочего email. Контакт принадлежит одному аккаунту; повторная регистрация с ним предлагает войти в существующий аккаунт. Эта таблица фиксирует подтверждение адреса, а резервная почта для восстановления назначается отдельным подтверждённым действием.

Новые сценарии не требуют E2EE-ключей или `e2ee_backup`.

## API

Все пути ниже начинаются с `/api/v1`. Административные и accept-запросы требуют действующую авторизацию.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/organizations/current/invitations?limit=10&offset=0` | Список `{items,total}` |
| POST | `/organizations/current/invitations` | Создать: `{email,team_id?:UUID}` |
| POST | `/organizations/current/invitations/:invitation_id/resend` | Новая ссылка и письмо |
| DELETE | `/organizations/current/invitations/:invitation_id` | Отозвать, ответ 204 |
| POST | `/auth/invitations/preview` | `{token}` → `{organization_name,email_hint,expires_at}` |
| POST | `/auth/invitations/code` | `{token}` → `{sent:true,retry_after:60}` |
| POST | `/auth/invitations/register` | `{token,code,first_name,last_name,iin,username,password}` |
| POST | `/auth/invitations/accept` | Авторизация и `{token,code}` |

Для платформенного администратора четыре административных пути имеют префикс `/platform/organizations/:organization_id/invitations`.

Создание и повторная отправка возвращают `{invitation,url}`. Секретная ссылка доступна только в результате её выпуска; в списке её нет. Регистрация и принятие возвращают `{organization_id,user_id,already_member,registered}` без выдачи сессии. Список содержит вычисляемые статусы `pending`, `accepted`, `revoked`, `expired`.

После ошибки отправки письма транзакция откатывается: предыдущая ссылка остаётся действующей. Если SMTP принял письмо, а соединение или commit затем потерялись, доставленное письмо может содержать недействующую ссылку. Повторная отправка администратором восстанавливает сценарий; API не обещает доставку при ошибке.

Создание, повторная отправка, отзыв и принятие фиксируются в существующем административном аудите. Секрет ссылки, код и пароль в снимки аудита не записываются.

## Запуск и проверки

1. Применить миграцию `20261025000100_organization_invitations.sql` штатным мигратором до использования нового API.
2. Проверить `APP_PUBLIC_URL`: публичный origin платформы по HTTPS. Разрешён HTTP только для localhost/127.0.0.1 в разработке. Ссылки строятся из конфигурации, не из заголовков запроса.
3. Настроить существующий `EmailService`: `MAIL_ENABLED=true`, `MAIL_PROVIDER=smtp`, SMTP-соединение и отправитель. Убедиться в доставке на внешнюю почту.
4. Проверить права Keycloak для пользователей, установки пароля/ролей и подготовки user-profile attributes.
5. Обновить backend и frontend; проверить приглашение нового пользователя и принятие существующим на тестовой компании.

Выполнены `go test ./...`, отдельные интеграционные тесты PostgreSQL и реального локального Keycloak 26.8.1, сборка frontend, ESLint изменённых компонентов, проверка переводов и 17 целевых frontend-тестов. Браузерные проверки на синтетическом API покрывают новую регистрацию, несовпадение паролей, возврат существующего пользователя после входа, создание и отзыв приглашения.

Общий набор frontend содержит независимый существующий сбой `tests/noteFilters.test.mjs`: модуль загружается через data URL и не может разрешить относительный импорт `./notesText`. Эти файлы не изменялись в задаче. Общая генерация Swagger также уже останавливается на существующих типах `service.NotebookResearchJobError` / `alem.ModelListResponse`; комментарии новых обработчиков и контракт в этом документе актуальны, существующие generated Swagger-файлы не перезаписаны.

Реализация подготовлена локально. Производственные данные, SMTP, realm и сервер в ходе разработки не изменялись.
