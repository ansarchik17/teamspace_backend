# BAS-017 BE-04: сотрудники компании

## Административный список

GET `/api/v1/organizations/current/administration/users` — директор своей компании.
GET `/api/v1/platform/organizations/:organization_id/administration/users` —
администратор платформы, выбранная компания.

Bearer JWT обязателен. `q` — поиск по ФИО, username, email и должности
(до 255 символов); `limit` — 1–100, по умолчанию 25; `offset` — от 0.
Поиск не учитывает регистр; `%` и `_` — обычные символы, а не wildcard.
Ответ: `{items: [...], total, limit, offset}`, порядок по ID сотрудника.
У сотрудника: `id`, `full_name`, `username`, `email`, `position`, `role`,
`is_active`, `is_blocked`, `is_director`. Удалённые сотрудники исключены.
Пароли, токены и Keycloak ID не выдаются. Ответ имеет `Cache-Control: no-store`.

## Блокировка и разблокировка

PUT `/api/v1/organizations/current/administration/users/:user_id/block`
PUT `/api/v1/platform/organizations/:organization_id/administration/users/:user_id/block`

Тело `{"blocked":true}` блокирует; `{"blocked":false}` снимает блокировку
и активирует сотрудника. Поле обязательно и должно быть boolean.
Успех — HTTP 204. Повторная операция безопасна; каждое успешное выполнение
записывается в аудит как `user.block.update` с состоянием до/после.

Разрешено только администратору платформы на platform API и назначенному
директору на current API. Сотрудник другой компании или удалённый сотрудник
возвращает `NOT_FOUND` / 404. Собственный аккаунт, действующий директор и
администратор платформы защищены от изменения этим API — `FORBIDDEN` / 403.
Перед блокировкой директора платформа должна назначить другого владельца.

Блокировка хранится отдельно от данных Keycloak. Триггер БД не позволяет
синхронизации или обычному обновлению профиля снова активировать блокированного
сотрудника. Изменение статуса и аудит сохраняются в одной транзакции; сбой аудита
откатывает блокировку. Для приостановленной компании изменение запрещено.

В production проверяется актуальная активность в БД при проверке ранее
выданных локальных access/refresh JWT и выдаче новых токенов. Вход с Keycloak
токеном также проверяет активность после синхронизации. Заблокированный аккаунт
не может использовать защищённые API. Недоступность БД не разрешает доступ.
Разблокировка снова разрешает действующие, не отозванные и не истёкшие токены.

WebSocket-сессии на текущем сервере закрываются после блокировки. На других
экземплярах проверка выполняется перед приёмом/отправкой сообщений и heartbeat
(период 9 секунд). Уже начавшийся запрос не отменяется задним числом.
Блокировка Workspace не изменяет учётную запись в самом Keycloak и не является
отзывом сессий сторонних приложений.

## Права и структура

Используются существующие endpoints структуры и `access-management`:
`position` создаёт должность, `policy` задаёт права должности, `member`
назначает её сотруднику, `unassign` снимает назначение. Проверки компании
и аудит сохранены. Этот механизм не назначает глобальную роль `admin`.
Изменение глобальных ролей остаётся отдельной возможностью платформы.
