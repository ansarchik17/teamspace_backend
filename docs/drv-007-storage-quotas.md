# DRV-007 — квоты Drive и лимиты загрузки (только бэкенд)

Добавлены персональные квоты и единый расчёт занятого/свободного места.
По умолчанию квота — 10 GiB (10 737 418 240 байт) на владельца файлов.
Загрузка в общую папку расходует квоту владельца нового файла (загрузившего
пользователя); редактирование чужого файла расходует квоту владельца файла.
Файлы, к которым только предоставлен доступ, в квоту получателя не входят.

## Контракт для фронтенда

С авторизацией: `GET /api/v1/drive/storage` (Cache-Control: no-store).
Ответ содержит:

```json
{
  "quota_bytes": 10737418240,
  "used_bytes": 1000,
  "free_bytes": 10737417240,
  "active_bytes": 700,
  "version_bytes": 200,
  "trash_bytes": 100,
  "max_upload_bytes": 1073741824,
  "max_request_bytes": 1074790400,
  "max_files_per_request": 20,
  "upload_limits": {
    "file": 524288000,
    "image": 52428800,
    "audio": 104857600,
    "video": 1073741824
  },
  "quota_exceeded": false,
  "can_upload": true
}
```

`GET /api/v1/drive/summary` сохраняет существующие поля и добавляет `storage`
с этой структурой. Его `used_bytes` теперь учитывает ревизии и корзину,
а не только текущие активные файлы. `active_bytes` соответствует прежнему
показателю. Все объёмы передаются целыми байтами, `free_bytes` не бывает меньше 0.
При заполнении ровно до лимита `can_upload=false`, `quota_exceeded=false`.
Флаг `quota_exceeded=true` означает, например, что администратор уменьшил квоту
ниже текущего использования. Фронтенд может показывать заполнение по отношению
used_bytes/quota_bytes, отдельно обрабатывая quota_bytes=0.

Отказ в загрузке из-за места: HTTP **507**, `error.code=DRIVE_QUOTA_EXCEEDED`,
понятный `error.user_message`. При предварительной проверке `error.details`
содержит quota_bytes, used_bytes, free_bytes, requested_bytes. При отказе
транзакционной проверки — quota_bytes, required_bytes (итоговый объём
незафиксированной операции), owner_id. Не нужно считать required_bytes
актуальным объёмом: операция откатилась. Обновите storage после ошибки.

Превышение размера файла/запроса — HTTP **413**, `error.code=FILE_TOO_BIG`.
Конкурентное изменение хранилища, требующее повтора, — HTTP **409**.
Без авторизации storage возвращает 401. Пользователь не может менять квоту
или запрашивать статистику другого пользователя через этот endpoint.

## Что занимает место

- Текущие активные файлы + сохранённое историческое содержимое.
- Файлы и все их ревизии в корзине менее 720 часов.
- Повторное использование одного объекта в рамках одного файла (восстановление
  старой версии) считается один раз. Восстановление версии или объекта из
  действующей корзины не требует повторного выделения этого места.
- Копии — отдельные логические файлы, поэтому считаются отдельно, даже если
  MinIO-объект общий. Копирование не позволяет обойти квоту.
- По истечении 720 часов объект перестаёт занимать логическую квоту. Как и в
  DRV-006, физическое удаление объектов MinIO — отдельный процесс; used_bytes
  не является размером бакета. Файлы с scope вне drive не учитываются.

## Ограничения и защита от обхода

На обычную multipart-загрузку разрешено до 20 файлов, суммарное тело запроса
до 1 GiB + 1 MiB служебных данных. Предел применяется и без Content-Length.
Категорийные лимиты остаются: обычный файл/новая версия — 500 MiB,
картинка — 50 MiB, аудио — 100 MiB, видео — 1 GiB; настройка аккаунта может
их уменьшить. Внешний импорт ограничен также существующими 100 MiB.
OnlyOffice проверяет квоту владельца перед сохранением; ответ без известной
длины читается с пределом во временный файл, который удаляется после запроса.

Перед отправкой в MinIO выполняется предварительная проверка. Окончательная
проверка выполняется триггерами PostgreSQL в транзакции записи files/file_versions.
Она покрывает версии, OnlyOffice, внешние импорты, экспорт Notes, копирование
файлов/папок, восстановление и передачу владения. Ошибка откатывает транзакцию.
Проверки сериализуются записью в строку аккаунта. Для конкурентных транзакций
REPEATABLE READ (копирование) возможен 409 с требованием повторить запрос.
Одной проверки свободного места вне транзакции недостаточно — она не является
резервированием объёма на время передачи файла.

При определённом отказе квоты/лимита загруженный, но не сохранённый объект
удаляется. Неопределённые ошибки commit при обновлении ревизии оставляются
существующему процессу сверки, чтобы не удалить реально зафиксированный объект.
Несколько файлов одного multipart-запроса записываются последовательно:
предварительно проверяется суммарный размер; если последующий файл не прошёл
проверку, `error.details.uploaded_files` и `uploaded_count` перечисляют уже
сохранённые файлы. Полной атомарности HTTP-пакета нет.

## Настройка и развёртывание

Применить миграцию `20260927140000_drive_storage_quotas.sql` перед запуском
нового кода. Новые зависимости и изменения фронтенда не нужны. Существующие
файлы учитываются сразу, отдельный пересчёт/перезапись не требуются.

Оператор БД может настроить политику по умолчанию:

```sql
UPDATE drive_storage_policy
SET quota_bytes = 10737418240, max_upload_bytes = 1073741824
WHERE singleton;
```

Индивидуальное ограничение (например, user_id=123):

```sql
INSERT INTO drive_storage_accounts(user_id, quota_bytes, max_upload_bytes)
VALUES (123, 5368709120, 104857600)
ON CONFLICT(user_id) DO UPDATE
SET quota_bytes=EXCLUDED.quota_bytes, max_upload_bytes=EXCLUDED.max_upload_bytes;
```

NULL в индивидуальных полях означает использование общей политики.
Нулевая квота запрещает добавлять положительный объём. Чтение, скачивание,
переименование и удаление существующих файлов остаются доступны после
уменьшения квоты; для освобождения логической квоты учитывайте срок корзины.

## Проверки

Тесты Drive с временным PostgreSQL покрывают расчёт места, точную границу,
истечение корзины, восстановление без двойного учёта, сохранение истории,
квоту владельца при редактировании, отказ до MinIO, откат записи/рекурсивного
копирования, передачу владения и конкурентные загрузки/копии. HTTP-тесты
проверяют ограничение тела запроса и количества файлов, тесты OnlyOffice —
ответы с известной и неизвестной длиной. Реальные байты ревизий дополнительно
проверяются существующим тестом с S3 HTTP-фикстурой.

```sh
TEST_MESSENGER_DATABASE_URL='postgres://.../test?sslmode=disable' \
  go test ./internal/service ./internal/handler ./internal/apperrors -run TestDrive -count=1
```

Тесты создают и удаляют изолированные схемы. Полный TestDriveStructureIntegration
дополнительно требует тестовый MinIO; он пропускается, если адрес не задан.
