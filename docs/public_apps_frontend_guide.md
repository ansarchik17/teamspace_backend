# Public Apps Frontend Guide

## Назначение

Этот документ для frontend-команды, которая будет внедрять изменения в Alem Store и в смежные экраны, работающие с `public apps`.

Документ описывает:

- что именно изменилось в backend по `public apps`
- какие поля теперь приходят в API
- как безопасно использовать новые возможности в новом Store
- что важно не сломать для старых клиентов
- как работать с категориями, тегами и анонимным рейтингом

Все примеры ниже относятся к backend этого репозитория и маршрутам под `/api/v1`.

---

## Коротко: что мы сделали

Для `public apps` в backend добавлены:

- теги приложения `tags`
- категория приложения `category`
- анонимный рейтинг пользователей от `1` до `5`
- агрегированные поля:
  - `average_rating`
  - `rating_count`
  - `my_rating`
- новый режим сортировки списка по рейтингу через query-параметр `sort=rating`
- фильтр списка по категории через query-параметр `category`

При этом специально сохранена совместимость:

- старые маршруты не удалены и не переименованы
- старые поля ответа сохранены
- новые поля только добавлены
- старый порядок списка `public apps` сохранён по умолчанию
- сортировка по рейтингу включается только явно

Это значит, что старая мобилка не должна сломаться, если продолжит вызывать API как раньше.

## Базовый URL

Во всех примерах ниже:

```text
BASE_URL=https://YOUR_HOST/api/v1
```

Все запросы требуют авторизацию:

```http
Authorization: Bearer <ACCESS_TOKEN>
```

---

## Что осталось совместимым

Следующие вещи работают как раньше:

- `GET /public-apps`
- `GET /public-apps/:id`
- `POST /public-apps`
- `PUT /public-apps/:id`
- `DELETE /public-apps/:id`
- `PUT /public-apps/reorder`

Старый frontend может ничего не менять, если ему не нужны теги и рейтинг.

### Важно про совместимость

По умолчанию список `public apps` всё ещё сортируется по старому порядку:

```text
sort=position
```

Это поведение используется автоматически, даже если параметр `sort` вообще не передан.

Новая сортировка по рейтингу включается только так:

```text
GET /public-apps?sort=rating
```

## Модель `PublicApp`

Теперь backend возвращает объект приложения с новыми полями:

```json
{
  "id": 12,
  "app_name": "AlemGPT",
  "link": "https://example.com/app",
  "app_photo": "https://example.com/icon.png",
  "created_at": "2026-04-06T10:00:00Z",
  "updated_at": "2026-04-06T10:00:00Z",
  "is_global": false,
  "is_private": false,
  "web_view": true,
  "position": 7,
  "category": "ИИ",
  "tags": ["AI", "Demo"],
  "average_rating": 4.67,
  "rating_count": 3,
  "my_rating": 5
}
```

### Значение полей

`id`

- идентификатор приложения

`app_name`

- название приложения

`link`

- ссылка на приложение

`app_photo`

- иконка или изображение приложения

`is_global`

- приложение доступно глобально

`is_private`

- приложение приватное и может быть доступно не всем

`web_view`

- открывать ли приложение через webview

`position`

- старое поле ручного порядка
- по-прежнему важно для старых экранов и reorder

`category`

- хранимая категория приложения из `public_apps.category`
- возможные значения: `ИИ`, `Документация`, `Прочие`
- если категория не задана у старой записи, backend определяет её по названию, ссылке и тегам

`tags`

- массив строк
- может быть пустым: `[]`
- backend чистит пустые теги и убирает дубликаты

`average_rating`

- средняя оценка приложения
- округляется backend до двух знаков после запятой
- если оценок нет, приходит `0`

`rating_count`

- количество всех оценок
- если оценок нет, приходит `0`

`my_rating`

- оценка текущего пользователя
- если пользователь ещё не оценивал приложение, поле будет `null` или может отсутствовать в зависимости от JSON-serializing клиента

## Список приложений

## 1. Получить список `public apps`

Endpoint:

```http
GET /api/v1/public-apps
```

Поддерживаемые query-параметры:

- `name` — поиск
- `category=ИИ|Документация|Прочие` — фильтр по категории
- `downloaded=true|false` — фильтр по установленным/неустановленным
- `sort=position|rating` — режим сортировки

### Важно про поиск

Поиск теперь работает не только по `app_name`, но и по тегам.

Пример:

```http
GET /api/v1/public-apps?name=ai
```

Такой запрос может найти:

- приложение с названием `AlemGPT`
- приложение с тегом `AI`

### Режимы сортировки

`sort=position`

- старое поведение
- использовать для совместимости и старых экранов

`sort=rating`

- новый Store/каталог может использовать это для витрины "лучшие приложения"
- backend сортирует по:
  1. `average_rating DESC`
  2. `rating_count DESC`
  3. `position ASC`
  4. `id DESC`

### Примеры запросов

Старое поведение:

```http
GET /api/v1/public-apps
```

Новый Store по рейтингу:

```http
GET /api/v1/public-apps?sort=rating
```

Поиск по тегу и сортировка по рейтингу:

```http
GET /api/v1/public-apps?name=ai&sort=rating
```

Только неустановленные:

```http
GET /api/v1/public-apps?downloaded=false
```

### Пример ответа

```json
[
  {
    "id": 12,
    "app_name": "AlemGPT",
    "link": "https://example.com/app",
    "app_photo": "https://example.com/icon.png",
    "created_at": "2026-04-06T10:00:00Z",
    "updated_at": "2026-04-06T10:00:00Z",
    "is_global": false,
    "is_private": false,
    "web_view": true,
    "position": 7,
    "tags": ["AI", "Demo"],
    "average_rating": 4.67,
    "rating_count": 3,
    "my_rating": 5
  }
]
```

## Теги

## Что frontend должен знать

Теги — это обычный массив строк:

```json
["Документация", "AI", "Demo"]
```

Backend:

- убирает пустые строки
- убирает дубликаты без учёта регистра
- хранит теги прямо у приложения

### Рекомендации для UI

В Store лучше показывать теги как chips/pills:

- компактно
- максимум 2-3 тега на карточке
- остальные можно скрывать под `+N`

### Если тегов нет

Если `tags.length === 0`:

- не показывайте пустой контейнер
- просто скрывайте блок тегов

### Важно

Отдельного backend endpoint "получить все доступные теги" сейчас нет.

Если нужен sidebar/filter по всем тегам, есть два варианта:

1. собирать уникальные теги из текущего списка приложений на frontend
2. завести позже отдельный endpoint под каталог тегов

На текущий момент для первого релиза можно спокойно использовать вариант 1.

---

## Анонимный рейтинг

## Что backend гарантирует

Рейтинг анонимный в том смысле, что frontend не получает список пользователей, которые поставили оценку.

Frontend видит только:

- средний рейтинг `average_rating`
- количество оценок `rating_count`
- свою собственную оценку `my_rating`

Backend не отдаёт:

- кто именно поставил оценку
- список оценок по пользователям

### Важная бизнес-логика

- один пользователь может иметь только одну активную оценку на одно приложение
- пользователь может менять свою оценку
- пользователь может удалить свою оценку

---

## 1. Поставить или изменить оценку

Endpoint:

```http
POST /api/v1/public-apps/:id/rating
```

Body:

```json
{
  "rating": 5
}
```

Допустимые значения:

- `1`
- `2`
- `3`
- `4`
- `5`

### Пример запроса

```bash
curl -X POST "$BASE_URL/public-apps/12/rating" \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "rating": 5
  }'
```

### Что вернёт backend

Backend возвращает уже обновлённый объект `PublicApp`.

Это удобно для frontend:

- не нужно отдельно перезапрашивать карточку
- можно сразу заменить локальный объект приложения ответом сервера

Пример ответа:

```json
{
  "id": 12,
  "app_name": "AlemGPT",
  "link": "https://example.com/app",
  "app_photo": "https://example.com/icon.png",
  "created_at": "2026-04-06T10:00:00Z",
  "updated_at": "2026-04-06T10:00:00Z",
  "is_global": false,
  "is_private": false,
  "web_view": true,
  "position": 7,
  "tags": ["AI", "Demo"],
  "average_rating": 4.5,
  "rating_count": 4,
  "my_rating": 5
}
```

### Как использовать в UI

После успешного ответа:

- обновить `my_rating`
- обновить `average_rating`
- обновить `rating_count`
- если открыт список, обновить карточку в списке
- если открыт detail screen, обновить detail screen

---

## 2. Удалить свою оценку

Endpoint:

```http
DELETE /api/v1/public-apps/:id/rating
```

### Пример запроса

```bash
curl -X DELETE "$BASE_URL/public-apps/12/rating" \
  -H "Authorization: Bearer <ACCESS_TOKEN>"
```

### Что вернёт backend

Backend снова возвращает обновлённый объект `PublicApp`.

После удаления:

- `my_rating` станет `null`
- `average_rating` может измениться
- `rating_count` может уменьшиться

## Рекомендации по UI для Alem Store

## Карточка приложения

На карточке приложения рекомендуется показывать:

- иконку
- название
- 1-3 тега
- среднюю оценку
- количество оценок
- действие: открыть / установить / подключить

### Пример отображения рейтинга

Если есть оценки:

```text
4.7 ★ (128)
```

Если оценок нет:

```text
Нет оценок
```

### Отдельно про звёзды

Для выбора своей оценки удобнее использовать:

- 5 интерактивных звёзд
- hover/press preview
- подтверждение по клику

Если `my_rating = 4`, можно подсветить первые 4 звезды.

## Рекомендации по UX

### 1. Не ломать старую страницу

Если экран был старый и уже завязан на существующий порядок:

- продолжайте использовать `GET /public-apps` без `sort`

### 2. Для нового Alem Store

Если делаете новый каталог приложений:

- используйте `GET /public-apps?sort=rating`

### 3. Для поиска

Frontend может не знать, что поиск идёт ещё и по тегам.
Это нормально.

Достаточно просто отправлять:

```http
GET /public-apps?name=<user_input>
```

Backend сам найдёт и по названию, и по тегам.

### 4. Для фильтра "AI", "Документация", "Demo"

Есть два пути:

1. frontend фильтрует по уже загруженным `tags`
2. frontend отправляет `name=AI` и получает backend search

Для первого релиза лучше:

- загрузить список
- построить фильтрацию по тегам локально

Это быстрее и проще для UX.

## Рекомендуемый frontend flow

## Вариант 1. Старый экран, ничего не ломаем

1. Вызываем `GET /public-apps`
2. Показываем карточки как раньше
3. Если нужно, постепенно добавляем рендеринг:
   - `tags`
   - `average_rating`
   - `rating_count`

## Вариант 2. Новый Alem Store

1. Вызываем `GET /public-apps?sort=rating`
2. Строим каталог по рейтингу
3. Показываем теги как chips
4. Показываем рейтинг и число оценок
5. Даём пользователю поставить свою оценку
6. После ответа backend заменяем локальный объект приложения свежим ответом

## Вариант 3. Экран деталей приложения

1. Открываем `GET /public-apps/:id`
2. Показываем:
   - большую иконку
   - название
   - теги
   - средний рейтинг
   - число оценок
   - свои звёзды `my_rating`
3. При оценке вызываем `POST /public-apps/:id/rating`
4. При снятии оценки вызываем `DELETE /public-apps/:id/rating`
5. Локально заменяем состояние ответом backend

## Edge cases

## 1. Нет тегов

Пример:

```json
"tags": []
```

Что делать:

- не рендерить пустой блок тегов

## 2. Нет оценок

Пример:

```json
"average_rating": 0,
"rating_count": 0,
"my_rating": null
```

Что делать:

- не показывать `0.0 ★`
- лучше показать `Нет оценок`

## 3. Пользователь ещё не оценивал

Пример:

```json
"my_rating": null
```

Что делать:

- показывать пустые звёзды
- не считать это ошибкой

## 4. Пользователь меняет оценку

Пример:

- было `my_rating = 3`
- пользователь нажал `5`
- frontend снова делает `POST /rating` с новым значением

Это нормальный сценарий.

## 5. Пользователь удаляет оценку

Если в UI предусмотрена кнопка:

- `Убрать оценку`
- `Сбросить`
- крестик возле своего рейтинга

тогда используйте `DELETE /rating`.

## Ошибки

Типовые ошибки:

### 400 Bad Request

Например:

- рейтинг вне диапазона `1..5`
- невалидный JSON

### 404 Not Found

Например:

- приложение не существует
- приложение недоступно текущему пользователю

### 500 Internal Server Error

- внутренняя ошибка backend

### Рекомендуемое поведение frontend

При ошибке рейтинга:

- не менять локальное состояние окончательно
- откатить optimistic update, если он был
- показать toast/snackbar:
  - `Не удалось сохранить оценку`

---

## Что важно не делать на frontend

- не ожидать список пользователей, поставивших оценки
- не рисовать `0 ★`, если `rating_count = 0`
- не переводить все старые экраны на `sort=rating` автоматически
- не полагаться на порядок по рейтингу без явного query-параметра
