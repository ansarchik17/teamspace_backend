# CAL-003 — повторяющиеся события и отдельные повторения

Backend поддерживает ежедневные, еженедельные и ежемесячные серии, а также изменение, удаление и восстановление одного экземпляра серии. Все указанные ниже маршруты требуют Bearer-токен. Изменять серию или экземпляр может только организатор; приглашённый участник может просматривать исключения события, к которому имеет доступ.

## Правило повторения

В `POST /api/v1/calendar/events` и `PUT /api/v1/calendar/events/{id}` можно передать старый формат `"recurrence_rule": "DAILY" | "WEEKLY" | "MONTHLY"` с отдельными `recurrence_interval` и `recurrence_until` либо поддерживаемое подмножество RFC 5545:

```json
{"recurrence_rule":"RRULE:FREQ=WEEKLY;INTERVAL=2;UNTIL=20261231T235959Z"}
```

Допустимы только `FREQ=DAILY|WEEKLY|MONTHLY`, `INTERVAL=1..3650` и `UNTIL=YYYYMMDDTHHMMSSZ` в UTC. `BYDAY`, `COUNT`, `BYMONTHDAY` и другие части RRULE **не поддерживаются** и возвращают `400`, а не игнорируются. Backend хранит нормализованные значения отдельно и возвращает в `recurrence_rule` частоту (`WEEKLY`), а не исходную строку RRULE. `recurrence_until` включительно для начала повторения.

`POST /api/v1/calendar/grid` и `GET /api/v1/calendar/events` возвращают экземпляры с одинаковым `id` серии и уникальным `occurrence_id` вида `{event_uuid}:{original_start_unix_seconds}`. При переносе экземпляра суффикс остаётся равным **исходному** времени начала, чтобы его можно было редактировать или восстанавливать дальше. Диапазон календаря — полуоткрытый `[start, end)`; в ответ попадают и перенесённые в диапазон экземпляры.

## Изменить одно повторение

```http
PUT /api/v1/calendar/events/{event_id}/occurrences/{original_start_unix_seconds}
Content-Type: application/json
Authorization: Bearer <token>

{"title":"Особая встреча","start_time":"2026-10-02T12:00:00Z","end_time":"2026-10-02T13:00:00Z","location":"Переговорная 2"}
```

Можно менять `title`, `description`, `start_time`, `end_time`, `location`, `is_all_day`. Передавать хотя бы одно поле обязательно. Непереданные поля сохраняют прежнее значение. `end_time` должен быть строго позже `start_time`. `calendar_id`, состав участников, онлайн-комнату и правило серии здесь менять нельзя. Для всей серии используется обычный `PUT /api/v1/calendar/events/{id}`.

Ответ `200` — объект исключения с `id`, `event_id`, `occurrence_date`, `exception_type: "modified"`, `event_data` (полный снимок изменяемых полей), `created_at`, `updated_at`. Повторный PUT для той же даты обновляет то же исключение.

## Удалить или восстановить одно повторение

```http
DELETE /api/v1/calendar/events/{event_id}/occurrences/{original_start_unix_seconds}
```

Ответ `200` — исключение с `exception_type: "deleted"`. Остальные экземпляры серии остаются. Повторный DELETE идемпотентен.

```http
GET /api/v1/calendar/events/{event_id}/exceptions
```

Ответ `200`: `{ "exceptions": [ ... ] }` (пустой массив, если нет исключений). Доступ только организатору и участникам события.

```http
DELETE /api/v1/calendar/events/{event_id}/exceptions/{exception_id}
```

Ответ `200`: `{ "message": "ok" }`. Восстанавливает исходное повторение, удаляя исключение. Повторный вызов возвращает `404`.

## Ошибки и ограничения

- `400` — неверный RRULE, timestamp, пустое изменение, неверный интервал или вызов для неповторяющегося события.
- `403` — пользователь не организатор при изменении; просмотр исключений недоступного события не раскрывает его данные.
- `404` — событие, исходное повторение или исключение не найдены.
- Все SQL-запросы параметризованы. Исключения привязаны внешним ключом к событию и удаляются при физическом удалении серии.
- В одном ответе разворачивается не более 3000 повторений одного события; старые серии начинают расчёт рядом с запрошенным диапазоном.

Важно: перенос одного повторения не создаёт отдельного списка участников, напоминания или ссылки онлайн-встречи; они остаются общими с серией. При изменении правила всей серии исключения с датами, которых больше нет в новой серии, сохраняются в БД, но не отображаются.
