# CNT-007 — Офбординг и передача рабочих данных

## API

Активный владелец компании или роль `admin` в своей активной компании:

`POST /api/v1/contacts/{user_id}/offboarding?dry_run=true`, BearerAuth, JSON до 4 KiB:

```json
{
  "successor_id": 42,
  "reason": "Завершение трудовых отношений"
}
```

`dry_run=true` по умолчанию: выполнить все проверки и операции передачи в
транзакции, затем откатить. Для применения отправить тот же запрос с
`dry_run=false`. Преемник — активный неудалённый сотрудник той же компании,
кроме guest; может быть действующим администратором. Сотрудник не может быть
преемником самого себя или выполнять собственный офбординг. Владельца любой
компании, платформенного admin и служебного support пользователя деактивировать
этим API нельзя. Сначала отдельно решить передачу управления компанией/ролью.
Уже неактивного сотрудника разрешено обработать для завершения передачи данных.

Ответ 200: user_id, successor_id, actor_id, reason, dry_run, applied,
offboarded_at, boards/projects/files/folders/units/direct_reports (счётчики),
handover_folder_id при наличии Drive, identity_sync_status=pending|complete.
Время/UUID папки в предпросмотре предварительные и не сохраняются. Изменения
между предпросмотром и применением проверяются заново. GET
`/api/v1/contacts/{user_id}/offboarding` доступен тем же администраторам и
возвращает сохранённый результат с текущим состоянием синхронизации Keycloak.
Это API работает и после исключения сотрудника из обычного Contacts.

Повторное применение с тем же сотрудником/преемником возвращает уже сохранённый
результат без повторной передачи (даже при dry_run=true). Причина, инициатор и
время остаются первоначальными. Другой преемник после применения — 409.
Неизвестные поля/неверный dry_run/неположительный ID/пустая или длиннее 500 символов
причина — 400; недостаточные права — 403; чужой/удалённый/неизвестный сотрудник
или отсутствующий audit GET — 404. Неверный преемник — 400 без раскрытия его
данных. Конфликт/конкурентное изменение/таймаут блокировки — 409. Нехватка квоты
Drive — 507; превышение лимита принимаемого файла — 413. Любой отказ откатывает
всю передачу, аудит и деактивацию.

## Что происходит при применении

Одна транзакция PostgreSQL:

1. Владение досками и проектами сотрудника, включая архивные записи, передаётся
   преемнику. `projects.owner_id` отделён от неизменяемого `created_by`;
   существующие проекты получают owner_id=created_by при миграции. Преемник
   получает owner на переданных досках и не меньше editor на других досках с
   переданными проектами. Права досок действуют на всю доску, согласно модели
   Kanban; это следует показать при подтверждении передачи. Старая запись
   участника собственной доски остаётся с ролью member. Проект на доске,
   принадлежащей пользователю вне компании, вызывает 409: сначала устранить
   такую legacy-связь. Проекты других сотрудников не меняются.
2. Все собственные Drive-файлы (`scope=drive`) и папки, включая корзину,
   передаются преемнику. Создаётся отдельная непубличная папка «Передано от
   сотрудника ID». Вложенность собственных папок сохраняется, корни и файлы
   в чужих папках перемещаются в контейнер передачи. Имена, UUID ресурсов,
   object_name, байты, версии, авторы версий и deleted_at сохраняются. Квота
   учитывает исходные версии/корзину по штатным правилам Drive. Объекты MinIO
   не копируются и не удаляются. Если настроен Elasticsearch content search,
   после коммита запускается последовательное асинхронное обновление индекса
   переданных файлов (до 60 секунд на файл/30 минут на пакет). Это штатный
   best-effort индекс: при сбое или перезапуске повторить применённый POST с тем
   же преемником для повторного обновления; основная передача повторно не идёт.
   До обновления индекса файлы доступны в обычном Drive, но поиск по содержимому
   может их не находить. Проверка выдачи поисковых результатов берёт текущий ACL
   из БД и не раскрывает ресурс по устаревшей записи индекса.
3. Преемнику назначается owner ACL; прямые права уходящего пользователя на
   переданные ресурсы удаляются. Остальные адресные права сотрудников
   сохраняются. Публичность переданных ресурсов отключается, существующие
   bearer-ссылки на них истекают, сами записи ссылок/авторство сохраняются.
   Преемник может выдать новые ссылки. Ключи ONLYOFFICE переданных файлов
   меняются, чтобы старые сессии/колбэки не продолжали редактирование.
   Перед применением сохранить и закрыть открытые редакторы передаваемых
   документов: сохраняются уже записанные версии, а несохранённый буфер старой
   сессии DocumentServer после смены ключа не принимается. Предпросмотр сам
   не выполняет force-save и не меняет ключи после отката.
4. Руководство подразделениями передаётся преемнику. Прямые подчинённые
   переназначаются прежнему активному руководителю уходящего сотрудника либо получают
   manager_id=null. Это позволяет выбрать собственного подчинённого преемником
   без создания цикла и не назначает ему автоматически руководящую роль.
5. Пользователь получает is_active=false/status offline. Запись users и история
   сообщений, задач, версий/действий сохраняются. Авторы истории не заменяются.
   Назначения исполнителей задач, переписка, почта и календарь не переносятся:
   текущий объём передачи — доски/проекты, Drive и оргструктура.
6. В employee_offboardings сохраняются инициатор, причина, преемник, результат
   и идентификаторы переданных ресурсов. Одновременно сохраняется durable outbox
   для отключения Keycloak и завершения его сессий.

Для согласованной передачи используются advisory locks, совместимые с импортом
и оргструктурой, и кратковременные блокировки таблиц рабочих ресурсов. Это
административная операция: записи в Drive/Kanban могут кратко ожидать её
завершения. Lock timeout 5 секунд, statement timeout 30 секунд. При конфликте
повторить запрос. Предпросмотр использует те же блокировки и квоты.

## Блокировка доступа

После коммита локальная проверка JWT при каждом запросе читает активность users
из БД без кэша: ранее выданные access/refresh JWT тоже перестают работать.
Новые локальные токены не выдаются неактивному сотруднику. Password/PIN,
Keycloak code login и refresh проверяют активность. Raw Keycloak middleware не
реактивирует неактивного пользователя синхронизацией профиля. При недоступности
БД проверка доступа закрывается с ошибкой.

Открытые Messenger WebSocket проверяют активность перед каждым входящим и
исходящим сообщением, а также на ping; неактивное соединение закрывается.
Новые соединения проверяются штатной авторизацией. Уже выполняющийся запрос
или ранее скачанные данные отозвать нельзя. Ранее выданные прямые подписанные
URL хранилища действуют до собственного срока истечения. Доступ к другим продуктам с общей
SSO-сессией зависит от завершения отключения в Keycloak; локальный API не ждёт
его доступности.

Встроенный worker обрабатывает outbox сразу при старте и каждые 10 секунд,
до 10 записей за проход. Lease 1 минута, операция до 30 секунд; сбои повторяются
после истечения lease, в том числе после перезапуска процесса. Выключает
`enabled` пользователя в настроенном Keycloak realm, вызывает logout всех его
сессий и отзывает локальные сохранённые токены. Без привязанного Keycloak ID
отзывает локальные токены и завершает запись. Сбой любой операции оставляет
status=pending, локальный доступ уже заблокирован. Нужны действующие права
Keycloak admin на update/logout и существующая конфигурация Redis, если включён
token storage. Для другого внешнего IdP/realm отключение его аккаунта требует
отдельной интеграции; статус pending нужно контролировать через audit GET.
Пароли, токены и содержимое ошибок IdP в аудит не записываются.

Миграционные guards запрещают реактивацию, смену компании/SSO ID и soft delete
офбордированного пользователя через legacy-обновления или LDAP/AD. Новые рабочие
ресурсы нельзя назначать неактивному владельцу, в том числе из запроса, ожидавшего
транзакцию офбординга. Обычный admin update/HR-провижининг сначала проверяет
сохранённый офбординг, прежде чем менять внешний аккаунт. API возврата после
офбординга в текущей задаче не добавлен.

## Развёртывание и проверка

До запуска новой версии применить `20261001200000_employee_offboarding.sql`
после прежних миграций Contacts/Drive/Kanban. Новых env нет. Down удаляет owner_id,
аудит и очередь, но не отменяет уже выполненную передачу и не включает сотрудника
обратно. Перед откатом учитывать потерю аудита и незавершённых заданий.

Swagger обновлён. Фронтенд/production не менялись; интерфейсу нужны выбор
преемника, причина, предпросмотр, подтверждение применения и status Keycloak.

Проверки: go test ./..., одноразовая PostgreSQL с реальными миграциями Up/Down,
режимом prepared statements как в production и квотами Drive; матрица прав,
преемники/изоляция компаний, сухой запуск, rollback по квоте, конкурентная
идемпотентность, сохранение авторства/версий, ACL/старые ссылки/ONLYOFFICE key,
блокировка JWT/password/SSO/открытого WebSocket, защита от реактивации и повтор
outbox после сбоя. Регрессия Contacts CNT-001–007, Kanban, Drive/Docs прошла.
Keycloak update/logout проверены HTTP-эмулятором. Проверка реального Keycloak,
MinIO и браузерная приёмка офбординга в окружении компании не выполнены;
TestDriveStructureIntegration требует отдельные MinIO env и был пропущен.
