# Задача 4: отправитель ЭДО и неизменяемый outbox v1

Реализован в `workspace-odo-backend`, ветка `odo-integration`. Используется [контракт v1](odo-assignments-contract.md) и [приёмник задачи 3](odo-assignments-receiver.md). Фронтенд не меняется. Наличие локальной реализации не подтверждает развёртывание на production.

## Изменения

- Создание, редактирование деталей/срока/приоритета/подразделения/исполнителя и смена статуса записывают полный снимок в outbox в той же PostgreSQL-транзакции, что и изменение поручения. Ошибка outbox откатывает изменение.
- `workspace_revision` увеличивается под блокировкой строки. UUID события совпадает с outbox.id/event_id; event_id, payload, revision, компания и тип события защищены триггером от перезаписи.
- BFF и AI передают title/description/department/priority/result_comment при создании через расширенный совместимый protobuf. Нет промежуточного запроса записи деталей после создания. Старые клиенты с тремя полями продолжают работать: отправитель задаёт название «Поручение по документу».
- Результат выполнения и completed_at/closed_at сохраняются одновременно со статусом. Повтор той же смены статуса не создаёт новое событие; допустимость перехода повторно проверяется под блокировкой строки.
- PATCH поручения объединён в одну транзакцию. Пропущенные поля сохраняются; description, department_id и due_date можно очистить пустой строкой или null. Title и исполнитель обязательны и не очищаются. Существующие значения priority `normal`/`urgent` сохраняются в API ЭДО; снимки преобразуют их в `medium`/`critical`.
- Компания, issuer, timezone и публичная ссылка закрепляются при создании. Компания берётся из проверенного access context, автор — из текущего пользователя workflow; поля JSON не могут их подменять. Обновление не приписывает неизвестное историческое поручение компании действующего пользователя.

Начальный снимок создаётся в состоянии `held`. После успешных операций lifecycle/ACL workflow атомарно переводит его в pending. При ошибке lifecycle существующая компенсация удаляет поручение вместе с удержанными событиями, поэтому Workspace не получает отменённое создание. После аварии до подтверждения запись held сохраняется для проверенного восстановления; воркер не публикует её автоматически.

## Доставка и подтверждение

Воркер отправляет ровно сохранённый JSON. Он больше не читает актуальные детали assignments и не дополняет payload настройками в момент отправки. Повтор использует тот же event_id, body и `Idempotency-Key: odo-assignment:<event_id>`; пользовательские токены не используются.

Только HTTP 200 с согласованной квитанцией признаётся доставкой. Проверяются company/assignment/event/source, received_revision/current_revision, applied/outcome, UUID задачи/доски и source-поля возвращённой задачи. Неполный старый ответ 200 не считается успехом. Для duplicate/stale допускается более высокая текущая revision; stale требует current_revision выше полученной. Подтверждение outbox и таблицы сопоставления записывается одной транзакцией.

Повторные/конкурентные воркеры используют FOR UPDATE SKIP LOCKED, lease и fencing token. Истёкшая попытка не может подтвердить или отменить новую. `synced_revision` не уменьшается; подтверждение старой версии не скрывает новую pending-версию. Сбой после удалённого commit восстанавливается повтором неизменённого события с подтверждением duplicate.

| Ошибка | Действие |
| --- | --- |
| Сеть, timeout, 5xx, некорректный/неполный ack | Повторы с ограничением попыток и backoff |
| 401 Workspace | Повтор с новым client_credentials token |
| 429 | Повтор с учётом Retry-After |
| 400/403/404/409/422 Workspace | failed без автоматического повторения; исправить причину перед ручным retry |
| Неизвестная компания/issuer, старый или некорректный snapshot | failed до получения токена и отправки запроса |

Тела ошибок провайдера и токены не записываются в диагностику. Redirects запрещены для OAuth и доставки. Для 429 поддерживаются секунды и HTTP-date; Retry-After ограничен 24 часами. Максимум попыток задаётся ALEM_WORKSPACE_SYNC_MAX_ATTEMPTS. Таблица сопоставления хранит latest_revision/synced_revision; ошибки старых событий остаются в outbox и не откатывают состояние уже подтверждённой новой версии.

## Миграции и включение на production

1. Сначала развернуть Workspace receiver задачи 3 с миграцией `20261014000300_odo_assignment_sync_v1.sql` и сервисной авторизацией задачи 2.
2. В ЭДО применить новую workflow-миграцию `000018_workspace_assignment_snapshots.sql` и обновить BFF + workflow-service вместе. Существующий migrate runner применяет её из embedded workflow migrations.
3. Настроить выделенный Keycloak service client, audience, закреплённый service sub и одинаковый issuer по [документу авторизации](odo-assignments-service-auth.md).
4. Настроить подтверждённые компании и timezone источника. Новые параметры:

```dotenv
ALEM_WORKSPACE_SYNC_IDENTITY_ISSUER=https://identity.example.test/realms/Workspace
ALEM_WORKSPACE_SYNC_ALLOWED_ORGANIZATIONS=<company UUID>,<company UUID>
ALEM_WORKSPACE_ASSIGNMENTS_TIMEZONE=Asia/Almaty
# Необязательные отдельные значения для компаний:
ALEM_WORKSPACE_ASSIGNMENTS_TIMEZONES=<company UUID>:Asia/Almaty,<company UUID>:UTC
DOCUMENTOLOG_PUBLIC_URL=https://teamspace.kz/odo
```

Список timezone привязок проверяется на корректные UUID, дубликаты и IANA-зоны; Local запрещён. Если timezone не задана, используется явный fallback UTC. Нельзя считать timezone браузера timezone компании. Параметры должны соответствовать принятой политике сроков до создания поручений; закреплённая timezone существующей записи сама от изменения env не меняется.

`DOCUMENTOLOG_PUBLIC_URL` может включать базовый путь `/odo`. В Workspace при этом `ODO_ASSIGNMENTS_SOURCE_ORIGIN=https://teamspace.kz` — только scheme + host. Query, fragment, credentials и HTTP в публичной ссылке не допускаются. При пустом публичном URL source_url будет null.

`ALEM_WORKSPACE_ASSIGNMENTS_BOARD_ID` больше не используется: приёмник выбирает системную доску проверенной компании. Остальные OAuth/API/retry настройки задачи 2 сохраняются. Пользовательская синхронизация остаётся выключенной.

## Исторические данные и границы

Миграция не угадывает компании, issuer или версии старых поручений и не переписывает старые события. Старый outbox без полного v1 безопасно переводится в failed с диагностикой необходимости контролируемого backfill. Ручной retry неизменённой старой записи не исправляет её контракт. Новые записи без проверенной компании/issuer тоже сохраняют локальное поручение, но событие помещается в failed; новая компания не подставляется из последующего пользователя.

Перенос исторических поручений, доверенное сопоставление каталогов и восстановление незавершённых созданий held реализованы отдельным операторским CLI в [задаче 5](odo-assignments-backfill.md). Миграция workflow `000019` необходима и обычному sender: сохранённые связи используются для следующих снимков; состояния `held_backfill`/`superseded` обычный воркер не выбирает. [Команда выполнения задачи 6](odo-assignments-completion.md) создаёт completed-снимок в том же outbox атомарно с результатом и receipt (миграция `000020`). Подключение интерфейса — задача 7. Интеграция с реальным production Keycloak/Workspace отдельно не проверена.

Проверки: полный go test ./... и go vet ./...; PostgreSQL-тесты транзакционного rollback, immutable payload, concurrent revisions/workers, fencing, crash recovery, Retry-After, bounded retries, legacy quarantine, полный снимок через protobuf, completion timestamps/result, очистка полей и компания. Проверены примеры контрактов и публичный URL с `/odo`. Более старые интеграционные тесты, требующие отдельный TEST_WORKFLOW_DATABASE_URL, запускаются только на подготовленной workflow-БД; их нельзя направлять на случайную общую базу.
