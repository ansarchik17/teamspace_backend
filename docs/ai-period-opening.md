# Определение и открытие периодов ИИ: задача 09

Актуальное правило с 2026-10-22: новое пятичасовое окно открывается первым принятым запросом после истечения предыдущего, без привязки к постоянной сетке. Старые резервы остаются в исходном пятичасовом окне и в недельном финансовом учёте. Подробности и миграция: [контракт лимитов](ai-user-limits-contract.md#пятичасовое-окно-после-простоя).

Реализация: `internal/domain/ai_periods.go`, `internal/repository/ai_periods.go`. Используются таблицы миграций 05–06 без изменения их схемы.

## Определение и завершение

`domain.AIPeriodAt(anchor, now, duration)` определяет окно постоянной сетки `[start,end)`. Поддерживает только 168 часов и 5 часов. Применяет UTC и микросекундную точность PostgreSQL. Вычисления целочисленные, через UnixMicro, без float и без `time.Sub` для длинного простоя: последний насыщается примерно после 290 лет. Диапазон времён ограничен годами 1–9999; время до якоря, неподдерживаемая длительность и выход правой границы за диапазон дают `ErrAIInvalidPeriodTime`.

`Contains` проверяет полуоткрытую принадлежность; `Ended` возвращает true с точной правой границы. Завершение логическое: не удаляет историю, не сбрасывает резервы и не меняет настройки. Фоновый cron для закрытия окон не требуется. При отсутствии запросов никакие промежуточные окна не создаются; следующий запрос вычисляет нужное окно относительно исходного якоря, а не начинает новую сетку.

## Транзакционное открытие

`NewAIPeriodRepository(now)` принимает управляемый источник времени `func() time.Time`; nil использует серверный `time.Now`. `OpenForReservation(ctx, tx, organizationID, userID)` принимает **уже открытую pgx-транзакцию**, не коммитит её и не открывает отдельную транзакцию внутри.

Порядок:

1. Для личного плательщика блокирует строку пользователя, проверяет текущую компанию, active и отсутствие deleted_at.
2. Блокирует строку бюджета компании. Общий порядок блокировок: пользователь, затем бюджет; последующие сервисы должны его сохранять.
3. Читает часы один раз после получения блокировок. Ожидание конкурентного запроса не должно закрепить устаревшее окно.
4. Создаёт отсутствующий недельный якорь через ON CONFLICT DO NOTHING, читает сохранённый якорь, вычисляет окно, идемпотентно создаёт его и возвращает сохранённый UUID.
5. Для личного плательщика аналогично открывает пятичасовое окно userID. Для службы userID=nil: персональный якорь и окно не создаются.

Результат содержит ObservedAt, Weekly и опциональный FiveHour. Отдельные агрегаты личного/служебного расхода и сам резерв здесь не создаются: их атомарно добавит сервис резервирования.

**Вызывать только из сценария принятия резерва, не из GET.** В той же транзакции необходимо проверить роли, права ИИ, статус компании, квоты, политику и достаточный остаток, создать резерв и обновить счётчики. При любой ошибке caller обязан откатить всю транзакцию. Это гарантирует, что первый отклонённый запрос не оставит якорь. Нынешняя проверка членства — защита открытия личных окон, не полная авторизация платного вызова.

Read Committed используется по умолчанию. При Repeatable Read/Serializable возможны штатные конфликты сериализации, которые должен обрабатывать внешний транзакционный сценарий; repository не повторяет часть уже начатой транзакции самостоятельно.

При переводе компания получает свой недельный якорь, но сохраняется существующий персональный пятичасовой якорь. Старые периоды и их счётчики не изменяются, revision настроек не увеличивается. Повторное открытие не сбрасывает used/reserved.

## Границы задачи

Нет HTTP-маршрутов или подключения к текущим вызовам провайдера. Новая логика не включает ограничение ИИ сама по себе. Перенос удержания незавершённых резервов (carried), журнал попыток и атомарное списание реализуются следующими сценариями. Пока нельзя использовать полученное новое окно для выдачи полного бюджета без этих проверок. Для чтения текущих лимитов можно использовать чистый AIPeriodAt по сохранённому якорю, без вызова OpenForReservation.
