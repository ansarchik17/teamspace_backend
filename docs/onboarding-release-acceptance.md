# Локальная приёмка и подготовка выпуска приёма сотрудника

Дата: 22.10.2026. Пакет: `2026.10.22-rc.1`. Область по решению пользователя: **локальная приёмка и подготовка выпуска**. Рабочая компания не выбрана; рабочие назначения и шаблон не подставлялись. Коммиты, push, развёртывание и включение процесса на стенде/production не выполнялись.

## Что именно принято

Основная цепочка выполнялась обычной заявкой через API iForm на реальной одноразовой PostgreSQL с Flyway и Flowable. Внешний Workspace заменён контролируемым HTTP-адаптером; он моделирует отзыв ролей, состояния ЭДО/SD, потерю ответа, квитанции и запрет раннего доступа. Отдельно проверены настоящие серверные границы Workspace, ЭДО и SD, включая их интеграционные тесты с PostgreSQL. Эти два уровня проверки **не являются запуском всех четырёх сервисов одной общей сессией**.

Цепочка: решение руководителя → решение директора → подготовленный PDF и маршрут ЭДО → `completed` и завершённый маршрут → сотрудник с датой допуска → SD → ожидание IT → подготовка первого входа HR → подтверждение HR → уведомление инициатора.

Новая версия проверена как v2: существующая заявка сохраняет привязку к прежней v1, новая заявка использует v2. Номер v2 относится к синтетическому тестовому процессу; в рабочей компании номер определит сервер.

## Сценарии и результат

| Проверка | Результат |
| --- | --- |
| Нет действующего руководителя с правом согласования или нет директора | Отправка блокируется 422, остаётся тот же черновик, внешних операций нет |
| Отзыв роли согласующего после назначения | Прямое действие API получает 403; после восстановления выполняется |
| Возврат и исправление должности | Та же заявка, revision данных 1 → 2; устаревшие отправка и согласование получают 409 |
| Отказ руководителя и отказ директора | Два отдельных контрольных запуска завершаются REJECTED, внешних созданий нет |
| Отзыв HR у инициатора перед созданием ЭДО | Создание приостановлено, внешнего результата нет; после восстановления повторяется существующая операция |
| Потеря ответа после создания документа | Один документ; повтор использует те же PDF, входные данные и идентификатор операции |
| Черновик, регистрационный номер, registered, возврат, подпись и completed при активном маршруте | Сотрудник и SD ещё не создаются |
| Завершение всего ЭДО | Только `completed` вместе с завершённым маршрутом разрешает создать сотрудника |
| Три потерянных ответа создания сотрудника и повтор после инцидента | Сохраняются ID операции, occurrence, idempotency key и request hash; один внешний результат |
| Потеря ответа создания SD | Одна заявка SD с ID созданного сотрудника, датой и требованиями к месту |
| IT не закончил работу | Этап HR не открыт; подготовка пароля преждевременно недоступна |
| HR пытается завершить подготовку без настройки первого входа | 422; задача остаётся открыта |
| Подготовка первого входа заранее | Подготовка успешна, допуск до даты остаётся закрыт |
| Отзыв HR после подготовки пароля, затем перед финальным подтверждением | Оба прямых API-действия получают 403; после восстановления завершаются |
| Финал и повторные проходы воркера | COMPLETED; одно итоговое уведомление инициатору, новых внешних созданий нет |
| Отказ/отмена ЭДО, техническая ошибка, отмена заявки и поздний результат | Покрыты отдельной матрицей прежнего серверного сценария; преждевременного создания нет |
| Реальные квитанции Workspace/ЭДО/SD | Проверены отдельными тестами; для ЭДО и SD 12 конкурентных запросов создают один объект, изменённый payload получает конфликт |
| Дата допуска, отмена и обновление сессии | Отдельные тесты Workspace проверяют актуальную серверную функцию допуска, локальные/Keycloak JWT, сессии и авторизацию запросов |
| Браузер | 5 сценариев Edge: ожидание/возврат/отказ/отмена/ошибка, дата допуска, конфликт revision, отмена без старой даты; в том числе ширина 390 px |

Отказ завершает экземпляр, поэтому его нельзя одновременно выполнить на успешно завершившейся заявке. Для отказов использованы два контрольных экземпляра; исправление, отзыв прав, потеря ответов, IT, подготовка входа и финал прошли на **одной основной заявке**.

## Найденные и исправленные дефекты

1. После подготовки пароля назначенный HR мог завершить ручную задачу, уже утратив роль HR. Сервер теперь заново требует актуальную HR/TENANT_ADMIN на этапах `credentials` и `hr_confirmation`. Назначение задачи само по себе не сохраняет полномочия.
2. При потере ответа создания ЭДО PDF сохранялся, но JSONB менял порядок полей его описания. Квитанция Workspace хеширует вложенный JSON, поэтому повтор мог ошибочно считаться другим payload. Повторная подготовка теперь восстанавливает тот же порядок полей и тот же файл. HTTP-адаптер приёмки проверяет неизменность полного запроса; сценарий потери ответа проходит.

Изменений дизайна в этой задаче нет. Новых зависимостей и новых миграций для этих двух исправлений нет.

## Пакет выпуска iForm

В репозитории iForm добавлены:

- `scripts/prepare_onboarding_release.cjs` — локальный генератор без сетевых вызовов и публикации.
- `scripts/prepare_onboarding_release.test.cjs` — проверки детерминированности, обязательных назначений, версии шаблона и запрета случайных секретов.
- `examples/onboarding-release.company.example.json` — пустой пример настроек компании.

Скопировать пример в отдельный локальный файл и заполнить: UUID компании, IANA-пояс, ID **и утверждённую версию** шаблона, `workspace:<id>` регистратора/подписанта, UUID проекта/объекта/исполнителя/категории/приоритета SD. Наличие ID в файле ещё не доказывает права и принадлежность компании: это отдельно проверяется сервером. Токены и пароли в настройки не входят.

Из корня iForm:

```text
node scripts/prepare_onboarding_release.cjs --config company.local.json --out release/onboarding-2026.10.22
```

Каталог должен быть новым или пустым. Результат: `process.json`, `configure-draft.json`, `manifest.json`, `ENABLE.md`. Манифест содержит контрольные SHA-256 файлов, стабильный ключ повторной публикации и статус `PREPARED_NOT_ACTIVATED`. Хеш файла отличается от нормализованного `specification_hash`, который вернёт сервер; оба нужно сохранять.

Локальный синтетический пакет помечен `synthetic: true` и создаётся только с явным `--synthetic`. Его ID нельзя переносить в рабочую компанию. Подготовленный пакет проверен через API: создание нового пустого процесса → применение команд → validate → публикация в одноразовой тестовой компании. Узлы, поля и переходы совпали с принятой цепочкой. Генератор сам запросов не выполняет.

## Порядок обновления и включения

1. Зафиксировать состав изменений каждого репозитория, сохранить резервные копии и проверить ledger миграций. В checkout есть изменения других задач, поэтому выпускать весь dirty diff нельзя.
2. Проверить цепочки доступа из `access-rollout.md`. Workspace: существующие organization access/позиции/iForm access и `20261019000100_iform_operation_receipts.sql`; затем новая ранее подготовленная `20261022120000_employment_admission.sql` **до обновления кода Workspace**, использующего функцию допуска. SD: `20261019000100_ticket_idempotency.sql`. ЭДО: штатные последовательности auth/document/workflow, включая квитанции создания документа и маршрут. iForm: Flyway V1–V5 и штатное обновление Flowable. Промежуточные миграции не пропускать и не выполнять повторно вручную.
3. Обновить backend ЭДО и SD, затем Workspace backend, затем backend/frontend iForm. Для этого пакета Workspace frontend не требует нового изменения. Проверить действующие настройки межсервисного подключения и хранилища. Секреты в пакет выпуска не копировать.
4. Директору компании или суперадмину проверить пояс компании через существующий API настроек допуска. Пояс манифеста должен совпасть с фактическим. Проверить реальные права HR, регистратора, подписанта, руководителя, директора и исполнителя SD, подразделение и утверждённую версию шаблона. Самоподпись и самосогласование не разрешать в обход существующих ограничений.
5. Сформировать пакет с рабочими значениями без `--synthetic`. До включения допускается создать **новый пустой черновик** через `POST /api/v1/processes`. Проверить revision=1, отсутствие полей/публикации и только start/end. Использовать именно пустой процесс: пакет команд не предназначен для наложения на произвольный существующий черновик.
6. Применить `configure-draft.json` через `PATCH /api/v1/processes/{id}/draft`, затем вызвать `POST /api/v1/processes/{id}/validate`. Требуется valid=true без errors/unresolvedItems. При 409 не перезаписывать чужой черновик; сверить изменения. Сохранить новую revision и перепроверить маршруты/права в реальных ЭДО и SD.
7. В согласованный момент вызвать `POST /api/v1/processes/{id}/publish` с актуальной `{ "revision": N }` и `Idempotency-Key` из manifest. **Публикация сразу включает версию**: отдельной операции «опубликовать без активации» в API нет. Сохранить version ID/hash, затем пройти контрольную синтетическую заявку уже на общем стенде.
8. После проверки переключить точку запуска/ссылку компании на новый процесс. Архивирование старого процесса согласовать отдельно: оно закрывает форму и создание новых черновиков, но уже существующие черновики можно отправить по прежней версии. Для полной остановки старого приёма отдельно сверить и обработать такие черновики. Уже запущенные заявки сохраняют прежний version_id, автоматического переноса и повторного создания внешних объектов нет.

Новые переменные окружения этим пакетом не добавлены. Список настроек существующего подключения и ограничения повторов описаны в `employee-document-automation.md`, `onboarding-edo-wait.md`, `onboarding-employee-sd.md` и `onboarding-employment-admission.md`.

## Остановка и откат

Если контрольная заявка не проходит, закрыть создание новых черновиков: убрать новую ссылку и вызвать `POST /api/v1/processes/{id}/archive`. Ранее созданные черновики и запущенные заявки требуют отдельного разбора: архив сам их не останавливает. Это не удаляет историю и уже созданные аккаунты/документы/SD. Не публиковать старую версию поверх новой автоматически: рабочие экземпляры продолжают использовать собственную версию, их разбирает ответственный.

Сначала сверить квитанции и фактические объекты, затем повторять прежнюю операцию через существующее восстановление. Новую заявку ради сетевого сбоя не создавать. При необходимости остановить worker штатным способом, сохранив очередь и квитанции. Не удалять миграцию/функцию допуска ради отката: это может вновь открыть ранний вход. Откат кода и схемы требует отдельной проверки совместимости.

## Прогон и ограничения

Подробный результат текущего локального прогона и идентификаторы приведены ниже. Исходные JSON/BPMN, манифест и отчёт сохранены в локальном каталоге `.cache/onboarding-release/accepted` workspace-front; кэш не предназначен для Git или рабочего импорта.

Проверки Workspace: `go test` для domain/auth/handler/i18n/server; middleware с исключением `TestHTTPLoggingFormats`; repository с выборкой Employment/EmployeeCreation/Access/OrganizationAdministration/IForm. Известный тест логирования на Windows оставляет открытый файл и падает при cleanup; к кадровому процессу не относится и здесь не исправлялся.

Полный Maven-прогон iForm завершился с BUILD SUCCESS: 93 теста без падений, ошибок и пропусков. При остановке Surefire завершил fork JVM после 30-секундного таймаута; в логе также есть сообщения пула об уже остановленной Testcontainers-БД класса EngineIntegrationTest. Этот дефект очистки тестового окружения не устранён. Он не считается падением бизнес-сценария, но полностью чистым завершением JVM такой прогон не называется.

ЭДО: тесты Workflow/IForm, ручного запуска, проверок участника перед изменением и квитанций документа; SD: конкурентная идемпотентность создания. Оба прогона использовали настоящую отдельную PostgreSQL, а не пропуск из-за отсутствующей переменной окружения.

Браузерные тесты используют фикстуры компонентов с контролируемыми ответами API. Реальные ЭЦП, MinIO, корпоративный SSO, общий запуск всех четырёх сервисов и обновление копии производственной БД остаются для отдельной стендовой приёмки. Общие ворота релиза сервисов, включая контракт/Swagger ЭДО из `access-rollout.md`, не объявляются пройденными этим ограниченным кадровым прогоном.
