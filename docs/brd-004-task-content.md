# BRD-004 — содержимое задачи

Изменения только на бэкенде. Требуется миграция
`20260924000300_task_checklist_items.sql` до запуска новой версии.

## Подзадачи

Существующие методы: `POST /api/v1/kanban/tasks` с `parent_id`,
`PUT /api/v1/kanban/tasks/:id` с `parent_id` или `clear_parent_id: true`.
Родитель должен существовать на той же доске; самоссылка и циклы отклоняются.
В карточке `GET /api/v1/kanban/tasks/:id` возвращается `subtasks`.
Подзадача использует обычные методы редактирования/перемещения/удаления задачи.

При создании, изменении, перемещении или удалении подзадачи сервер отправляет
`kanban_subtasks_changed` для родительской карточки. При смене родителя обновляются
оба родителя. Поле `content.subtask_id` указывает изменённую подзадачу.

## Чеклист

В каждой задаче доступен список пунктов:

| Метод | Путь | Тело |
|---|---|---|
| GET | `/api/v1/kanban/tasks/:id/checklist` | — |
| POST | `/api/v1/kanban/tasks/:id/checklist` | `{"title":"Проверить отчёт"}` |
| PUT | `/api/v1/kanban/tasks/:id/checklist/:itemId` | `{"is_completed":true}` |
| DELETE | `/api/v1/kanban/tasks/:id/checklist/:itemId` | — |

Также поддерживаются те же методы по `/api/v1/kanban/tasks/:id/checklist-items`
и `/api/v1/kanban/tasks/:id/checklist-items/:itemId`. Для изменения пункта
доступны PUT и PATCH на обоих путях. GET не требует тела или Content-Type.

Создание возвращает `201`, остальные операции — `200`. PUT поддерживает
`title`, `is_completed` (в том числе `false`), `position`. Название — 1–500 символов
после trim. Позиция — 0–1000000; при создании без позиции пункт добавляется в конец.
Сортировка: `position`, затем дата создания и ID. Одинаковые позиции допустимы.
Пустой список — `[]`. Пустой PUT — `400`, чужой `itemId` — `404`.
Чтение доступно участникам доски; с BRD-007 изменение требует Editor/Admin.
Роль member совместима с Viewer (только чтение).

Событие `kanban_checklist_changed` содержит `content.action` (`created`, `updated`,
`deleted`), `content.item` для создания/изменения или `content.item_id` для удаления.

## Комментарии

Существующие `POST/GET /api/v1/kanban/tasks/:id/comments`,
`PUT/DELETE /api/v1/kanban/comments/:id` и загрузка фотографии
`POST /api/v1/kanban/tasks/:id/comments/photo` сохранены.
Текст обрезается по краям, максимум 10000 символов; нужен текст либо вложение.
Редактировать/удалять может автор с действующим доступом к доске задачи.
Удалённые комментарии не редактируются.

Сразу после сохранения запускается рассылка `kanban_comment_created`,
`kanban_comment_updated` (карточка комментария в `content`) или
`kanban_comment_deleted` (`content.comment_id`). HTTP-ответ не ждёт поиска
WS-получателей; жёсткая гарантия времени доставки не предоставляется.

## Вложения

- `POST /api/v1/kanban/tasks/:id/files` — multipart, поле `file`, до 500 МБ;
- `GET /api/v1/kanban/tasks/:id/files` — список с `download_url`;
- `GET /api/v1/kanban/tasks/:id/files/:fileId/download` — скачать;
- `DELETE /api/v1/kanban/tasks/:id/files/:fileId` — удалить;
- `POST /api/v1/kanban/tasks/:id/attachments` с `file_id` — прикрепить собственный
  файл из предварительной загрузки Kanban. Создаётся отдельный объект задачи.

Скачивание/удаление проверяют, что `fileId` принадлежит именно `taskId`.
Удаление доступно загрузившему файл, редактору или владельцу доски.
UUID в имени объекта исключает перезапись одноимённых загрузок за одну секунду.
Если сохранение метаданных не удалось, загруженный объект удаляется.
В случае ошибки создания комментария с фотографией выполняется очистка вложения.
Для реальной загрузки требуется доступное хранилище MinIO.

События: `kanban_attachment_created` (вложение в `content`) и
`kanban_attachment_deleted` (`content.attachment_id`). Старые общие объекты из
предварительных загрузок не удаляются вместе с одной привязкой к задаче.

## Доставка изменений

Все события содержат `type`, `board_id`, `task_id`, `from`, `timestamp`, `content`.
Получатели — владелец и текущие участники доски, включая отправителя и его сессии.
Входящие сообщения этих типов от клиента не нужны: запись выполняется через REST.
События не сохраняются, порядок асинхронной доставки не гарантируется. После события
можно перечитать соответствующий список; после переподключения нужно перечитать
карточку/списки через REST. Фронтенд должен подключить обработку этих событий.
