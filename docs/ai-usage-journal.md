# Журнал операций и резервов ИИ: задача 07

Миграция `20261020100300_ai_operations_and_reservations.sql`, после миграций задач 05–06. Основание — утверждённые документы кредитов/периодов в `workspace-front/docs`.

## Разделение записей

- `ai_usage_operations` — логическое действие пользователя или службы. UUID, компания на момент принятия, userID (обязателен для личного плательщика, опциональный инициатор службы), тип действия, ключ идемпотентности, SHA-256 fingerprint канонического запроса, статус и время. Компания/плательщик/fingerprint неизменяемы.
- `ai_usage_attempts` — каждый фактический вызов провайдера, включая retries, fallback и дополнительные вызовы инструментальных циклов. Ссылается на operation, сохраняет собственный UUID/номер, provider/endpoint, запрошенную и фактическую модель, provider request ID, версии коэффициентов и адаптера, снимок целых весов, исходные периоды, токены и окончательное списание.
- `ai_usage_reservations` — один резерв на попытку: UUID, положительный объём µcr, статус, время создания/закрытия, план следующей сверки. Удержанный объём immutable; расход после завершения находится в attempt, а не подменяет первоначальный резерв.

У компании и userID нет каскадного удаления этих данных. `source_kind/source_id` — необязательный информационный указатель на источник (например чат). Это **не внешний ключ** к сообщениям, чатам, Notebook, файлам или заданиям: удаление истории интерфейса не отменяет расход и не блокируется журналом. Не полагаться на существование источника при чтении журнала.

## Уникальность и идемпотентность

UUID operation глобально уникален. Для личной операции ключ уникален по `(user_id,idempotency_key)` независимо от компании: перевод не превращает повтор старого запроса в новое списание. Для служебной операции ключ уникален по `(organization_id,idempotency_key)`, независимо от инициатора. Fingerprint должен вычислять доверенный сервер; совпадение ключа с другим fingerprint/компанией не разрешает возвращать чужой результат или выполнять новый вызов. Будущий сервис обязан явно отклонить такой конфликт, а не делать безусловный upsert.

У попытки уникален `(operation_id,attempt_number)`. Известный `(provider_id,provider_request_id)` принадлежит только одной попытке. Provider ID должен включать область провайдерского аккаунта/проекта, если request ID гарантирован уникальным только в её пределах; ключи и секреты в provider_id не включать. Без такой гарантии адаптер не должен использовать неоднозначный ID как глобальный ключ. Provider_request_id nullable: неизвестный ID не заменяется пустой строкой или вымышленным значением.

Повтор получения одного результата не создаёт новую попытку; реальный повтор HTTP-вызова — новая попытка с новым номером. Ограничение UNIQUE на attempt_id не позволяет повторно создать резерв той же попытки. Проверка payload, запуск провайдера и идемпотентное завершение относятся к следующим сервисным задачам, а не обеспечиваются одним INSERT.

## Токены, веса и неизвестный результат

`reported_input_tokens/reported_output_tokens/reported_total_tokens` сохраняют исходные присутствовавшие целочисленные счётчики. `input_tokens/output_tokens/total_tokens` — нормализованные категории; input/output могут быть выведены адаптером по подтверждённому контракту. Cached/reasoning — подмножества соответствующих нормализованных категорий. Все счётчики nullable BIGINT: NULL означает неизвестно, а не 0.

Вместо произвольного JSON провайдера хранятся только типизированные поля: никаких промптов, файлов, ответов модели, ключей, URL или raw diagnostic payload. Некорректные отрицательные/дробные значения не записываются в нормализованные счётчики; ставится invalid, а безопасный код причины и диагностическое сопровождение определяются адаптером следующей задачи. Сырой JSON с потенциальными секретами в журнал не добавлять.

Вес input обязателен и положителен; остальные веса nullable, но при задании тоже положительны. Отсутствующий output weight подходит input-only профилям; для их verified/derived output_tokens нормализуется в 0. Финальное списание производится сервисом по снимку версии и весов, с checked arithmetic. Схема не является калькулятором: она не проверяет умножение токенов на коэффициенты. Число total — контрольное, не ещё одна категория списания. При verified/derived и известном total требуется равенство нормализованным input+output.

Снимки коэффициентов, идентификаторы, исходные окна и created_at неизменяемы после создания. Фактический иной model ID разрешается адаптером только по правилам версии политики; если его расход нельзя подтвердить по закреплённому профилю — сверка, без подмены исходной цены. Последующий механизм корректировок должен делать отдельные записи, не переписывать финальную попытку.

## Статусы

| Уровень | Допустимые статусы | Смысл |
| --- | --- | --- |
| operation | pending, running, completed, failed, cancelled, needs_reconciliation | Статус всего сценария; failed/cancelled не означают бесплатные попытки |
| attempt | reserved, sent, unknown | Ещё нет окончательного списания; charged_microcredits и completed_at NULL |
| attempt | settled | Verified/derived usage, списание >=0 и completed_at заданы |
| attempt | rejected | Подтверждено неисполнение, usage_status=confirmed_not_executed, списание 0 |
| attempt | waived | Неизвестный расход приняла платформа, usage_status=platform_absorbed, списание пользователю 0; токены остаются NULL, если неизвестны |
| reservation | active | closed_at NULL, включает неизвестные и ожидающие сверки попытки |
| reservation | settled | Резерв закрыт после списания, closed_at задан |
| reservation | released | Удержание снято без пользовательского списания, closed_at задан |

Usage_status: unknown/invalid/verified/derived/confirmed_not_executed/platform_absorbed. При verified/derived input/output и usage_source обязательны. Подтверждённый нулевой usage должен отдельно валидироваться адаптером; схема не доказывает бесплатность по нулю. Финальные попытки settled/rejected/waived и закрытые резервы не изменяются UPDATE. `reconcile_after` — срок следующей проверки, не автоматическое истечение резерва.

БД проверяет допустимые значения и согласованность полей внутри строки, но пока не обеспечивает весь автомат переходов между строками. Будущий сервис должен атомарно закрыть attempt и reservation, обновить все счётчики периода, правильно вывести operation status и не открывать новую попытку после окончательного закрытия сценария. Нельзя считать задачу 07 реализованным списанием.

## Периоды и перенос компании

Composite FK `(operation_id,organization_id)` не допускает перепривязку попытки к чужой компании; `(organization_id,company_period_id)` закрепляет недельное окно компании. Триггер требует личное пятичасовое окно пользователя операции, служебной попытке личное окно запрещено. Исторический пользователь сверяется по operation, а не по текущему `users.organization_id`.

При создании операции текущие права и принадлежность, а также соответствие момента резервирования границам периодов проверит будущий сервис. Миграция намеренно не отклоняет позднюю фиксацию истории уже переведённого пользователя. Она не переносит расход при переводе и не меняет revision настроек.

Индексы покрывают историю компании/пользователя, попытки операции, исходные периоды, известные provider IDs, незавершённые попытки и очередь активных резервов по reconcile_after. NULL reconcile_after не означает запрет обработки: соответствующие незавершённые попытки доступны по индексу pending.

Данная задача хранит исходный резерв и исходные окна. Материализация carried_reserved в новых периодах, блокировки бюджета, отсутствие двойного списания и сверка после сбоев будут реализованы сервисом позже. Не добавлен автоматический пересчёт старых `tokens_usage` сообщений: их недостаточно для достоверного журнала.

Команда: `go test ./db/migrations -count=1 -v` с `TEST_MESSENGER_DATABASE_URL` отдельной disposable БД. Тест `TestAIUsageJournalMigration` использует настоящие миграции обоих видов чатов, миграции 05–07 и минимальные users/organizations в уникальной схеме.

Проверяет конкурентное повторное создание операции, уникальность ключей/номеров/provider IDs/резервов, принадлежность окон, личного и служебного плательщика, NULL usage, границы и статусы, неизменяемые снимки, сохранение компании после перевода, а также удаление обычного и unified-чата: сообщения удаляются каскадно, подтверждённые кредиты и резерв остаются. Проверяются Down/reapply с сохранением таблиц предыдущей миграции.

Commit, push и развёртывание не выполняются этой задачей.
