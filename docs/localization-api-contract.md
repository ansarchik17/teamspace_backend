# BAS-010 / BE-06: контракт локализации для фронта

## Язык запроса и профиля

Поддерживаемые языки интерфейса: `ru` и `kk`. Значение по умолчанию — `ru`.

| Действие | API | Результат |
| --- | --- | --- |
| Получить сохранённый язык | `GET /api/v1/auth/me` | Поле `language` в профиле |
| Сохранить язык | `PUT /api/v1/auth/me/language` с `{"language":"kk"}` или `{"language":"ru"}` | HTTP 200, обновлённый профиль |
| Выбрать язык одного запроса | `Accept-Language: kk` или `Accept-Language: ru` | Перевод серверного текста без изменения профиля |

Профильные endpoints требуют обычной авторизации. Пустой, отсутствующий,
`null` или неподдерживаемый язык профиля возвращает HTTP 400. Значение
сохраняется между устройствами и сессиями. Для профиля используются ровно
`ru` / `kk`, а не `kz`, `en` или региональные варианты.

Для HTTP приоритет: поддерживаемый язык из `Accept-Language`, затем язык
авторизованного профиля, затем `ru`. Заголовок поддерживает региональные
теги и веса: `ru;q=0.2,kk-KZ;q=0.9` выбирает `kk`. Неподдерживаемый,
wildcard-only, некорректный или имеющий только нулевые веса заголовок
не переопределяет профиль. Ошибка чтения профиля даёт `ru`.

Ответ сообщает выбранный язык в `Content-Language: ru|kk` и включает
`Vary: Accept-Language`. Авторизованные ответы нельзя совместно кэшировать
между пользователями: без заголовка язык зависит от профиля. При сохранении
языка `Content-Language` относится к текущему запросу; поле `language`
ответа отражает новое сохранённое значение.

```ts
await fetch('/api/v1/auth/me/language', {
  method: 'PUT',
  headers: {
    Authorization: `Bearer ${token}`,
    'Content-Type': 'application/json',
    'Accept-Language': 'kk',
  },
  body: JSON.stringify({ language: 'kk' }),
});
```

## Ошибки API

Основной формат:

```json
{"error":{"code":"NOT_FOUND","message":"Данные не найдены.","user_message":"Данные не найдены."}}
```

`code` — стабильный идентификатор, независимый от языка. `message` и
`user_message` — безопасные тексты для показа пользователю. `details`
опционален и содержит только разрешённые бизнес-данные: например квоты,
версии заметки, конфликты календаря, требования доступа и локализованные
подсказки валидации. SQL, stack trace, ответы провайдеров и секреты не
предназначены для UI и исключаются из публичного ответа.

Некоторые старые endpoints сохраняют плоский формат:

```json
{"code":"BAD_REQUEST","error":"Некорректный запрос. Проверьте введённые данные.","message":"Некорректный запрос. Проверьте введённые данные.","user_message":"Некорректный запрос. Проверьте введённые данные."}
```

Фронт должен поддерживать оба формата. Обработку определяет `code`, а не
совпадение текста. Сначала можно использовать собственный перевод кода,
если он есть в каталоге фронта; иначе показывать серверный `user_message`,
затем `message`, затем строковый `error`. При отсутствии безопасного текста
используется общая ошибка из каталога фронта. Тексты ошибок не следует
интерпретировать как HTML.

Неизвестный, но корректный код сохраняется сервером и получает общий
безопасный перевод по HTTP-статусу. Фронт обязан поддерживать такие коды.
Для старых ошибок без кода действуют следующие значения:

| HTTP | Код по умолчанию |
| --- | --- |
| 400 и прочие клиентские ошибки | `BAD_REQUEST` |
| 401 | `UNAUTHORIZED` |
| 403 | `FORBIDDEN` |
| 404 | `NOT_FOUND` |
| 409 | `CONFLICT` |
| 413 | `FILE_TOO_BIG` |
| 422 | `VALIDATION_ERROR` |
| 429 | `TOO_MANY_REQUESTS` |
| 5xx | `INTERNAL_ERROR` |

Специфический код приложения имеет приоритет над таблицей. В Drive batch
HTTP 207 означает смешанный результат: проверяйте `results[].status`,
`results[].code` и `results[].error` отдельно для каждого элемента.

## Уведомления, email и пользовательские данные

Системные уведомления, push и email формируются отдельно на языке профиля
каждого адресата. Язык запроса инициатора и язык внешнего отправителя не
переопределяют адресата серверного шаблона. Нет поддерживаемого языка — `ru`.
Уже сохранённые уведомления не переводятся заново при смене профиля.

Имена, пользовательские сообщения, названия/описания встреч, задач,
документов и публикаций не переводятся. Машинные коды, enum, IDs, ссылки,
ISO-даты и содержимое скачиваемых файлов сохраняют свой формат. Промпты и
описания инструментов для модели не являются пользовательским переводом;
готовые серверные speech/display-ответы переводятся. Сгенерированный моделью
или полученный от пользователя текст не обрабатывается как ключ каталога.

## Каталоги и проверки

Каталоги `internal/i18n/*.json` встраиваются в сервер. Все используемые ключи
должны иметь непустые версии `ru` и `kk` с одинаковыми параметрами шаблона.
Отсутствующий перевод выбранной локали имеет runtime-fallback на русский;
CI-проверки всё равно считают неполный каталог ошибкой. Неизвестный ключ или
отсутствующий параметр — ошибка разработки, которую проверяют тесты.

Проверяются наборы ключей и параметров каждого каталога, используемые
литеральные ключи и именованные шаблоны в коде, варианты динамических email
и системных событий, выбор HTTP-языка, fallback, стабильность кодов,
защита диагностик, язык получателя и изоляция кэша готовых AI-ответов.
Инвалидация кэша удаляет обе языковые версии.

```sh
go test ./internal/i18n ./internal/middleware ./internal/apperrors ./internal/handler ./internal/service ./internal/server ./internal/repository
```

Для части тестов нужны локальные HTTP-серверы. БД-интеграционные тесты
используют настройки проекта и могут пропускаться, если тестовая БД не задана.
Новая миграция не требуется; используется поле языка из BE-01.

Подробности: [профиль](user-language.md), [механизм](server-localization.md),
[ошибки](api-error-localization.md), [уведомления](system-notification-localization.md),
[email](email-localization.md).
