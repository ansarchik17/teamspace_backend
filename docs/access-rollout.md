# Порядок выпуска прав и ЭДО — задача 10

Основание: [локальная приёмка и её границы](access-acceptance.md), [доставка поручений](odo-assignments-rollout.md), [команда выполнения](odo-assignments-completion.md). Документ готовит выпуск; серверы этой задачей не изменялись.

## 1. Зафиксировать состав

Собрать отдельный релиз только изменений задач прав/ЭДО. В Workspace есть посторонние незакоммиченные AI-изменения: не переносить рабочие каталоги целиком. Backend/frontend ЭДО и СД сейчас проверяются в отдельных рабочих копиях `access-task6-*`. iForm проверен по исходникам `west6ide/iform`; новых изменений Java-кода эта задача не добавляет.

Для каждого образа записать commit SHA, digest, пройденные проверки, migration ledger до/после и предыдущий совместимый digest. Для iForm сопоставить фактически установленную версию с проверенным контрактом; один факт доступа к репозиторию не доказывает обновление сервера. Секреты/токены/персональные данные не включать в манифест.

До выпуска исправить расхождения `api-contract-check` ЭДО со Swagger либо согласовать конкретный ограниченный состав отдельного выпуска с доказанным контрактом. Нельзя пометить общий gate зелёным, скрыв эту ошибку.

## 2. Схема БД

Новых миграций в задаче 10 нет. Сначала проверить фактически применённые версии штатным runner/ledger каждой БД; повторно уже применённые SQL вручную не выполнять. Сохранить проверяемые резервные копии в защищённом хранилище.

| БД | Требуемые существующие миграции/зависимости |
| --- | --- |
| Workspace | `20261002000100_organization_access.sql` → `20261003000100_sync_employee_access_position.sql` → `20261006000100_iform_access.sql`; для поручений `20261014000300_odo_assignment_sync_v1.sql` → `20261014000400_odo_assignment_backfill_audit.sql`; для операций iForm `20261019000100_iform_operation_receipts.sql` |
| ЭДО auth | Текущая последовательность до `000026`, включая `000023_organization_membership` и `000024_workspace_position_access` |
| ЭДО document | Текущая последовательность до `000026_document_creation_idempotency`, включая company scope, версии, подпись и архив. Полная цепочка включает `vector` через `000015_ai_agent` — нужен PostgreSQL с pgvector |
| ЭДО workflow | Последовательность до `000020_workspace_assignment_commands`, включая workflow-plan/CAS, `000018` snapshots и `000019` backfill |
| SenimDesk | Задачи применения прав не добавили SQL; проверить штатные prerequisites установленной версии |
| iForm | Flyway и Flowable установленного релиза; тестовая Java-приёмка выполнена на пустой отдельной БД, production ledger не проверен |

Таблица перечисляет зависимости функции, а не разрешает пропускать промежуточные миграции runner. Для Workspace использовать штатный migration job (`cmd/migrate`, `RUN_DB_MIGRATIONS`, `MIGRATIONS_DIR`, `POSTGRES_*`), проверив итоговый список pending SQL. Посторонние pending миграции требуют отдельного релизного состава. Для ЭДО использовать `cmd/migrate -service auth|document|workflow` с DSN соответствующей БД. `-service all` допустим только с тремя правильно заданными `*_DATABASE_URL`; не запускать все три сервиса против одного общего ledger.

В задаче 10 штатный runner ЭДО реально применил все эти цепочки на трёх пустых отдельных тестовых БД: auth/document до 26, workflow до 20. Это проверка чистой установки, а не обновления копии production с её историческими данными. Апгрейд snapshots отдельно покрыт миграционными интеграционными тестами; перед выпуском всё равно проверить состояние/данные согласованного стенда.

## 3. Конфигурация перед запуском

Вначале держать команды выключенными: Workspace `ODO_COMMANDS_ENABLED=false`, ЭДО `ODO_WORKSPACE_COMMANDS_ENABLED=false`. До готовности приёмника sender `ALEM_WORKSPACE_SYNC_ENABLED=false`. Это не отключение managed-режима должностей.

| Связь | Что сверить |
| --- | --- |
| Workspace → права ЭДО | Auth-service `WORKSPACE_API_BASE_URL` (или существующий fallback `ALEM_WORKSPACE_API_URL`), доступность пользовательских `/organizations/current/access?application=odo` и `/users?application=odo`; ошибки источника закрывают доступ |
| Пользовательская авторизация | `WORKSPACE_JWT_SECRET/ISSUER/AUDIENCE` соответствуют выпуску Workspace; Keycloak — фактический `KEYCLOAK_ISSUER_URL`, JWKS/audiences/AZP. Адреса из разных конфигурационных пространств не считать взаимозаменяемыми |
| Отправка поручений | `ODO_ASSIGNMENTS_ENABLED`, `ODO_ASSIGNMENTS_CLIENT_ID`, `ODO_ASSIGNMENTS_SERVICE_SUB`, `ODO_ASSIGNMENTS_AUDIENCE`, `ODO_ASSIGNMENTS_COMPANIES`, `ODO_ASSIGNMENTS_SOURCE_ORIGIN`; на ЭДО matching issuer/client/allowlist/service-account, `ALEM_WORKSPACE_API_URL`, token URL/secret и публичный URL по существующему rollout |
| Команда выполнения | Workspace `ODO_COMMANDS_BASE_URL` — закреплённый BFF без `/api/v1`, `ODO_COMMANDS_TIMEOUT=10s`; ЭДО `ODO_WORKSPACE_COMMANDS_ENABLED`; `ALEM_WORKSPACE_SYNC_IDENTITY_ISSUER` совпадает с namespace подтверждённых sub |
| SenimDesk | `WORKSPACE_ACCESS_API_URL`, `WORKSPACE_ACCESS_INTERNAL_TOKEN`, действующая связь UUID компании; managed worker не управляет ролями через старые `workers:update` |
| iForm | `IFORM_AUTH_MODE=workspace`, `IFORM_SSO_ISSUER`, `IFORM_SSO_PUBLIC_KEY_DER_B64`, `WORKSPACE_DIRECTORY_URL`, `IFORM_DIRECTORY_TOKEN`; действующие ключи соответствуют мосту Workspace |

Не подставлять сервисный токен вместо пользовательского. Не выдавать рабочие права по email, имени должности или названию компании. Проверить trusted proxy/HTTPS/часы и сетевую доступность из контейнеров. Env из `env_file` применяется пересозданием соответствующего контейнера штатным deploy, не одним restart. Новых секретов задача 10 не вводит.

## 4. Очерёдность обновления

1. Прогнать локальный gate, отдельные СД/iForm-проверки и стендовые сценарии; закрыть OpenAPI-расхождения. Зафиксировать релизный состав.
2. Подготовить тестовые компании A/B и семь отдельных активных пользователей A, плюс пользователя B. Сохранить наборы должностей с зависимостями и назначения; директор и суперадмин отдельно проверяют административную область. Названия ролей сами по себе ничего не выдают.
3. Применить отсутствующие миграции при выключенных новых командах/sender. Проверить версии, readiness и отсутствие ошибок мигратора.
4. Обновить Workspace backend: каталог, зависимости, актуальный access/directory, административные назначения и командный мост.
5. Совместимым комплектом обновить auth-service, document-service, workflow-service и BFF ЭДО. BFF и workflow должны понимать одинаковый protobuf/receipt. Старый сервис, не возвращающий durable receipt, не считается успешным получателем команды.
6. Обновить backend SenimDesk с guard рабочих прав. iForm обновлять, если установленная версия не соответствует проверенному контракту; без этого не объявлять общую связку готовой.
7. Обновить Workspace/ЭДО/СД frontend после готовности их API. Проверить загружаемые ассеты/кэши; сохранённые команды в sessionStorage не удалять ради обхода 409.
8. Включить приёмник Workspace, затем sender ЭДО. Проверить одно новое поручение и получение source revision. Исторический backfill запускать отдельно по его плану, не одновременно с включением прав.
9. Включить `ODO_WORKSPACE_COMMANDS_ENABLED=true`, затем Workspace `ODO_COMMANDS_ENABLED=true`. Проверить команду, durable receipt и последующий outbox-снимок. Статус Workspace меняется по снимку, а не по HTTP receipt.
10. Включать управление по должностям по одной согласованной компании/приложению после сохранения наборов. Для уже managed компаний режим сохранять. Пустые/неполные старые наборы не переписывать автоматически; исправлять явно через редактор. Нельзя включать legacy-режим для обхода отказов.

## 5. Обязательная стендовая приёмка перед расширением

Для каждой из семи ролей выполнить допустимое действие и повторить запрещённые действия напрямую к API с её реальной сессией; для каждого пользователя проверить документ A без ACL, документ B другой компании и отзыв нужного права при открытой странице. Записать ожидаемый/фактический код и неизменность объекта при отказе. Вернуть только тестовые права по завершении в соответствии с согласованным исходным состоянием.

Дополнительно:

- Автор → регистратор → текущий согласующий → исполнители → назначенный подписант согласно настроенному маршруту; отсутствие кандидата блокирует запуск заранее. Последовательный/параллельный этап не пропускается; возврат на доработку и повторный маршрут не используют старое решение.
- В компании с одним сотрудником автор может регистрировать/исполнять при правах; самосогласование и самоподпись остаются запрещёнными. Автоматически ослаблять правило нельзя.
- Действующий владелец получает все реализованные рабочие права своей компании автоматически. Должность «директор» без владения и суперадмин без рабочего набора сохраняют только разрешённое администрирование. Наблюдатель с `document.read_all` не становится участником решения/подписи.
- Переназначение, отзыв права/членства/модуля, старый command ID, одновременные команды, timeout после commit, 409 и повтор неизменной команды. Старому исполнителю отказывать даже по сохранённому receipt.
- Реальный handoff Workspace → ЭДО сохраняет компанию и документ; старые OnlyOffice/Collabora токены не дают читать/сохранять после отзыва. Проверить СД и iForm в тех же условиях, а не только вход в приложение.
- Пропажа источника прав не возвращает локальные административные привилегии. Новое поручение отображается после подтверждённой доставки; при обычной очереди проверить в пределах 30 секунд, при backlog учитывать next_retry_at.
- Подпись проверить через установленный провайдер на явно тестовом документе; локальная синтетическая подпись не доказывает настройку production-криптографии.

В акте оставить дату, SHA/digests, тестовую компанию, обезличенный actor, document/assignment ID, revision, command/event ID, HTTP-код, статус источника/проекции и ссылку на безопасный trace. Bearer, секреты и текст результата не записывать.

## 6. Остановка и откат

При отказе сначала выключить команды Workspace, затем ЭДО; при сбое доставки остановить sender. Receipt/outbox/revision сохранить. Не откатывать БД через `Down` и не очищать журнал, чтобы восстановить ложный успех.

Откат на версию до исправления рабочих прав может восстановить обходы admin/owner. Поэтому старые образы можно вернуть только при доказанной эквивалентности проверок; иначе временно закрыть соответствующий модуль/операции и исправить вперёд. Не отключать managed-режим как аварийное «исправление»: это возвращает legacy RBAC. После восстановления повторить стендовую матрицу на тестовых данных, затем расширять компании.

Критерий окончания: зелёные обязательные проверки, подтверждённый акт всех ролей на согласованном стенде, совпадение миграций/настроек/образов, отсутствие необъяснимых отказов и дублей. В текущей локальной задаче этот серверный акт ещё не выполнен.
